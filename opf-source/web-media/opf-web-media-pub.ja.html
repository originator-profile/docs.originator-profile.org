はじめに

Originator Profile Framework は、コンテンツの [=Recipient=] が、その コンテンツの [=Originator=] は誰か、そしてその [=Originator=] について 第三者が何を validate したかを、[=Originator=] 自身が提示するデータから 知ることを可能にする。Architectural Overview [[OPF-AOV]] は一般モデルを 記述している。Core Specification [[OPF-CORE]] はすべての use case が 共有するフレームワークの部分を定め、コンテンツをどう届けるかに依る部分は、 届け方ごとの [=Use Case Specification=] に委ねている。本文書は、website 上で公開され web ページの中で提示されるコンテンツについての [=Use Case Specification=] であり、その use case のモデル、すなわち [=Web Media Specific Model=] も定める。

概略を述べれば、このユースケースは次の 3 つから成る。

  • [=Originator Profile=] は、それをページとコンテンツに結びつける文書 とともにページの中を運ばれる。その文書とは、コンテンツに対する [=Content Attestation=]（コンテンツへの署名による証明）と、 サイトの well-known リソースから配られ、[=Originator Profile=] を 提示してよい origin を列挙する [=Website Profile=] である。この 2 つはいずれも [=Core Profile=] の [=Originator Verification Key=] で署名される。このユースケースでは、 [=Originator Profile=] は、[=Originator=] ではなく [=Core Profile Issuer=] が発行する [=Web Media Profile=] も含む。 [=Content Attestation=] と [=Website Profile=] は、 [=Originator Profile=] そのものの外側にある。
  • DNS は、Core Specification がすべてのユースケースで与えている役割、 すなわち鍵が現行であることの確認（currency）と revocation を担う（[[OPF-CORE]], Ordering of Local and DNS Steps）。[=Originator=] が 自身の [=Identity=] のゾーンに公開するレコードは、Core Specification では optional であり、[=Use Case Specification=] がそれを要求する ことも許されている。このユースケースはそれを optional のままとする。 ただし、[=Website Profile=] が自らの [=Identity=] の外の host を 挙げる [=Originator=] は [=Permitted Host Record=] を要する（）。したがって、自らのゾーンが DNSSEC で署名 されていない組織でも、この framework を利用できる。
  • 検証は、ページが提示される時点で、ブラウザ拡張のようなブラウジング ソフトウェア内の [=Verifier=] か、ページを取得するサービスによって 行われる。この配送チャネルには結果を記録しておける 場所が無いため、判断はページが提示されるたびに改めて行われ、 validity は検証の時点を基準として判断される。

他の文書との関係

本文書は、Core Specification [[OPF-CORE]] のいう意味での [=Use Case Specification=] である。すなわち、Core Specification をコンテンツ配送の一つの やり方に当てはめ、Core Specification が [=Use Case Specification=] に委ねている事項を定める。その事項は次のとおりである。

本仕様に固有の用語

Page Origin
ある提示における [=Page Origin=] とは、[=Content=] が [=Recipient=] に提示されるページの origin [[RFC6454]] である。 これは [=Content=] が届く際の identity であり、本仕様が [=Originator=] に結びつける対象である。すなわち、このユースケース における [=Presented Identity=] であり、 が求めるとおりに取得され、正規形に 直される。
Web Media Profile
[=Web Media Profile=] は、website で [=Content=] を公開する [=Originator=] に関する [=Validated Attributes=] の集合である。 編集方針や連絡先情報のように、web メディア向けの領域固有な [=Validated Attributes=] を含む。このユースケースでは、これは [=Core Profile=] と [=Profile Annotations=] とともに [=Originator Profile=] の一部であり、これが有効でなくなると [=Originator Profile=] も有効でなくなる。
Web Media Profile Issuer
[=Web Media Profile Issuer=] は、[=Core Profile Issuer=] が [=Web Media Specific Policy=] の下で [=Originator=] のために [=Web Media Profile=] を発行するときの役割であり、独立した Entity ではない。本仕様が求めるとおり、ある [=Originator=] の [=Web Media Profile=] は、その [=Originator=] の [=Core Profile=] を発行した [=Core Profile Issuer=] が発行する。 この issuer は、プロファイルに含まれる Attributes を validate し、それらが [=Originator=] を正確に表していることを保証する 責任を負う。
Web Media Specific Model
[=Web Media Specific Model=] は、Web Media のユースケースに向けて Base Model を拡張したモデルであり、領域固有な [=Validated Attributes=] と validation の仕組みを取り込む。
Web Media Specific Policy
[=Web Media Specific Policy=] は、[=Core Profile Issuer=] が発行する [=Web Media Profile=] と、[=Originator=] 自身が発行する [=Website Profile=] について、その発行と管理を律するポリシーの集合 である。
Website Profile
[=Website Profile=] は Signed Data from Originator であり、 [=Originator=] 自身が発行し、その [=Originator=] が自身の [=Content=] を公開する website を述べる。[=Verifier=] は、web ページを [=Originator=] に結びつけるためにこれを必要とする。この プロファイルは、それらの website の origin などの情報を含む。 これは [=Originator Profile=] の一部ではない。[=Content Attestation=] と同じくその外側にある。それに署名した鍵が [=current=] でなくなったとき、その鍵を運ぶ [=Core Profile=] が valid でなくなったとき、またはそれ自身の署名の有効期間が 終わったときに効力を失う（）。

ページの構造

本仕様に従って [=Originator Profile=] を提示するページは、3 種類のもの を運ぶ。[=Originator Profile Bundle=]、そのプロファイルの外側にあって それとともに運ばれる文書、そしてコンテンツそのものである。本節はこれら がそれぞれ何であるかを述べる。[=Verifier=] がそれらに対して何をするかは にある。

Originator Profile Bundle

Bundle が運ぶもの。[=Originator=] は、自身の [=Originator Profile Bundle=] に、Core Specification が [=Originator Profile Bundle=] の運ぶものと定める文書を含めなければ ならない (MUST)（[[OPF-CORE]], Originator Profile Bundle）。これらの各文書の形式は Core Specification [[OPF-CORE]] が定めている。

Originator が bundle の中で提示するもの。[=Originator=] は、自身の [=Originator Profile Bundle=] の中で、 自身の [=Profile Annotations=] を少なくとも 1 つ提示しなければ ならない (MUST)。これは、Core Specification が各 [=Use Case Specification=] に、[=Originator Profile Bundle=] を組む 当事者に課すよう求めている要件である（[[OPF-CORE]], Requirements on Use Case Specifications）。 このユースケースでは、[=Originator Profile=] は [=Originator=] の [=Web Media Profile=] を含み（）、 [=Originator=] は、自身の [=Web Media Profile=] も、ページの中か well-known リソースで、自身の [=Originator Profile Bundle=] の中に 提示しなければならない (MUST)（）。

chain は全体がページとともに運ばれる。 [=Originator Profile Bundle=] は各 [=Accreditation Chain=] の全体を 運ばなければならない (MUST)。[=Verifier=] は、ページと [=Page Origin=] の well-known リソースが運ぶもの以外に [=Originator Profile=] の一部を取得することを求められていない （）。[=Core Profile Issuer=] と各 [=Profile Annotation Issuer=] の [=Core Profile=] は、それぞれの [=Accreditation Chain=] とともに [=Originator Profile Bundle=] の 中にある。ただし [=Verifier=] が持つ [=Root Core Profile=] は除く。

Verifier が使わない文書は失敗ではない。 Core Specification が求めるとおり（[[OPF-CORE]], Originator Profile Bundle）、[=Verifier=] は、[=Originator Profile Bundle=] が自分の使わない文書や 認識しない文書を運んでいるという理由で、検証を失敗として扱わない。 これがあるからこそ、将来の版がページに文書を追加したり、 [=Originator Profile Bundle=] の一部を別の経路で取得するようにしたり しても、既に配備された [=Verifier=] を壊さずに済む。

Originator Profile の外側にある文書

プロファイルの外側にある 2 つの文書と、その内側にある Web Media Profile。2 つの文書が [=Originator Profile=] の外側にあり、それとともに運ばれる。 [=Content Attestation=] と [=Website Profile=] である。[=Content Attestation=] は、そのページの [=Content=] が [=Originator=] に由来することを証する。[=Website Profile=] は、 その [=Originator Profile=] を提示してよい origin を列挙する もので、 が [=Page Origin=] と突き合わせる 対象はこの文書である。[=Web Media Profile=] は、[=Originator=] の web メディアに固有の情報を運ぶもので、このユースケースでは [=Originator Profile=] の一部である。Core Specification は、 [=Use Case Specification=] がそう定めることを認めている。 の手続きはその発行者、署名、 署名の有効期間を確かめ、本版は [=Verifier=] がそれに対してほかに何をするかを 定めない。

Website Profile を誰が発行し、どの鍵で署名するか。 [=Website Profile=] は [=Originator=] 自身が発行しなければならず (MUST)、その発行者はその [=Originator=] の [=Identity=] である。 [=Originator=] は、これと [=Content Attestation=] に、自身の [=Core Profile=] の [=Originator Verification Key=] で署名する。

Web Media Profile を誰が発行し、どの鍵で署名するか。 [=Web Media Profile=] は、それが対象とする [=Originator=] の [=Core Profile=] を発行した [=Core Profile Issuer=] が発行し、その issuer 自身の [=Core Profile=] の鍵で署名しなければならず (MUST)、 [=Originator=] 自身が発行するのではない。その issuer は、 [=Core Profile=] に署名するのと同じようにそれに署名する。本仕様は、 その役割を [=Web Media Profile Issuer=] と呼ぶ。 [=Web Media Profile=] は [=Web Media Specific Policy=] の下で 発行される。その policy が発行者に何を求めるかは、ここではなく Operational Governance Requirements [[?OPF-GOV]] が述べる。

validity はプロファイルと署名鍵に従う。この 2 つの 文書はどちらも DNS に登録されず、どちらも自前の revocation 機構を 持たない。その validity は [=Originator Profile=] と、それらに署名 した鍵に従う。これは Core Specification [[OPF-CORE]] が [=Originator Profile=] の外側にある文書について述べているとおりで ある。[=Web Media Profile=] も DNS にレコードを持たず、自前の revocation 機構も持たない。それと [=Originator Profile=] は ともに終わる（3 つのそれぞれが服する validity の層: 。外側にある 2 つの文書の位置が 1 つのサイトについての主張の撤回にとって何を意味するか: ）。

allowedUrl が挙げてよいもの。[=Originator=] は、 [=Content Attestation=] の allowedUrl に書く各 URL Pattern string [[URLPATTERN]] を、scheme を https （host が localhost の場合は http でもよい） とし、固定の host 名を持つ形で書かなければならない (MUST)。host 名が 固定であるとは [[RFC1123]] Section 2.1 の意味においてであり、 許される wildcard は先頭の *. のラベルだけである。 allowedUrl がそれ以外に何を挙げてよいかは、 Operational Governance Requirements [[?OPF-GOV]] が上限を定める。

Core Specification [[OPF-CORE]] は、[=Originator Profile=] の外側に ある文書が何を含み、[=Verifier=] がそれに対して何をするかの定義を [=Use Case Specification=] に委ねているが、本版はまだそれを行って いない。それらの文書と、このユースケースが [=Originator Profile=] に加える [=Web Media Profile=] のそれぞれについて、下の箇条は、本文書が確定させて いること、現在の Originator Profile Blueprints [[?Originator Profile Blueprints]] でその文書を述べているページ、 ここではまだ定義していないこと、を挙げる。

  • [=Website Profile=]。
    • ここで確定していること: サイトの代表 URL と、[[RFC6454]] の 意味での origin（scheme、host、既定でないポート）を 1 つ以上 運ぶ。その発行者と、それに署名する鍵は、この節で述べている。
    • Blueprints では: Website Profile。そこでは、値は origin の ASCII serialization として、path、query、fragment を含めず、既定のポートを省いて 書く。これは URL Standard [[URL]] が origin を serialize する 形である。 の比較は、別の形で書かれた 値でもそれを parse して得られる origin を指すように定めてある。
    • ここではまだ定義していないこと: プロパティ名、多重度、origin の書き方。これらは Blueprints から取る。
  • [=Content Attestation=]。
    • ここで確定していること: 本版が名指すプロパティは allowedUrl 一つだけであり、それが何を挙げてよいかを 述べるため（この節）と、[=Verifier=] にその確認を求めるため （）に名指して いる。それに 署名する鍵は、この節で述べている。
    • Blueprints では: Content Integrity Descriptor。Blueprints は web ページ向けに、 [[OPF-AOV]] の意味での Content Integrity Descriptor を 3 種類 登録している。HTML の断片（その outerHTML）、DOM の部分木の中の テキスト（その textContent）、外部リソースである。4 つ目の DOM の部分木の中の可視テキスト（その innerText）は、そこでは 非推奨である。allowedUrl のほか、[=Content Attestation=] が何を運ぶべきかは Blueprints が述べるとおりのままである。
    • ここではまだ定義していないこと: [=Content Attestation=] が それらの種類のどれを、どの形で運ぶか。そして、そこから定まる、 [=Verifier=] が [=Content Attestation=] をページの [=Content=] とどう突き合わせるか。
  • [=Web Media Profile=]。
    • ここで確定していること: その発行者と、それに署名する鍵。 この節で述べている。そして、[=Verifier=] がそれについて何を 確かめるか（）。
    • Blueprints では: Web Media Profile。そこでは、組織の登録情報ではない、 [=Originator=] の web メディアに固有の [=Validated Attributes=]、 たとえば編集方針、プライバシーポリシー、連絡先情報、ロゴ、 公式 URL を運ぶ。
    • ここではまだ定義していないこと: その内容。そして、そこから 定まる、[=Verifier=] が [=Web Media Profile=] に対して の確認のほかに何をするか。

Originator Profile Bundle と Content Attestation が Verifier に届く道筋

[=Originator Profile Bundle=]（このユースケースでは [=Web Media Profile=] も運ぶ）と、[=Originator Profile=] の 外側にある 2 つの文書、すなわち [=Website Profile=] と [=Content Attestation=]（）は、2 つの 経路で [=Verifier=] に届く。ページは [=Originator Profile Bundle=] と [=Content Attestation=] を運び、[=Page Origin=] の well-known リソースは [=Originator Profile Bundle=] と [=Website Profile=] を 運ぶ。[=Verifier=] が同梱する文書をそれらに 加えることができる。[=Originator Profile=] のいかなる部分も DNS から取得されることはない。これらすべての出どころの文書は、 の順序で合わせて取り扱われる。 その順序の意味は Core Specification [[OPF-CORE]] が与えるところに よる。

  • ページが文書をどう運ぶか（）。
  • [=Verifier=] がいつページを読み、結果がいつ終わるか（）。
  • 2 つの経路と、[=Verifier=] が同梱する文書とを、どう合わせて 用いるか（）。
  • 文書をどの順序で取り扱うか（）。
  • [=Verifier=] が 1 つの文書の発行の中からどう選ぶか（）。

ページの中に運ばれる文書

ページはこれらの文書を script 要素 [[HTML]] の中に運ぶ。 その要素は type 属性を持たなければならない (MUST)。 その値は、要素が Content Attestation Set を運ぶ場合は application/ca-set+json、Originator Profile Set を運ぶ 場合は application/op-set+json である。要素は次の 2 つの 形式のいずれかを取り、ページはどちらを用いてもよい (MAY)。

  • 埋め込み形式: script 要素の内容が JSON オブジェクト そのものである。
  • 参照形式: 要素は src 属性の URL によってオブジェクト を指し示し、[=Verifier=] がその URL からオブジェクトを取得する。 本仕様は、そのような要素に integrity 属性 [[?SRI]] を求めず、付いている場合についても [=Verifier=] に何も 求めない。ブラウジングソフトウェア自身は、そのような要素の URL を 取得しない。型を知らない script 要素は処理しないからである [[HTML]]。取得するのは [=Verifier=] である。
値 application/ca-set+json と application/op-set+json は、Originator Profile Blueprints [[?Originator Profile Blueprints]] が求めるものである。 Blueprints は、それ以前に用いられていた値 application/cas+json と application/ops+json を非推奨とし、2027 年 11 月 1 日に そのサポートを終える。それまでは、ページはそれらを用いないことが、 [=Verifier=] はそれぞれをそれに代わる値として扱うことが望ましいと されている。この移行を本仕様が引き継ぐかどうかは決まっていない。 メディアタイプを最終的に何にするかは検討中であり、それらをどこに 登録するかは別の問いである（）。

ページについて本仕様が未定のまま残すこと。本仕様は 次のどれも定めない。

  • そのような要素がページのどこ、head か body かに置かれるか。
  • [=Verifier=] がいつページを読むか（）のほか、それが与えられたページから 文書を取り出す手続き。
  • 2 種類の set がそれぞれ何を含むか。個々の文書の内容を定めないのと 同様である（）。
  • 1 つの Originator Profile Set が、それの運ぶ [=Profile Annotations=] に単一の順序を与えるかどうか。これは、本仕様が 述べる何ごとかによってではなく、その set の形式から決まる。その形式を 定める版がそれを決し、順序を与えない場合にはその順序をここに書く。

各形式でページが決めるもの。本仕様が、文書がページの 中に運ばれる、と述べるとき、それは両方の形式を 指す。2 つの形式は、ページが何を決めるかで異なる。埋め込み形式では、 ページは文書そのものを決める。参照形式では、ページが決めるのは URL だけである。その URL を配信する者が、取得で何が得られるかを選び、 文書を返さないことも、以前の文書や別の文書を返すこともできる。ただし、 返したものがその発行者の署名を持たなければ、検証に通らない（それが 何を成り立たせ、何を成り立たせないかは ）。

[=Originator Profile Bundle=] の authenticity は、その中の文書が 運ぶ署名だけに依っており、他の何にも依っていない。ページを HTTPS で 配信することは [=Page Origin=] を確立し、それは が必要とするものである。しかしそれは [=Originator=] について何も述べない。その origin を支配する者が、 ページが何を運ぶかを支配するからである。文書の外側には、コンテンツと [=Originator Profile Bundle=] の存在とをまとめて守る署名が無い。 が [=Website Profile=] 自身の 言い分以上のものを求めるのは、一つにはこのためである。各文書の authenticity はそれ自身の署名に依っているので、 文書を参照する要素に integrity 属性を求めない。参照先を 差し替えられる者が得るのは、検証に通らないページ以上のものではなく、 それは が述べる否認である。

ページを読む時点

読み取りは要素が挿入されたときに始まる。 [=Verifier=] は、type が application/ca-set+json である要素の文書を探すことを、 その要素が Document に挿入された [[HTML]] ときに始めなければならない (MUST)。挿入したのがパーサーかスクリプトかは問わない。 template 要素の内容の中の要素や shadow tree の中の要素は、 この意味で Document に挿入されたものではなく、読まれない。ページを 取得するサービスはスクリプトを実行しないので、取得したソースの要素を 読む。

1 つの attestation の手続きの入力。1 つの [=Content Attestation=] の手続きが用いる文書は、1 つの Document の ある 1 時点の状態から取らなければならない (MUST)。それらは、その Document の要素、それがトップレベル文書である場合はその [=Page Origin=] の well-known リソース（）、そして [=Verifier=] が同梱する 文書から来る。親の文書や兄弟の文書の要素は用いない。 が比べるページの URL は、 その時点のその Document の URL である。

結果は、それが依拠したものが変わると終わる。 [=Verifier=] は、次のいずれかが起きたら、[=Content Attestation=] についての結果を無効にしなければならない (MUST)。

  • 手続きが用いた文書を運んでいた要素が、Document に留まらなく なる。
  • その [=Content Attestation=] が対象とするものが変わる。
  • allowedUrl の確認をやり直すことになる（）。

結果を無効にした後、[=Verifier=] はその [=Content Attestation=] を 改めて検証してよい (MAY)。無効にした結果は検証の失敗ではなく、 失敗としては提示されない。

スクリプトで内容を組むページがすること。 [=Content Attestation=] が対象とする [=Content=] をスクリプトで組む ページは、Content Attestation Set を運ぶ要素を、その [=Content=] を 組み終えた後に初めて挿入しなければならない (MUST)。その attestation の検証に要る Originator Profile Set を運ぶ要素は、その要素より 遅くならないように挿入しなければならない (MUST)。

要素が挿入された後、手続きの入力をいつ Document から取るかは、本改訂 では定まっていない。

2 つの経路と、Verifier が同梱する文書

両方の経路を用い、どちらも優先しない。 [=Page Origin=] の well-known リソースとは、その origin のパス /.well-known/sp.json [[RFC8615]] にあるリソースで あり、その形式は Originator Profile Blueprints [[?Originator Profile Blueprints]] が与える。そのリソースは Originator Profile Set と [=Website Profiles=] を運ぶ。[=Content Attestation=] は運ばない。 [=Content Attestation=] は、ページの中か、[=Verifier=] が同梱する 文書の中でだけ [=Verifier=] に届く。ページは [=Website Profile=] を 運ばない。[=Website Profile=] は、そのリソースからか、[=Verifier=] が同梱する文書の中でだけ [=Verifier=] に届く。[=Verifier=] は、ページの中にいずれかの形式で 運ばれる文書を、そのリソースにある文書と合わせて用いなければならない (MUST)。どちらの経路も他方に優先しない。各文書は が述べるとおりそれぞれ単独で 検証され、検証に通った文書は、どの経路で来たものであってもすべて 用いられる。したがって、一方の経路が欠いた文書も、他方の経路が 運んでいれば欠けてはいない。

何も得られない経路。ページがそのような要素を運んで いない、あるいは well-known リソースが得られない場合、その経路からは 何も得られないが、それ自体では検証の失敗ではない。 ページが [=Content Attestation=] を運んでいるのに、その [=Originator=] の [=Core Profile=] がどちらの経路からも来ず、 [=Verifier=] が同梱する文書の中にも無いなら、その [=Content Attestation=] の検証は失敗する。これは Core Specification [[OPF-CORE]] の手順から導かれる。その手順では、成功しない検査は失敗 である。[=Page Origin=] が与えられる場合、[=Website Profile=] は well-known リソースか [=Verifier=] が同梱する文書からしか来ない。 したがって、そのどちらからも得られなければ の binding は失敗する。

問い合わせの前に両方の経路を。 [=Verifier=] は、DNS の問い合わせを 1 つでも出す前に、両方の経路の 文書を取らなければならない (MUST)。[=Verifier=] は問い合わせの前に [=Originator Profile Bundle=] と [=Content Attestation=] を揃えることを 求められているからである [[OPF-CORE]]。 [=Verifier=] が打ち切った経路からは何も得られず、問い合わせを始めた 後に届いた文書はその検証に加えない。いつ経路を打ち切るかは [=Verifier=] が決める。 [=Page Origin=] を与えない状況（） と、origin が opaque なページでは、well-known リソースは存在せず、 文書はページが運ぶものと、[=Verifier=] が手元に持つものである。

Verifier が同梱する文書。[=Verifier=] は、これに 加えて自分が同梱する文書を用いてもよい (MAY)。それらの各文書も同じ ようにそれぞれ単独で検証され、検証に通った場合にだけ用いられる。 それらは、 の順序で、2 つの経路の 文書の後に取り扱われる。

文書を取り扱う順序

[=Verifier=] は、これらの出どころの 文書を、 の文書も含めて、次の順序で 取り扱わなければならない (MUST)。この順序は、Core Specification [[OPF-CORE]] が [=Verifier=] に [=Originator Profile Bundle=] の 文書を取り扱わせ、その上限を当てさせる順序である。[=Originator=] が 公開する文書が先に来て、[=Verifier=] が同梱する文書はそれらすべての 後に来る。

  1. [=Page Origin=] の well-known リソースにある文書。
  2. ページの中に運ばれる文書。ページ内の要素の順に取る。
  3. [=Verifier=] が同梱する文書。

1 つの経路または 1 つの要素の中では、文書はそれが与える順に取り扱われる。

処理の順序は Core Specification [[OPF-CORE]] の上限の内での優先の 順序であり、その優先は [=Originator=] が与えるものである。したがって、 [=Verifier=] が同梱する文書が、[=Originator=] の提示した文書を 押しのけることはない。[=Page Origin=] を制御する Originator 以外の [=Originator=]、たとえば配信された記事の [=Originator=] にとっては、 well-known リソースでの順序はその制御する者の順序であり、その者が その順序によってできることは が述べる否認以上のものではない。

重複と、順序が律するもの。既に取り扱った文書は、 同じ出どころからであれ別の出どころからであれ、2 度目に現れたときには 再び取り扱わない。したがって、その文書は上限に対して 1 つとして 数えられる。文書は、その署名済みの形が既に取り扱った文書のそれと 1 文字ずつ同一であるとき、その文書と同じである。この順序が律するのは、 [=Verifier=] が上限の内で何を処理するかだけである。[=Verifier=] が 検証したものをどの順序で提示するかは、これによって律されない （）。

1 つの文書の発行の中から選ぶ

検証に通った文書の中に 1 つの文書の発行が複数含まれる場合、 [=Verifier=] はそのうちの 1 つを用い、その他は手続きが用いない文書 として扱う。どの発行が 1 つの文書の発行であり、そのどれを用いるかは 次のとおりである。

Profile Annotation の発行。 2 つの [=Profile Annotation=] は、同じ種類で、同じ [=Profile Annotation Issuer=] が同じ [=Originator=] について発行した ものであれば、1 つの文書の発行である。検証に通った文書の中にそのような 発行が複数含まれる場合、[=Verifier=] は、判定時刻 （）を署名の有効期間が含むものの中で、 署名の有効期間の始まりが最も遅いものを用いなければならない (MUST)。 [=Verifier=] は、その他を手続きが用いない文書として扱う。始まりが同時の 2 つがあれば、 の順序で先に取り扱った方を 用いる。

1 つのサイトの Website Profile。同じ [=Originator=] がサイトの同じ代表 URL について発行した [=Website Profile=] が複数 ある場合も同じである。それらは 1 つの文書の発行である。同じ [=Originator=] が異なるサイトについて発行した [=Website Profile=] は それぞれ別の文書であり、そのいずれも用いられる。

1 つの Originator の Web Media Profile。同じ [=Core Profile Issuer=] が同じ [=Originator=] について発行した [=Web Media Profile=] が複数ある場合も同じである。それらは 1 つの 文書の発行であり、用いるものは の 確認に通ったものの中から選ぶ。

選択が決めるもの。この選択は、検証に通り、かつ判定時刻において有効である 文書の中で行う。したがって、検証に通らない文書や、その時点で有効で ない文書が、そうである文書を押しのけることはない。その中で、 署名の有効期間の始まりは発行の間で選ぶためだけに、代表 URL はどの発行が 1 つの 文書に属するかを見分けるためだけに用いられる（）。

現在の Originator Profile Blueprints [[?Originator Profile Blueprints]] は、複数の言語の [=Profile Annotation=] や [=Website Profile=] を、別々の文書として 並べて配布する。本小節のもとでは、そうした文書は、種類、発行者、 対象が同じであるか、発行者と代表 URL が同じであるので、1 つの文書の 発行であり、[=Verifier=] はそのうちの 1 つを用いる。文書の言語を 文書どうしを見分けるものとするかどうかは決まっていない。

1 つのページの複数の Originator

1 つのページが、 複数の [=Originator=] の文書を運ぶことがある。他の [=Originator=] から配信された記事を運ぶページや、アグリゲータのページである。各 [=Content Attestation=] は自分の [=Originator=] を名指し、自分が 対象とする [=Content=] と共に運ばれるので、どの [=Originator Profile=] に対して検証するかに疑いはない。 の手続きは [=Content Attestation=] ごとに、その attestation が名指す発行者を [=Identity=] とする [=Core Profile=] を用いて行われ、Core Specification [[OPF-CORE]] の上限は各 [=Originator Profile=] に別々に当てはまる。

1 つの attestation の手続きが数えるもの。1 つの [=Content Attestation=] について行う手続きでは、その手続きの [=Originator Profile Bundle=] は、その attestation に紐付く文書である。 それは、その attestation が名指す [=Originator=] の文書と、その [=Core Profile=] と [=Profile Annotations=] の発行者たちの [=Accreditation Chains=] とであり、それらがページの どの経路、どの要素から来たかを問わない。ページの文書のうち他の attestation にだけ紐付くものは、その手続きの上限には数えない。この attestation の連鎖に用いられる文書は、それがページの他の [=Originator=] の文書でもある場合にも、この attestation について 数える。

1 つのページの Originator は互いに独立である。 [=Verifier=] は、1 つのページの [=Originator=] どうしが互いに独立で あるので、それらについての手続きを並列に行ってもよい (MAY)。1 つの [=Originator=] の手続きの中では の順序がそのまま保たれる。1 つの Document の複数の [=Content Attestation=] の手続きが同じ [=Originator Profile=] を 用いる場合、[=Verifier=] はそれを 1 度だけ検証し、その結果が 無効にされていない間、それぞれの手続きでその結果を用いてもよい (MAY)（）。結果は、Core Specification が定めるとおり、[=Content Attestation=] ごとに得られる。

well-known リソースと参照された文書への要求

どの Verifier も well-known リソースを要求する。 [=Verifier=] は、ページが本節の文書のどれかを運んでいるかどうかに かかわらず、そのページの [=Page Origin=] の well-known リソースを 要求しなければならない (MUST)。そうしなければ、 [=Content Attestation=] を運ぶが [=Originator Profile Bundle=] を 運ばないページが失敗するからである。 [=Verifier=] は HTTP キャッシュ [[RFC9111]] に保持された応答を用いて もよい (MAY)。得たものは の 上限の範囲で保持する。

ブラウジングソフトウェアの中の Verifier が要求してよい時。 ブラウジングソフトウェアの中の [=Verifier=] は、ブラウジング ソフトウェアがそのページへのナビゲーションを始める前にその要求をしては ならない (MUST NOT)。[=Recipient=] が訪れると決めていない origin に 要求が届かないようにするためである。とくに、アドレスを入力している 途中では要求せず、[=Recipient=] がまだ行っていないナビゲーションに 備えてブラウジングソフトウェアが前もって用意したページについても 要求しない。要求をいつするかについて、本仕様はこれ以上定めない。

要求に credential を付けない。[=Verifier=] は、 参照された文書や well-known リソースへの要求に credential を付けては ならない (MUST NOT)。要求は credentials mode を "omit" [[FETCH]] として行い、したがって cookie も authorization ヘッダフィールドも 運ばない。要求が通常運ぶヘッダフィールドは credential ではなく、 通常どおり送られる（）。参照された文書に ついては、その URL をページが選ぶので、credential を付けて行う要求は [=Recipient=] の credential をページの選んだ host に届けることになる。

ページを取得するサービス。要求に応じてページを取得 するサービスは、ホストが非公開アドレス、たとえばループバック、 リンクローカル、プライベート用途のアドレスやサービス自身の基盤の アドレスであるか、またはそこに解決される URL から参照された文書を 取得することを拒むべきである (SHOULD)。ページ自体と、どちらかの要求の リダイレクトを追って至るすべての URL にも同じ規則を当てるべきである (SHOULD)。

[=Verifier=] は well-known リソースを [=Page Origin=] に要求する。 その要求に対して返されたリダイレクト、とくに別の origin へのリダイレクト を追うべきかどうかは、この版では決まっていない。[=Verifier=] が別の origin へのリダイレクトを追う場合、その origin を配信する者が、 [=Verifier=] がこの経路から何を受け取るかを選び （）、検証が行われていることを知る （）。

フレームの中で提示されるコンテンツ

トップレベルの document [[HTML]] の [=Page Origin=] の well-known リソースから得た文書は、フレームの中、すなわちそのトップレベルの document の中に入れ子になった document の中で提示される [=Content=] の検証に用いてはならない (MUST NOT)。

Presented Identity と Originator のレコード

本仕様は、framework の DNS 設計にリソースレコードも名前も追加しない。 名前、レコード型、形式は Core Specification [[OPF-CORE]] と [[?OPF-DNS]] が定めている。本仕様が定めるのは、このユースケースに おいて [=Verifier=] がそれらのレコードのうちどれを引くか、 [=Originator=] が公開することを求められるのはどれか、そしてそれらが 存在しないことが何を意味するか、である。

Presented Identity

Presented Identity とは何か。ページの [=Content=] が 提示される際の identity は [=Page Origin=] である。すなわち、その [=Content=] が提示されるページの origin [[RFC6454]]、つまりその scheme、host、および scheme の既定でない場合のポートである。これは、 このユースケースにおける [=Presented Identity=] である。

Page Origin を与えない状況。本仕様の下で公開 されたコンテンツは、ブラウジングソフトウェアのナビゲーションの外で 読まれることもありうる。アーカイブビューア、オフラインリーダ、 メールの添付のビューアで読む、といった場合である。それらが [=Page Origin=] を与えない状況であり、配送が [=Presented Identity=] を与えない状況にあたる（[[OPF-CORE]], Procedure の手順 3）。 本仕様はそれらも対象とする。ブラウジングソフトウェアが提示する ページは、opaque な origin の下であってもそれに含まれない。その ようなページは、本節の塊「正規形に直せない host」で扱う。

突き合わせる名前は host である。 [=Presented Identity=] は、その host を通して突き合わされる。 [=Verifier=] は突き合わせの前に [=Page Origin=] の host を取り出し、 その host が、本仕様が [=Core Profile=] の運ぶ [=Identity=] と突き合わせる 名前である。 [=Verifier=] はその host を、Core Specification [[OPF-CORE]] がドメイン名を比較する際の正規形に直さ なければならない (MUST)。ページの URL を parse するとその形になる。 parse 済みの URL におけるドメインの host は小文字の ASCII 名だから である。ただし、parse 済みの URL は末尾ドットを残していることが ある。正規形には末尾ドットが無いので、[=Verifier=] は比較の前に そのドットを取り除く。

比較そのものは Core Specification のものである。 origin 全体は が述べるとおりに比較される。 それを除けば、本仕様は独自の変換を定めない。比較そのものは、ある 名前が別の名前の下にあるとはどういうことかを含めて、 Core Specification [[OPF-CORE]] の規則による。

正規形に直せない host。IP アドレスリテラルなど、 ドメイン名でない host はその形に直せない。Core Specification [[OPF-CORE]] は、正規形に直せない値を、それを必要とした検査の失敗と しているので、そのような host を origin に持つページについては の binding が失敗する。ローカルファイルから、 data: URL から、または sandbox 化されたフレームの中で 読まれたページの origin のような opaque な origin には、正規形に 直せる host が無い。したがって、そのような origin の下で提示された ページについても binding は失敗し、その host について問い合わせは 行わない。

opaque な origin の下にあるページを [=Page Origin=] を与えない設定の 1 つに数えれば、ページを組み立てる者が、binding を検査していないものと して報告される経路を選べてしまう。sandbox 化されたフレームや data: URL はページの側が作るものであり、アーカイブ ビューアやオフラインリーダはそうではない。

Page Origin を Originator に結びつける

Verifier が成り立たせるもの。[=Verifier=] は、 ページの [=Content=] を、[=Core Profile=] が運ぶ [=Identity=] を持つ [=Originator=] のものとして扱う前に、次のすべてを成り立たせなければ ならない (MUST)。

  • [=Website Profile=] が、その [=Core Profile=] の [=Originator Verification Key=] の下で検証でき、判定時刻 （）において自身の署名の有効期間の内に あること。かつ、[=Website Profile=] の発行者がその [=Originator=] の [=Identity=] であること。
  • [=Page Origin=] が、[=Website Profile=] の挙げる origin のいずれか であること。
  • [=Page Origin=] の host が、[=Originator=] の [=Identity=] であるか その下にあること。あるいは、その [=Identity=] のゾーンがその host に ついての [=Permitted Host Record=] を、認証されたデータとして公開 していること。

Page Origin が挙げられた origin の 1 つであるとき。 [=Page Origin=] が [=Website Profile=] の挙げる origin のいずれかで あるのは、その origin としての serialization（[[HTML]]）が、 [=Website Profile=] の運ぶ値を URL として [[URL]] parse して得た URL の origin のそれと等しい場合であり、かつその場合に限る。 の比較の前に [=Verifier=] が host から取り除く末尾のドットは、この比較では取り除かない。parse できない 値、または origin が opaque である値は、どの origin も挙げていない。

ゾーンが許していない、Identity の外の host。 [=Page Origin=] の host が [=Originator=] の [=Identity=] でもなく、 その下にもない場合、[=Permitted Host Record=] の認証された不在、 および Insecure な応答は、いずれも 検証を失敗させる。それは Core Specification が求めるとおりであり（[[OPF-CORE]], Records Published by the Originator）、名前解決のあらゆる失敗と同じである。Insecure な応答とは、署名 されていないゾーンからの応答である。そのような host を、pinning されていない [=Originator Profile=]（）を 提示しているものとして扱ってはならない (MUST NOT)。 [=Website Profile=] がその host を自分のものであると主張しており、 失敗の中身は、[=Originator=] の [=Identity=] のゾーンがその主張を 裏づけていない、ということだからである。

Permitted Host Record をどの名前について引くか。 [=Permitted Host Record=] を引く場合、[=Verifier=] は [=Page Origin=] の host について、 の正規形でそれを引く。レコードが どの名前を覆うか、そしてその存在と不在をどう読むかは Core Specification のものであり（[[OPF-CORE]], Records Published by the Originator）、[=Verifier=] はここでもそれを 変えずに適用する。

[=Originator=] の [=Identity=] に対して誤って発行された [=Core Profile=] を入手した攻撃者は、自分のサイトを名指しする [=Website Profile=] に 署名できる。[=Website Profile=] は [=Originator=] 自身が発行するもの だからである。挙げられた origin との突き合わせが binding のすべてで あったなら、この 1 つの失敗だけで なりすましが成立してしまう。host が [=Originator=] の [=Identity=] に対して一定の関係に立つことを、名前自身に よってか [=Originator=] 自身のゾーンのレコードによって示させる要件が、 2 つめの失敗を必要にしている。

代表 URL は関与しない。[=Website Profile=] は、 サイトの代表 URL も運ぶ。その URL は、binding にも、検証のいかなる 判断にも関与しない。それは提示のための情報であり、ほかには、 [=Website Profile=] のどの発行が 1 つの文書の版であるかを見分ける ためだけに用いられる（）。

Originator のレコードとそのゾーン

レコードが公開される場所。[=Originator=] が公開 できる 2 つのレコードは、いずれも [=Originator=] 自身の [=Identity=] のゾーンの、Core Specification [[OPF-CORE]] が定める名前において公開される。[=Page Origin=] の host が [=Originator=] の [=Identity=] でもその下でもない場合、その host のゾーンはこの framework のレコードを何も持たず、DNSSEC で署名されて いることを要求されない。

Issuer Pinning Record は任意であり、引くかどうかは状況に よる。[=Originator=] は、自身の [=Issuer Pinning Record=]、 すなわち自分に対して発行することを許された [=Core Profile Issuers=] を挙げるレコードを公開することを要求されない。したがって、自身の [=Identity=] のゾーンに署名することも一切要求されない。[=Verifier=] がそのレコードを引くかどうかは状況によって決まる。状況が [=Page Origin=] を与えない場合、[=Verifier=] はそれを引かなければ ならず (MUST)、[=Page Origin=] が与えられる場合、[=Verifier=] はそれを 引いてもよい (MAY)。そのレコードを引く [=Verifier=] は、その結果を Core Specification が求めるとおりに扱う（[[OPF-CORE]], Records Published by the Originator）。

結果の読み方は Core Specification のものである。認証された不在と Insecure な応答、そして別名を経て到達した応答は、 [=Originator=] を pinning されていない状態のままとし、検証は続く。それ以外の 結果は、Core Specification が述べるとおり、[=Originator=] を pinning するか、 検証を失敗させるかのどちらかである（[[OPF-CORE]], Records Published by the Originator。[[OPF-CORE]], DNSSEC Requirements and Resolution Outcomes）。本仕様はそれに何も付け加えない。 検証状態を resolver から得る [=Verifier=] に Indeterminate な結果がどう見えるか、そして の保証のもとではその状態がなぜ生じないかも、 そこに注記されている。

レコードの公開の推奨。自身の [=Identity=] のゾーンが DNSSEC で署名されている [=Originator=] は、自身の [=Issuer Pinning Record=] を公開するのがよい (SHOULD)。レコードは、 応答が認証されている場合にのみ効力を持つ。したがって、署名されていない ゾーンにあるレコードや、_op.<originator> に委任された ゾーンであって [=Originator=] の [=Identity=] のゾーンに DS レコードが 無いものにあるレコードは効力を持たない。本仕様はいかなる [=Originator=] に 対してもそのゾーンに署名することを要求しない。署名できない組織も 参加できるようにするためである（）。

ゾーンの残り。[=Originator=] の [=Identity=] のゾーンの別の所にある wildcard や DNAME と、レコードの公開が それらに及ぼすことは、Core Specification が述べるとおりである。その名前を [=Originator=] がどう確かめるかは [[?OPF-OPS]] にある。

Originator のゾーンに署名しなければならないとき。 [=Permitted Host Record=] が必要となるのは が挙げる場合、すなわち [=Website Profile=] が名前を挙げている host であって、[=Originator=] の [=Identity=] でもなくその下にも無いものに ついてだけである。 から、そのような host を 挙げる [=Originator=] は自身の [=Identity=] のゾーンに署名しなければ ならないことが導かれる。[=Verifier=] は応答が認証されている場合に のみそのレコードに基づいて動作するからである。自身の [=Identity=] で あるかその下にある host しか挙げない [=Originator=] にはその必要が 無い。

発行者のレコードは Core Specification のものである。 発行者たちが公開するレコード、すなわち各発行者の [=Issuer Key Record=]、[=Core Profile Issuer=] の [=Originator Key Records=]、 [=Profile Annotation Issuer=] の [=Revocation Records=] は、 すべてのユースケースに共通であり、Core Specification が定めている（[[OPF-CORE]], Issuer Key Record。[[OPF-CORE]], Originator Key Records。[[OPF-CORE]], Revocation Records）。本仕様はそれらに対して、それ以上の要件を 何も課さない。

検証

本節は、このユースケースについて、Core Specification [[OPF-CORE]] の 検証手続きをどの当事者が実行するか、その当事者が自らの動作する場所で DNSSEC の validation state を確立するために何を備えている必要がある か、その当事者が [=Web Media Profile=] をどう確かめ、ページの URL を allowedUrl とどう照合するか、そして結果がどう扱われるかを 定める。validity をどの時点を基準として判断するかは にある。

検証を行う当事者

Verifier の 2 つの配置。検証を行う当事者は、[=Recipient=] にページを提示する当事者か、 ページを取得して検証するサービスである。本仕様はその当事者に独自の 名前を与えない。この役割を指す用語は [[OPF-CORE]] から import した [=Verifier=] であり（）、2 つの 配置の違いは、何を検査しな ければならないかにではなく、何を入手できるかにある。サービスが到達 した結果を、その後ページを提示する別の当事者に伝えるかどうか、また その当事者がその結果の何に依拠してよいかは未決である （）。

validation state を確立する 2 つの手段。[=Verifier=] は、自らが依拠するすべての応答について、Core Specification が求めるとおり（[[OPF-CORE]], DNSSEC Requirements and Resolution Outcomes）、自前の trust anchor で validate するか、validating resolver を認証しその応答を保護する チャネルを通すかによって、DNSSEC の validation state を確立する。 resolver に依拠する場合、[=Verifier=] は、設定または試験によって、その resolver が validate することの保証を持つ。そのどちらもできない [=Verifier=] は、Core Specification が 述べるとおり、そもそもこの手続きを実行できない。

validate しない resolver からの応答は Insecure ではない。そのような resolver からの応答は validation state を持たず、 [=Verifier=] はそれを Insecure と読まない。 [[OPF-CORE]] が求めるとおりである。このユースケースでこの読み方が意味を持つのは、 [=Originator=] の [=Issuer Pinning Record=] については、Insecure な 応答が [=Originator=] を pinning されていない状態のままとするから である（。[[OPF-CORE]], DNSSEC Requirements and Resolution Outcomes）。

ブラウジングソフトウェアの中の Verifier は自前の手段を備える。拡張のように、ブラウジングソフトウェアの中で動作する [=Verifier=] は、 ブラウジングソフトウェアが自身の目的のために行う名前解決を通じて 得た応答を、それだけを理由に認証されたデータとして扱ってはならない (MUST NOT)。ブラウジングソフトウェアは一般に DNSSEC を validate しない。また、応答が validate されたという表示は、その表示自体が 認証されないまま届くなら、ネットワーク経路上の誰でも書き込める。したがって、そのような [=Verifier=] は 2 つの手段のいずれかを自ら備える。自前の validator か、 validating resolver への認証されたチャネルである。

Document の中での URL の変化。新しい Document に ならずに Document の URL が変わる場合、たとえば fragment への ナビゲーションでは、[=Verifier=] は allowedUrl の確認を 新しい URL に対してやり直さなければならない (MUST)。前の一致に依拠 していた結果は終わる（）。

結果がどう扱われるか

結果を記録しておく場所は無い。配送チャネルは結果を記録しておける場所を提供せず、本仕様は記録された 結果の形式も、それを封印する手段も定めない。ページは [=Verifier=] が読む文書であって、それを扱う 当事者が自前のフィールドを付け加えるメッセージではない。[=Verifier=] が 書いたものは、次にそれを読む当事者にページとともに運ばれることが無い。 したがって [=Verifier=] は提示のたびに改めて判断する （）。

結果が当事者の間を渡るかどうか。検証する当事者と提示する当事者が同一である場合、すなわちブラウジング ソフトウェアの中の [=Verifier=] の場合、当事者間を結果が渡ることはそもそも 無い。結果は導かれ、提示され（）、提示の 後には何も残らない。サービスが検証し、ページを提示する当事者が別である場合、結果は両者の 間に成り立つ取り決めによってその当事者に届く。本仕様はその取り決めを 定めない。

Core Specification [[OPF-CORE]] は、ある当事者が別の当事者から結果を 受け取ったときに何に依拠してよいかを、[=Use Case Specification=] が述べることを 求めている。これに関わる次の 3 つが、この版では決まっていない。

  • ページを取得するサービスが、その結果を、ページを提示する別の当事者に 伝えるかどうか。 は [=Verifier=] の 2 つの配置のうちの一つとしてサービスを認める。本節は、結果が両者の間に 成り立つ取り決めによって提示を行う当事者に届くとだけ述べており、この 2 つが同一の当事者であるかどうかを述べていない。
  • 同一でない場合に、結果がどのような形式で伝えられるか、そして 受け取った当事者が何に依拠してよいか。
  • ある当事者から別の当事者へ渡った結果に依拠してよい信頼の境界が 必要かどうか。このユースケースはそれを定めていない。

このユースケースは結果を記録しないので、結果を記録するための値を 定めず、結果を保持する手段も持たない（）。

提示

提示されるものについて Core Specification が既に求めていること。検証の結果は、それが対象とする [=Content=] とともに [=Recipient=] に 提示される。 Core Specification [[OPF-CORE]] は、[=Profile Annotation=] が効力を 持っているかのように [=Verifier=] が提示すべきでないものを述べ、 結果が pinning について何を区別するか、すなわち pinning されている [=Originator=]、されていないもの、その [=Issuer Pinning Record=] が 引かれなかったものを述べている。そのどちらもここでは繰り返さない。 このユースケースで [=Issuer Pinning Record=] が引かれないのは、[=Page Origin=] が与えられ、 [=Verifier=] がそのレコードを引くことを選ばなかった場合だけである （）。

検査されなかった binding。Core Specification は、検査 されなかった binding を結果がその旨報告することも求めている。このユースケースでは、それは [=Page Origin=] を与えない状況について当てはまる。ブラウジング ソフトウェアの中で提示されるページはこれを持ち、その binding は検査される。これに対し、[=Page Origin=] を与えない状況 （）のいずれかで読まれる コンテンツはこれを持たず、その場合の結果は binding が検査されな かったことを運ぶ。

判断はそれを下した時点のもの。[=Verifier=] が提示するものは、検証した時点で下した判断であり、他の いかなる時点についての言明でもない （）。[=Verifier=] がある検証から次の 検証へ持ち越してよいものは、Core Specification [[OPF-CORE]] と に列挙してある。結果はその中に 含まれない。

現在の実装。現在の実装では、[=Verifier=] はブラウザ拡張であり、結果を [=Recipient=] に提示する役も担う。これがデモンストレーションの ユーザーインタフェースである。[=Recipient=] に要となる視覚的な情報を 与えるために、ブラウジングソフトウェアそのものに手を入れることも 検討されている。

本仕様は、[=Content Attestation=] を運ばないページを評価しない（）。現在の Originator Profile Blueprints [[?Originator Profile Blueprints]] は、そのようなページが 自身の well-known リソースから得る [=Website Profile=] を検証し、 そのサイトを運営する [=Originator=] を提示する。そのようなページに ついて [=Verifier=] が何かを提示してよいか、どのような条件でよいかは 決まっていない。

Validity、revocation、時刻

本節は、一般モデルの validity の層がこのユースケースでどう現れるか、 そして発行がどのような不変条件に服するかを記す。また、ここでは置き換えられた鍵を retired な鍵として残すか withdraw するか、validity をどの時点を基準として判断するか、そして [=Verifier=] が ページのある提示から次の提示へ何を持ち越してよいかも記す。

Validity の層

4 つの層は Core Specification のものである。このユースケースでは、validity の層は Core Specification の 4 つ（[[OPF-CORE]], Revocation Model and Time Constraints）の外側に無い。ページとともに運ばれる 文書の外側にあるものが、ページに署名することが無いからである。このユースケースに 固有のことが 2 つある。鍵の層が覆うのは、[=Content Attestation=] と [=Website Profile=] に署名する鍵である。[=Originator=] が登録を終わらせる宣言は、 [=Verifier=] がその [=Issuer Pinning Record=] を引く所でのみ効力を持つ （）。

プロファイルの外側の文書は層を成さない。[=Content Attestation=] と [=Website Profile=] は、DNS における名前も revocation 機構も持たない （）。それらは次の 3 つの道のいずれかに よって効力を失う。

  • それらに署名した鍵が [=current=] でなくなること（鍵の層）。
  • その鍵を運ぶ [=Core Profile=] が valid でなくなること（Core Profile の層、 または当該 [=Originator=] のすべての [=Core Profile=] を終わらせる登録の層）。
  • それら自身の署名の有効期間が終わること。

Web Media Profile と Originator Profile はともに終わる。 [=Web Media Profile=] は、 [=Originator=] の [=Core Profile=] が valid でなくなると valid で なくなり、[=Originator Profile=] は、その [=Web Media Profile=] の 署名の有効期間が終わると valid でなくなる。[=Verifier=] はその 終わりを確かめる（）。これは層を 加えない。 [=Web Media Profile=] は DNS における名前も自前の revocation 機構も 持たないからである。それは、それに署名した鍵を [=Core Profile Issuer=] がもう公開しなくなったときにも終わる（）。

Website Profile は Web Media Profile に従属しない。2 つの文書は 並べてともに運ぶことができるが、[=Website Profile=] の validity は [=Web Media Profile=] の validity に依らず、上に挙げた 3 つが、 [=Website Profile=] が効力を失う道のすべてである。 [=Web Media Profile=] が終わっているとき、その [=Originator=] の各 [=Content Attestation=] の検証は、その [=Website Profile=] が何であれ の手順 5 で失敗する。 [=Website Profile=] そのものは影響を受けず、 [=Originator Profile=] が valid な [=Web Media Profile=] を運ぶように なれば再び用いられる。

1 つのサイトについての主張だけを撤回することはできない。効力を失う道がその 3 つしか無いので、このユースケースでは、あるサイトについての主張 の撤回が、鍵または [=Core Profile=] の revocation に畳み込まれる。 撤回するべき第 3 のものが存在しない。これは簡潔さであると同時に粗さ でもある。[=Website Profile=] が挙げる origin のうちの 1 つで自らの [=Originator Profile=] を提示するのをやめたい [=Originator=] には、その 1 つの 主張だけを撤回する手段が無いからである。そこから何が導かれるかは にある。

置き換えられた鍵で署名されたコンテンツがどれだけの間検証できるか。[=retired=] な鍵は [=withdrawn=] ではない。そのレコードは残っているので、 それで署名された文書は の 手順 7 を引き続き通る。 したがって、置き換えられた鍵で署名され既に公開されたコンテンツがどれ だけの間検証可能であり続けるかは、その鍵を運ぶ [=Core Profile=] の 署名の有効期間で上限が決まり、鍵が [=withdrawn=] になれば、 すなわち [=Originator=] が鍵を retire せずに withdraw することを 選べば（）、そこで短く切り上げられる。

Website Profile の署名の有効期間が、Originator がやめた主張の上限になる。本仕様が発行に課す要件の 1 つ目は、[=Website Profile=] の 署名の有効期間についてのものである。[=Originator=] は、ある origin を挙げるのをやめてからその主張が 提示されなくなるまでの間に許容できる遅れを超えない長さに、その期間を 設定するのがよい (SHOULD)。[=Website Profile=] は自前の revocation 機構を持たないので、[=Originator=] がもはや挙げていない origin がなお 提示されうる長さは、その期間で上限が決まる。

それ以上の不変条件は無い。[=Website Profile=] についての 2 つの要件以上に、本仕様は不変条件を加えない。とくに、framework は [=Originator Profile=] の外側にある文書の署名の有効期間と [=Core Profile=] の署名の有効期間との間に不変条件を置いておらず、 その必要も無い。そのような文書は、それ自身の署名の有効期間が何を 述べていようと、鍵と [=Core Profile=] が現行である間しか用をなさないから である（）。

置き換えられた鍵を retired として残すか withdraw するか

Core Specification が use case に委ねる選択。署名鍵を差し替える [=Originator=] は、2 つの道のどちらかを選ぶ。置き換えられた鍵を [=retired=] な 鍵として残すことができる。その場合、その鍵のレコードは、 その鍵を運ぶ各 [=Core Profile=] の [=Originator Key Record=] に、その [=Core Profile=] が期限切れになるまで残る （）。あるいは自身の [=Core Profile Issuer=] に withdraw させることができる。その場合、その鍵のレコードを、 それを載せているすべての [=Originator Key Record=] から消す。Core Specification は、その 選択が何と何を引き換えにするものかを述べ、どちらが適するかを述べる ことを各 [=Use Case Specification=] に委ねている。

Core Profile は署名された後に変えられない。したがって、置き換えられた鍵を 運ぶ [=Core Profile=] は期限が来るまで効力を保つ。新しい鍵の ために発行される [=Core Profile=] は置き換えられた鍵を運ばないものと される。これは Core Specification [[OPF-CORE]] が [=Core Profile Issuer=] に推奨していることである。

鍵を retired として残すと、狭まらない窓が残る。置き換えられた鍵を [=retired=] な鍵として残した場合に何を支払うことになるかは、 Core Specification [[OPF-CORE]] が述べている。その鍵を運ぶ [=Core Profile=] が効力を持つ間、その秘密鍵を持つ者は、[=Verifier=] が本物の古い [=Content Attestation=] と区別できないものに署名できる。その attestation がいつ署名されたかについての信頼できる説明を [=Verifier=] が持たないからである （）。この窓は時間が経っても狭まら ない。したがって、Core Specification [[OPF-CORE]] が述べるとおり、 compromise されたと考えられる鍵は、その結果どのコンテンツが検証 できなくなろうと、直ちに [=withdrawn=] とされる。

判断の基準時点

validity は検証の時点を基準として判断する。Core Specification [[OPF-CORE]] は、[=Use Case Specification=] が別段の定めを しない限り、validity を検証の時点を基準として判断するものとし、それ 以外の時点は、配送チャネルが [=Verifier=] に与えるものに限っている。本 仕様は別段の定めをしない。validity は検証が実行される時点を基準として 判断され、 における 署名の有効期間の検査はすべてその時点に対して行われる。 このチャネルは、名指しできるような他の時点を与えない。 [=Verifier=] が時計のずれに対して認める許容は、その期間のどちらの 端についても、Core Specification [[OPF-CORE]] の一般手続きのものである。

ページが運ぶ ものはそれを公開する当事者が書いたものであり、その当事者が書いた時刻 は一般規則が除外するものである。文書を判断される当事者自身がその値を 選ぶことになるからである。また、そのような時刻を保存しておけるものも 無い（）。

サービスが下した判断。サービスが検証し、ページを提示する 当事者が別である場合、判断はそのサービスが検証した時点で下したもので ある。それが提示される時点でどれだけ古くてよいかは、 が未決のまま残している取り決めに属する。

結果は保持されないので、公開時の validity を示すものも無い。このユースケースは検証の結果を保持する手段を持たず、そのための手段も 定めない。したがって、アーカイブされたページの複製も、後日のその 検証も、そのページが公開された時点でプロファイルが valid であった ことを、この framework の中で示すことはできない。そのような証明が 求められる場合、それは framework の外から得るべきものである。 アーカイブされたページの複製をどう扱うかは別の問いであり、本仕様は それを決めない。

キャッシュとページの再訪

保持してよい範囲は Core Specification のものであり、検証済みの chain のキャッシュは実行コンテキストより長く残す。[=Verifier=] が入手したものを保持してよい範囲は Core Specification のもの であり（[[OPF-CORE]], Caching。[[OPF-CORE]], Accreditation Chain Verification and Caching）、本仕様はこれを広げない。ブラウジングソフトウェアの中で動作する [=Verifier=] は、検証済みの [=Accreditation Chains=] の自身のキャッシュを、検証が走った実行 コンテキストよりも長く生き残る記憶域に保持するのがよい (SHOULD)。

検証が走った実行コンテキストは、アイドルになると停止されるのが 普通であり、そのメモリの中にしか無いキャッシュは次の提示の時点で 再び空になっている。 キャッシュの価値は、後の検証が前の検証の問い合わせを繰り返さずに済む ことにあり、その価値はキャッシュが生き残ってはじめて実現する。

再訪では問い合わせが減る。発行者の chain を既に検証して保持しているサイトを再訪する場合、それら の chain に関わる問い合わせは繰り返されない。残るのは [=Originator=] とその [=Core Profile=] についての問い合わせ、および各 [=Profile Annotation=] についての問い合わせであり、これらもまた、 time to live の内にある DNS 応答のキャッシュから答えられうる。

ブラウジングソフトウェアのキャッシュにあるページは判断を伴わない。ブラウジングソフトウェアのキャッシュに保持されたページの検証は、 結果が保持されないので（）、提示の たびに改めて行われる。したがって revocation は、time to live の内にあるキャッシュから応答が読まれることのなくなった最初の提示 において効力を生じる。revocation が検知されるまでの遅れは、一般モデル と同じく、それらの time to live によって上から抑えられており、ページを 長期にキャッシュしてもその遅れは延びない。

この版では、[=Verifier=] がある検証の結果を後の提示に、たとえば リロードのときや同じ origin の別のページで再利用してよいかは決まって いない。そのような再利用は、その結果が依拠する各文書の署名の有効期間の 終わりと、各 DNS 回答の TTL の満了とのいずれよりも遅くまでは続かない （）。現在の Originator Profile Blueprints [[?Originator Profile Blueprints]] は、検証されるものと その入力のすべてが変わらず、かつそれらの終わりのうち最も早いものが まだ来ていない間だけ再利用を認め、well-known リソースにある文書に ついての結果を同じ origin の別のページに再利用することを認めている。

経路が成り立たせるものと、署名が成り立たせるものとは、分けて考え なければならない。どの経路も [=Originator=] について何ひとつ成り 立たせない。ページを改変できる攻撃者は、ページに埋め込まれている ものを改変できるのと同じ自由さで、ページの中の参照も改変でき、参照 されたリソースや well-known リソースを配信する者は、それが何を返すかを 選ぶからである。各文書の authenticity は、経路が何であれ、その文書が 運ぶ署名と の binding に依っている。本節の 他の事柄にとって経路に違いが無いのは、そのためである。

[=Content Attestation=] を運ぶページは、その [=Originator=] の [=Core Profile=] が得られない場合でも [=Originator Profile=] を提示 するページである。その場合には検証が失敗し （）、評価されないままにはならない。 [=Content Attestation=] を運ばないページは、その [=Page Origin=] の well-known リソースが何を運んでいようと、[=Originator Profile=] を 提示しない。結果は [=Content Attestation=] ごとに得られる （）ので、それを 1 つも運ばないページ には結果が無い。そのようなページは本仕様の下で評価されず、本仕様は それについて何も述べないので、結果が無いこと自体は結果ではない。すなわち、framework による裏書きは、[=Recipient=] に届く 途中のコンテンツから奪うことはできるが、コンテンツに対して偽造する ことはできない。

ページを改変できる者だけでなく、文書が [=Verifier=] に届くまでの間に それを運び、あるいは並べるすべての当事者にとっても、できるのは denial だけであり、誤った結果ではない。そのような当事者には、[=Page Origin=] の well-known リソース やページが名指す URL について応答する者（）、 [=Originator=] のために [=Content Attestations=] を配布する当事者、 [=Verifier=] が同梱する文書を供給する者が含まれる。いずれも、 [=Originator Profile Bundle=] の文書がどの順序で [=Verifier=] に届くか、 どれが届くかを変えることができるが、文書を改変することはできない。 各文書はそれぞれ単独で署名されているからである。

そのような当事者が得るのは denial であって、誤った結果ではない。 順序や取捨を変えることは 文書を差し控えることに等しい。これは Core Specification [[OPF-CORE]] が [=Profile Annotations=] の順序について述べるとおりである。また、 その当事者が 2 度目に加えた文書が別の文書を上限の外へ押し出すことは ない。 がそれを 1 度だけ取り扱うから である。[=Web Media Profile=] をページと well-known リソースから 取り除くことも、同じく失敗をもたらし（ の手順 5）、誤った結果は もたらさない。

文書を別のページに移すこと

文書を別のページに移し替えることもできない。[=Originator=] の本物のページから [=Originator Profile Bundle=] と [=Content Attestation=] を複製して 自分のページに載せ、[=Website Profile=] を自分の origin の well-known リソースに載せる攻撃者を止める のは、ページ全体に対する何らかの署名ではなく である。そのページの [=Page Origin=] は [=Website Profile=] が挙げる origin のいずれかでなければならず、その host は [=Originator=] の [=Identity=] であるか、その下にあるか、その [=Identity=] のゾーンのレコードによって許されていなければならない。

[=Content Attestation=] は、第 2 の確認によってもページにつなぎとめ られる。ページの URL が、その [=Content Attestation=] の運ぶ allowedUrl に一致しなければならない （）。この確認は、 正規の [=Content Attestation=] を、それが名指さない URL のページに 置いたものを止める。そのページがその attestation の対象とする [=Content=] を再現している場合、すなわち attestation 自身の内容では 止められない場合でも止め、そのページが [=Website Profile=] の挙げる origin の上にある場合でも止める。

allowedUrl の確認で得られるものは、 allowedUrl をどれだけ狭く書くかに依る。host 全体を 名指す pattern は、その host のすべてのページを認める。内容が必要と する以上に広く書かないことは、[=Originator=] と、その代わりに署名する オペレータの規律であり、Operational Governance Requirements [[?OPF-GOV]] がそれを両者に課す。必要以上に広く書かれた pattern が 悪用されたなら、それは運用の失敗であって、確認の失敗ではない。

他者の文書を寄せ集めたページに載せられた [=Content Attestation=] が、 そのページのコンテンツを対象としていないことがどこまで判明するかは、 本版では答えられない。[=Content Attestation=] が何を含むかをここでは 定めていないからである。そこから定めるべき Content Integrity Descriptor の種類は、Originator Profile Blueprints [[?Originator Profile Blueprints]] が述べるものである（）。それが 定まるまでは、他者の文書を寄せ集めたページに対して本文書が述べる ことは、binding と allowedUrl の確認がすべてである。

配送はまた、[=Verifier=] の前にページを持ち込める者は、その前に 仕事を積めるということでもある。このユースケースには、Core Specification の検査が始まる前に攻撃者を止める前提条件が無い。最初に検証 すべき、[=Originator Profile Bundle=] と [=Content Attestation=] の外側の署名が存在しないからである （ の手順 1）。[=Verifier=] は 持ち込まれたページを何であれ評価する。

[=Verifier=] にその仕事をさせられるのが誰かは、[=Verifier=] の配置に よって異なる。ブラウジングソフトウェアの中の [=Verifier=] には [=Recipient=] 自身のブラウジングによってページが持ち込まれるので、 攻撃者はまず [=Recipient=] をそのページに連れてこなければならない。 要求に応じてページを取得するサービスには、それに依頼できる者なら誰でも ページを持ち込める（）。

参照された文書はページの選んだ URL から取得され、要求に応じて取得する サービスは、ページの作者が持たないネットワーク上の位置を占めている。 ホストがサービスのネットワークの内側のアドレスであるか、またはそこに 解決される URL や、要求と共に 送られる credential は、取得を、ページに代わって [=Verifier=] の 位置から行われる要求に変えてしまいかねない。credential と非公開 アドレスについての の規則は、これを 防ぐためのものである。

ページが複数の [=Originator=] の文書を運ぶ場合 （）、検証のコストは [=Content Attestation=] ごとに生じる。他の [=Originators=] の本物の ページから複製された文書はローカルには検証に通るが、問い合わせを 要さない の比較で 失敗する。したがって、その attestation について他の手順の問い合わせを 出す前にその比較を行う [=Verifier=] は、それらに問い合わせを費やさない。

ニュースアグリゲータのトップページのように、多くの [=Originator=] から コンテンツを集めるページは、多数の [=Content Attestation=] を運びうる。 また、コンテンツを動的に取り込むように設計されたページは、取り込む コンテンツが伴ってくるだけの数を運び、その数は提示のたびに変わりうる。 attestation の 1 つ 1 つがそれ自身の検証のコストを加えるので、1 つの ページの数は、それを検証するコストに直接効く。そのようなページの 運用者は、ページがコンテンツをどう集めるかを選ぶときにこれを考慮に 入れることができる。

Presented Identity をどう取得し、どう結びつけるか

このユースケースにおいてコンテンツが提示される際の identity は [=Page Origin=] であり、[=Verifier=] はそれを、評価しようとしている ページの URL から取る（）。 コンテンツがその origin の下で届いたことを成り立たせるものは framework の中には無い。それはトランスポートの仕事であり、それが このチャネルの持つ唯一のもう一つの層である。ページが HTTPS で配信 される場合、host が名指しされたものであるという保証はトランスポートと それが依拠する認証局の保証であり、それは [=Page Origin=] を確立し、 それ以上のものは確立しない（）。

TLS 無しで配信されるページには そのような保証がそもそも無く、ネットワーク経路上の攻撃者がコンテンツ と、それとともに運ばれる文書とを等しく選ぶことになる。scheme は が突き合わせる origin の一部であるから、 [=Website Profile=] が scheme を https とする origin しか挙げていない [=Originator=] については、TLS 無しで配信される ページでは binding が失敗する。そのようなページの [=Page Origin=] は 挙げられた origin のいずれでもない。

identity を比較される形に直すことは、ここではほとんどコストを生まない。 ページの URL を parse した時点で、[=Verifier=] が取り除く末尾ドットを 除けば既に小文字の ASCII の host が得られているので、本仕様は独自の 変換を定めない （）。変換が開く種類の誤りは、 ここでは、URL のパーサが行う変換と Core Specification [[OPF-CORE]] の A-label の形とが食い違う少数の名前に 限られる。

Core Specification が比較に課すところはそのまま当てはまる（[[OPF-CORE]], Resolution Failures and the Pinning Downgrade）。比較は正規形 どうしで行われ、かつ厳密である。したがって、他の名前に似ているという理由で 登録された host は、自分自身にだけ結びつき、他の何にも結びつかない。 [=Recipient=] が、自分の知っている名前に似た名前をどう受け取るかは、 framework が答える問いではない。

Core Specification [[OPF-CORE]] は、[=Core Profile Issuer=] とは独立 に何がコンテンツをその [=Originator=] に結びつけるのかを、各 [=Use Case Specification=] が述べることを求めている。発行されるべきでなかった [=Identity=] に対して発行された [=Core Profile=] が、それだけでは足りないように するためである。このユースケースにおいて、[=Core Profile Issuer=] とは独立に コンテンツをその [=Originator=] に結びつける要素となるのは、 [=Page Origin=] の host と [=Originator=] の [=Identity=] との間に が求める関係である。

誤って発行された [=Core Profile=] を持つ者は、自らのページを、次のどちらかの下で提示しなければならない。 1 つは、その [=Identity=] であるかその下にある host であり、これには [=Originator=] 自身の名前空間にある名前と、それを配信する手段とを 支配することが要る。もう 1 つは、[=Originator=] 自身のゾーンが許す host であり、これにはそのゾーンを支配することが要る。いずれも第 2 の失敗であり、 第 1 の失敗とは別のものであって、別の当事者の手中にある。 [=Website Profile=] はその要素ではない。理由は の注記が述べるとおりで、その要素は名前で あって、文書ではない。

[=Originator=] の [=Identity=] の下にある host がページを結びつける 強さは、[=Originator=] がその [=Identity=] の下のすべての名前を 支配している程度にとどまる。その下の名前の うち、[=Originator=] が委任したもの、利用者に渡したもの、もはや 保持していないサービスを指したまま放置したものは、[=Originator=] の ゾーンを何も変えることなく別の当事者が配信できる。そのような当事者が 誤って発行された [=Core Profile=] も併せ持てば、binding を満たす。

自身の [=Identity=] に対して誤って発行された [=Core Profile=] に対して [=Originator=] 自身が持つ手段は、 binding が何を成り立たせるかとは別の問いである。Core Specification は 許された [=Core Profile Issuers=] を挙げるレコードを必須とせず、[=Use Case Specification=] がそれを要求することを許している。要求する場合には、 すべての [=Originator=] が自前の手段を手にする（[[OPF-CORE]], What Pinning Protects, and Why It Is Optional）。このユースケースはそれを要求 しない（）。また [=Page Origin=] が与えられる場合には [=Verifier=] はそれを引かなくてよい。

自身の [=Issuer Pinning Record=] を公開していない [=Originator=] は、 自分が求めていない [=Core Profile=] を revoke してもらうにあたり、 自らの [=Core Profile Issuer=] に依存することになる。ゾーンが署名 されているものには、それを公開して、そのレコードが引かれる所でその ような手段を手にすることが推奨されている （）。 の binding は、[=Originator=] が 2 つのどちらであるかに左右されない。 pinning されている [=Originators=] にも、されていないものにも等しく 当てはまる。

ある host が [=Permitted Host Record=] によって許される場合、それを 許しているのは [=Originator=] であって [=Core Profile Issuer=] ではなく、その許可の security は [=Originator=] のゾーンの security である。 [=Permitted Host Record=] の名前にあるレコード集合で、Core Specification [[OPF-CORE]] の定める形のレコードを含まないもの、 たとえばゾーンの別の所にある wildcard から合成されたものは、不在と 読まれる（）。

許された host のゾーンはこの framework のレコードを何も持たず、署名されていること を要求されない（）。したがってこの framework は、それを運用する当事者に何も求めない。その当事者にできる ことは、host を配信する者なら誰にでもできることである。 [=Originator=] がその host を許すのも、許すのをやめるのも、自身の ゾーンにおいてのみである。やめることが何に及び、何に及ばないかは にある。

Verifier がどこに置かれるか、そこで DNSSEC の validation をどう得るか

の 2 つの配置はいずれも、依拠 できる DNSSEC の validation state を、Core Specification [[OPF-CORE]] が認める 2 つの手段のいずれかによって必要とする。両者は それをどれだけ容易に手にできるかにおいて異なる。ブラウジング ソフトウェアの中の [=Verifier=] は、[=Recipient=] のいる場所で、 [=Recipient=] が支配していないネットワークの上で、その端末に与えられた resolver が何であれそれとともに動作する。ブラウジングソフトウェアは 一般に DNSSEC を validate しない。また、応答が validate されたという 表示は、その表示自体が認証されないまま届くなら、ネットワーク経路上の 誰でも書き込める。 がその要件を 明示的に述べ、その根拠を退けているのはこのためである。

ページを取得するサービスは、 自らの配備の問題としてどちらの手段でも備えることができ、この 1 点に 限れば 2 つのうち容易な方である。その代償は別の所にある。すなわち [=Recipient=] について何を知ることになるかという点 （）と、結果がページを提示する当事者に届か なければならないという点（）である。

ここで最も重要なのは、pinning されていない経路がそもそも存在するという 点である。Core Specification は、[=Use Case Specification=] が pinning されていない [=Originator=] を受け入れる場合にだけ、[=Verifier=] が pinning されていないまま先へ進むことを認める。レコードを要求する [=Use Case Specification=] ではその不在が失敗となり、pinning されて いない経路は存在しない（[[OPF-CORE]], What Pinning Protects, and Why It Is Optional）。このユースケースはそのレコードを 要求しない。認証された不在と Insecure な応答は、いずれも [=Originator=] を pinning されていない状態のままとし、検証は続く （）。別名を経て到達した応答は Insecure な応答として読まれる。 [=Page Origin=] が与えられる場合、[=Verifier=] はそもそもそのレコードを 引かなくてよく（）、 そのときはそれについて応答を読まない。

[=Originator=] の 2 つのレコードのうちもう一方である [=Permitted Host Record=] は、pinning されていない結果を認めない。 このレコードについては、認証された不在も Insecure な応答もいずれも失敗である。 そのような host は pinning されていない [=Originator Profile=] を提示しているものとして 扱われない（）。そこでは [=Website Profile=] がその host を自分のものであると主張しており、それを裏づけるものが 期待されているからである。2 つのレコードのうち一方は pinning されて いない結果を認め、他方は認めない。攻撃者が向き合うのは、この非対称性 である。

ネットワーク経路上の攻撃者が、pinning されていない結果を用いてできる ことは、Core Specification が述べるとおりである（[[OPF-CORE]], Resolution Failures and the Pinning Downgrade）。pinning されて いない経路に至る結果はどちらも偽造できず、名前解決を妨害すれば失敗で あって決して不在にはならない（）。攻撃者に 残るのは、[=Originator=] が [=Issuer Pinning Record=] またはその否定の 形を公開する前に作られた不在の証明を、その署名が切れるまで replay することである。validate しない resolver はあらゆる応答を Insecure に見せかねず、それを除くのが の求める保証である。

同じ replay は [=Permitted Host Record=] については逆向きに働く。[=Originator=] がそのレコードを削除する前に作られた、そのレコードを運ぶ認証済みの 応答は、その署名が切れるまで提示でき、その間その host がもう許されて いないことを隠す（）。

認証済みの応答の replay を除けば、 ネットワーク経路上の攻撃者は、pinning されている [=Originator=] を pinning されていないものに変えることはできない。できるのは検証を 抑え込むことだけである。失敗を示された [=Recipient=] は、そのような 攻撃者と一時的に到達できないゾーンとを区別できない。どちらの場合も 同じ結果が報告されるからである。また、問い合わせが平文で resolver に 届く場合には、名前がどの [=Originator=] を検証しているかを語るので、 この抑え込みは特定の一者を狙って行える。

ネットワーク経路上の攻撃者にできることについてのこの限界が成り立つのは、 の要件を 満たす [=Verifier=] についてだけである。応答が validate されたという 認証されていない表示を額面どおりに受け取ってしまう [=Verifier=] には、 限界がまったく無い。その場合はすべての応答が攻撃者の選ぶところと なり、不在と読まれる応答もその中に含まれる。そのような [=Verifier=] に とって、pinning されていない経路は攻撃者が好きに開けるものであり、 framework は、ページとともに運ばれた文書が既に主張していること以上の ものを何も加えない。Core Specification [[OPF-CORE]] はこれを、この 要件が存在する理由として挙げている。

この要件は、このユースケースで 最も多く見られるであろう配置に最も重くのしかかる。ブラウジング ソフトウェアの中の [=Verifier=] こそが、拠り所にできる自前の validating resolver を持たないものだからである。 2 つの手段のどちらも備えない [=Verifier=] はそもそも 検証できず、代わりに拠るべきより弱い検査も存在しない。

[=Originator=] が pinning されていたか、されていなかったか、引かれなかったかは結果に 引き継がれる（[[OPF-CORE]], Outcome and Time of Judgement）ので、 結果を受け取った当事者は、それが pinning されていなかったこと、または そのレコードが引かれなかったことを見て取れる。 見て取れないのは、認証された 2 つの結果のどちらがそれをもたらしたか である。署名されたゾーンにそのようなレコードを公開していない [=Originator=] なのか、ゾーンがそもそも署名されていないものなのか、 である。この 2 つは異なる validation state で あり、[=Verifier=] はどちらを得たかを知っている。しかし本文書はその 区別をつける機会を与えない。一般モデルがそのいずれをも結果に引き 継がないからである。

Core Profile Issuer を挙げることが、求められず推奨にとどまる理由

許された [=Core Profile Issuers=] を挙げるレコードの公開は、この ユースケースでは optional である。したがって、誤って発行された [=Core Profile=] に対する第 2 の、そして独立した要素は、ある [=Originators=] には存在し、他のものには存在しない。 レコードの公開を要件にすることはできない。このレコードは [=Originator=] 自身の [=Identity=] のゾーンにあり、[=Verifier=] は応答が認証されている場合にのみ それに基づいて動作する。したがってこれを要求することは、そのゾーンが DNSSEC で署名されていることを要求することになる。このユースケースは それを要求しない立場を採っている（）。

[=Verifier=] もまた、あらゆる状況でそのレコードを引くことを求められる わけではない。状況が [=Page Origin=] を与える場合、 の binding がそれ自体で、[=Core Profile Issuer=] から独立した 第 2 の要素となる（）。 本仕様はそこでは引くかどうかを [=Verifier=] に委ねる。状況が [=Page Origin=] を与えない場合、binding は検査されず、そのレコードが そのような要素の唯一のものとなるので、[=Verifier=] はそれを引くことを 求められる（）。

Privacy Considerations

本節は、このユースケースにおける検証が何を誰に対して明らかにするか、 そしてそれを限定するためにこのユースケースが何をしているかを述べる。本節は要件を 述べない。 の問い合わせが一般に何を明らかに するか、およびそれに対する手立ては、Core Specification [[OPF-CORE]] の privacy considerations にあり、ここでは繰り返さない。このユースケース が加えるのは、同文書が [=Use Case Specification=] に委ねている事柄である。 それは、問い合わせがいつ行われるか、文書を得ることが何を明かすか、 どの当事者がどこで動作して行う か、[=Originator=] 自身のゾーンに対する問い合わせが何を名指しするか、 そしてページを取得する [=Verifier=] が何を知ることになるか、である。

問い合わせがいつ行われるか

問い合わせはページが提示されるときに行われる。検証の結果は保持されず、 判断は毎回改めて行われる（、 ）。したがって、ブラウジング ソフトウェアのキャッシュに保持されたページは、再び表示されるときに再び 検証され（）、キャッシュが答え られない問い合わせのタイミングは [=Recipient=] のブラウジングの タイミングである。

キャッシュは、問い合わせのタイミングが明かすものを狭めるが、無くしはしない。chain を 既に検証して保持しているサイトを再訪する場合、それらの chain について の問い合わせは一つも繰り返されず、DNS からの応答はその time to live が尽きるまで使える（）。したがって 問い合わせが印すのは、ページが読まれるたびではなく、最初の訪問と、 キャッシュが期限切れになった後の訪問である。

文書を得ることが明かすもの

問い合わせが [=Originator=] に届くのは、そのゾーンのサーバを通して、 それらのサーバが受け取る総計としてだけである。これに対して 文書の取得が何を明かすかは、文書がどの経路で得られるかによる。文書がページに 埋め込まれている場合、[=Originator Profile=] を得るために well-known リソースへの要求のほかには何も取得されない。

文書が [=Page Origin=] の well-known リソースから得られる場合（）、 [=Verifier=] はそれを、ページを配信するサーバから取得する。そのサーバは ページが取得されたことを既に知っている。それまで読まれたことを知らな かった当事者がそれを知ることは無く、取得が加えるのは、[=Recipient=] が [=Verifier=] を使っている、ということである。ページが、ページを配信する host の上の URL で文書を名指ししている場合も同じである。その URL が 別の host の上にある場合、[=Verifier=] はそこから文書を取得し、ページを 配信していないその host は、自分を名指すページが検証されていることを 知る。

well-known リソースへの要求はページが [=Originator Profile=] を運んで いるかどうかにかかわらず行われるので（）、 [=Recipient=] が [=Verifier=] を使っているという事実は、枠組みに参加 していないサイトも含め、[=Recipient=] が訪れるすべてのサイトに明かされる。 その事実はある [=Recipient=] を他と見分ける材料に なりうる。

その要求は、[=Recipient=] がそのページを訪れると決める前には 行われない。要求は、[=Recipient=] が好む言語など、ブラウジング ソフトウェアが通常送るものを運び、HTTP キャッシュに保持された 応答があれば、要求はそもそも行われない。

どの当事者が問い合わせを行うか

どの当事者が問い合わせを行い、その当事者がどこで動作するかが、誰が それを見るかを決める。ブラウジングソフトウェアの中の [=Verifier=] は [=Recipient=] 自身の端末の上で動作し、その端末またはそのネットワークに 与えられた resolver を用いるか、自ら validate する。いずれにせよその resolver、またはそれが到達する権威サーバは、どの [=Originator Profiles=] がいつ検証されているかを見る。つまり、 [=Originator Profile=] を提示するサイトのうちどれを [=Recipient=] が 読んでいるか、そしてそれをいつ読んでいるかを見る。

ブラウジングソフトウェアの中の [=Verifier=] が validating resolver への自前の経路を持つ場合 （）、それによってその resolver を 選んでいることになり、その resolver は本手順のすべての問い合わせを [=Recipient=] 自身のアドレスから見る。その選択は [=Verifier=] のもので あって、[=Recipient=] のものではない。このユースケースでは、サービスが 検証するのでない限り、これを集約することで [=Recipient=] からこの露出を 取り除く当事者はいない。

問い合わせが何を名指しするか

問い合わせが何を名指しするかは、一般モデルと同じ切り分けに従う。発行者 が公開する [=Originator Key Records=] と [=Revocation Records=] は不透明な label を運ぶので、resolver と権威サーバの 間の観測者が知るのは、発行者のレコードのいずれかが検査されているということであって、 それが誰のものかではない。この性質は Core Specification [[OPF-CORE]] のものであり、ここでもそのまま成り立つ。 この性質は、[=Originator=] 自身のゾーンのレコードには及ばない。それらの名前はドメインそのものを 運ぶからである。

[=Originator=] が、許された [=Core Profile Issuers=] を挙げるレコードの 公開を求められていないことは、この露出を減らさない。そのレコードを引く [=Verifier=] は、それが存在するかどうかにかかわらず問い合わせるからで ある。[=Verifier=] がそれを引くことを求められるのは [=Page Origin=] を 与えない状況だけであり、それ以外の状況では引いてもよい （）。検証のたびに引く [=Verifier=] は、自らが評価するすべてのページについて問い合わせを行い、 [=Originator=] のゾーンはそれを見る。求められる所でだけ引く [=Verifier=] は、ブラウジングソフトウェアの中で提示されるページに ついては問い合わせを行わない。

ゾーンのサーバがその問い合わせを見るのは、それらに問い合わせる resolver が作り出す総計としてだけであり、キャッシュによって減る。1 つの レコードがその [=Originator=] のすべてのページに対して用いられるから である。またゾーンのサーバは、どの [=Recipient=] が尋ねたかを知らない。 問い合わせは resolver から届くからである。[=Permitted Host Record=] を 引くのは、[=Originator=] の [=Identity=] でもなくその下にも無い host に ついてだけであり （）、その名前はその host を運ぶ。

ページを取得するサービスが知ること

ページを取得する [=Verifier=] は、ブラウジングソフトウェアの中の [=Verifier=] が知らないことを知る。検証するためにはページを持たなければならないので、 そのページの URL を持ち、どの [=Originator=] かだけでなく、どのページが 検証されているかを知る。[=Recipient=] にそのページがこれから見せられる という理由でサービスがページを取得する場合、サービスはその閲覧を、 それが起きている時点で知る。 そのようなサービスがそういう位置に置かれるのかどうかは未決である （、）。 ブラウジングソフトウェアの中の [=Verifier=] は、[=Recipient=] 自身の端末が 既に持っていること以上のものを何も知らない。

resolver においては、この 引き換えが逆向きに働く。サービスは多数の [=Recipients=] のために検証 するので、その resolver と、それが問い合わせるゾーンとが見るものは、 それらにわたって集約 されている。これに対し、[=Recipient=] 自身の端末の上の、ブラウジング ソフトウェアの中の [=Verifier=] は何も集約しない。 の 2 つの配置は、この ように、security において異なるのと同じく privacy においても異なる （）。そしてこの引き換えは、 resolver に対する露出と、サービス自身に対する露出との間のものである。

本仕様は、他者のために検証する当事者が、取得したページや、どの [=Recipient=] がどのページをこれから読もうとしていたかという知識を どう扱ってよいかについて、何の制限も課していない。また framework は その当事者にいかなる位置づけも与えていない。その当事者とページを提示 する当事者との間の取り決めは未決のまま残されており （）、本仕様はそのような当事者が立つ信頼の境界を 定めていない。本仕様がそのような当事者に 何かを求めるべきかどうか、あるいはこの事柄が本文書ではなく framework のガバナンスに属するのかどうかは、この版では決まっていない。 これは、依拠してよいものについて が提起する問い の、privacy 側の半分である。

Email Use Case Specification との違い

本付録は、本仕様が Email [=Use Case Specification=] [[OPF-EMAIL]] とどう異なるか を示す。構造としての結論は、違いが次の 5 つであるということである。

  2. [=Presented Identity=] をどう取り、どの文書が binding を宣言するか。
  3. 外側の certificate の層があるかどうか。
  4. 検証がどこで行われ、どの時点を基準として判断し、その結果が保持される かどうか。

DNS の発行者側にあるものはすべて両ユースケースに共通 であり、それを担っているのが Core Specification [[OPF-CORE]] である。

この表と、[[OPF-EMAIL]] の付録「Differences from the Web Media Use Case Specification」の表とは 1 つの表であり、それぞれ自分の側から書いたものである。両者は 整合が保たれるべきものであり、一方に行を足したら他方にも足す。列見出し はあちらと同じにしてあり、両者を突き合わせて読めるようにしてある。 「Web media」の見出しの列が本仕様のものである。
