はじめに

Originator Profile Framework は、コンテンツの [=Recipient=]（受け手）に 対して、そのコンテンツの [=Originator=]（出所）の検証可能な profile を 与える。この profile は、[=Core Profile Issuer=] が発行する [=Core Profile=] と、独立した [=Profile Annotation Issuers=] が発行する [=Profile Annotations=] から成る。この枠組みをアーキテクチャの水準で 記述しているのが Architectural Overview [[?OPF-AOV]] である。本文書は、 枠組みのうちユースケースに依存しない共通の部分を、規範的な用語で規定 する。

この枠組みが存在するのは、コンテンツの [=Recipient=] が、自分の手元に 届いたものの背後に誰がいるのかを判断する材料をほとんど持たないから である。その問題と設計の背景にある論理は [[?OPF-AOV]] が述べている。 本文書が述べるのは、その結果として得られる profile が検証可能である ために何を作り、何を運用しなければならないかである。すなわち、識別子、 署名された文書が持つプロパティ、DNS に何が公開されるか、その存在と 不在が何を意味するか、そして [=Verifier=]（受け手に代わって検証を行う ソフトウェア）が結論に至る手続きである。

スコープ

本文書が規定するのは、すべてのユースケースに共通するものである。 すなわち次のものである。

  • この枠組みが用いる識別子。
  • [=Core Profile=]・[=Profile Annotation=]・[=Content Attestation=] が検証のために持つプロパティ。
  • [=Root Core Profile=] と [=Accreditation Chain=]。
  • issuer が公開する DNS レコードと、その存在および不在の意味。
  • ユースケースが自らの入力を供給する地点までの検証手続き。

本文書は次のものを規定しない。

  • 本文書が依拠する DNS レコード型のワイヤフォーマット。これは [[OPF-DNS]] が定義する。
  • [=Originator Profile=] が [=Recipient=] にどのように配送されるか、 コンテンツが提示される際の identity がどのように [=Originator=] に結びつけられるか、検証がどこでいつ行われるか。これらは [=Use Case Specifications=]（Web Media や Email のようなユースケース ごとに、本文書の上に立つ仕様）に属する。
  • issuer が自らの zone を運用する際の運用規則とガバナンス規則。 これらは Operational Governance Requirements [[?OPF-GOV]] と Operations 文書 [[?OPF-OPS]] に属する。

他の文書との関係

本文書は、枠組みを説明する Architectural Overview [[?OPF-AOV]] と、 本文書の上に立つ諸文書との間に位置する。

Internet-Draft [[OPF-DNS]] は、OPKEY というレコード型、その配置、移行期の公開を 定義しており、本文書の規範的な参照である。[[OPF-DNS]] が record publisher、すなわち _op の下にレコードを公開する CP issuer または PA issuer と言うところを、本文書は [=issuer=] () と言う。[=Accreditation Body=] と [=Root Issuer=] は、[[OPF-DNS]] の語では PA issuer である。それらが 発行する [=Issuer Accreditations=] は [=Profile Annotations=] だから である。また [=Root Issuer=] は、自らが発行する [=Core Profiles=] については、同じ語で CP issuer である ()。

個々の [=Use Case Specification=]（Web Media、Email、および計画中の Web Advertisement）は、 配送、identity の結びつけ、検証の場所と時点、そしてそれらの選択から 導かれるセキュリティ上の考慮事項を定義する。Operational Governance Requirements [[?OPF-GOV]] は枠組みを運用する当事者が求められることを 述べ、Operations 文書 [[?OPF-OPS]] は、それらの要求を満たすための値、 サービスレベル、手順を担う。この 2 つの文書は、どちらもまだ公開されていない。

Originator Profile Collaborative Innovation Partnership が公開する Originator Profile Blueprints [[Originator Profile Blueprints]] は、 枠組みの文書と資源を今日実装されている形で記述しており、本文書は 署名された文書のプロパティ名をそこから採る ()。Blueprints は現状、次の点で 本文書と異なり、それを本文書に揃える作業が進行中である。

  • 失効。本文書は、鍵を [=withdrawn=]（取り下げられる）とし、 [=Core Profile=] または [=Profile Annotation=] を revoke するのを、 DNS のレコードによって行う ()。 Blueprints は、失効リストのような独自の失効の仕組みを採らない。
  • 鍵の使用を止めること。本文書は鍵を [=Originator Key Record=] から 除くことで止め、その鍵を保持する以前の [=Core Profile=] は、期限が 切れるか revoke されるまで有効であり続ける。Blueprints は、鍵を [=Core Profile=] に含めないことで止める。
  • 信頼の根。本文書は、[=Verifier=] に、[=Root Core Profile=] で 終わる [=Accreditation Chain=] を通じて issuer を受け入れさせる ()。 Blueprints は、[=Verifier=] に [=Core Profile Issuers=] の鍵と 識別子をあらかじめ受け入れさせる。
  • issuer の認定。本文書は、[=Root Issuer=] 以外のすべての issuer に [=Issuer Accreditation=] を求める。Blueprints は、[=Verifier=] が [=Profile Annotation Issuer=] の登録を確かめることを推奨し、 [=Core Profile Issuer=] の認定については何も述べない。
  • record name。Blueprints は、[=Core Profile=] が運ぶ [=Originator Key Record Name=] のためのプロパティも、 [=Profile Annotation=] が運ぶ [=Revocation Record Name=] と発行ごとの 識別子のためのプロパティも、まだ与えていない ( の issue)。
  • [=Key Identifier=]。本文書はそれを鍵の SubjectPublicKeyInfo から 導く ()。Blueprints は鍵をその JWK Thumbprint で識別しており、本文書の形へ変更されつつある。
  • [=Profile Annotation=] の終わり。本文書では、署名の有効期間が終わった annotation は効力を失い、[=Originator Profile=] の残りは影響を 受けない。Blueprints では、それは [=Originator Profile=] 全体が 有効である期間を縮める。
  • 他の [=Originator=] についての annotation。本文書では、 [=Core Profile=] が保持するものとは別の [=Identity=] を名指す [=Profile Annotation=] は有効でなく、他の annotation は影響を 受けない ( の手順 8)。Blueprints は、 文書の集合（Blueprints の Originator Profile Set）全体を無効として扱う。
  • [=Verifier=] の時計の許容。本文書は 5 分の上限を定める ()。Blueprints は、それを [=Verifier=] のポリシーに委ねる。

本文書の記法

何が規範的か、key word の無い文は何をするか。 非規範的と記された節、およびすべての note、例、附属書は informative である。それ以外はすべて規範的である。規範的な本文で key word を 一つも使わない文は、他所で述べた要件をその出典を示して言い直すか、 語や値を定めるか、説明するものである。他のどこにも述べていない要件は key word で 述べる。

DNS 名の書き方。本文書における DNS 名は、 末尾のドットを付けない完全修飾ドメイン名として書く。ラベル <originator> と <cp-issuer> は、それぞれの当事者の FQDN を表す。<cp-issuer> は当該の [=Core Profile=] の発行者であり、その [=Core Profile=] を [=Root Issuer=] が発行したときは [=Root Issuer=] である ()。 <issuer> はいずれかの issuer () の FQDN を、 <record-label> は [=record label=]、すなわち issuer が 割り当てる名前ごとに選ぶ不透明な左端の label (。 の例では UUID) を、<host> は host の名前を表す。<name> のような山括弧の ラベルでそれ以外のものは、使う箇所で説明する。

validation state と SVCB のフィールド名。[[RFC4035]] の DNSSEC の validation state は、Secure や Insecure のように italic で書き、 名詞を修飾する形で使う場合も同じとする。SVCB レコード [[RFC9460]] の フィールド名は、ServiceMode や TargetName のように code の書体で書く。

用語

Accreditation Body
[=Accreditation Body=] は、[=Root Issuer=] が、直接に、またはその 権限を受けた entity を介して、[=Issuer Accreditations=] を発行する 権限を与えた entity である。
Accreditation Chain
[=Accreditation Chain=] は、ある issuer から [=Root Core Profile=] までの [=Issuer Accreditations=] の列であり、各 issuer の [=Core Profile=] を伴う。各 [=Issuer Accreditation=] は、それが accredit する issuer の [=parent issuer=] が発行したものである。
Content
[=Content=] は [=Originator=] に由来する情報である。
Content Attestation
[=Content Attestation=] は [=Signed Data from Originator=] の一種で あり、[=Content=] が対応する [=Originator=] に由来することを確認する。 [=Content Attestation=] は、[=Originator=] の [=Originator Profile=] の一部である [=Core Profile=] が載せる [=Originator Verification Key=] で検証される。
Content Validity Period（内容の有効期間）
内容の有効期間は、[=Profile Annotation=] が述べることのできる期間で あり、その間、annotation が述べることが成り立つ。annotation の 署名の有効期間を含まなければならない ()。
Core Profile
[=Core Profile=] は、ある [=Originator=] に関する本質的な [=Validated Attributes=] の集合であり、[=Core Profile Issuer=] が 発行する。ただし [=Root Core Profile=] は、その [=Root Issuer=] が 自らについて発行し、他の者は validate しない。これはその [=Originator=] の [=Originator Verification Keys=] を載せる。 [=Root Core Profile=] 以外の [=Core Profile=] は [=Originator Profile=] の一部である。
Core Profile Issuer
[=Core Profile Issuer=] は、自身の [=Core Profile Policy=] の下で [=Core Profile=] を発行する entity である。
Core Profile Policy
[=Core Profile Policy=] は、[=Core Profiles=] の発行と管理を律する ポリシーの集合である。
Identity
[=Originator=] の [=Identity=] は、その [=Originator=] が枠組みの中で 知られるドメイン名である。[=Core Profile=] がこれを載せ、 [=Verifier=] は [=Presented Identity=] をこれと照合する。
Issuer Accreditation
[=Issuer Accreditation=] は、issuer 自身の [=Core Profile=] に 対する [=Profile Annotation=] であり、枠組みにおけるその issuer の 立場、たとえば [=Core Profile Issuer=] や [=Profile Annotation Issuer=] としての立場を述べる。これは [=Root Issuer=] または [=Accreditation Body=] が発行する。
Issuer Key Record
[=Issuer Key Record=] は、鍵そのものではなく [=Key Identifiers=] を列挙する DNS record set である。issuer () が自身の名前の下でこれを公開し、 これは、その issuer の文書の上の署名が受け入れられるべき鍵を 名指す。すなわち、issuer が署名に用いている鍵、これから署名に用いる 鍵、およびその署名がまだ検証されうる鍵である ()。
Issuer Pinning Record
[=Issuer Pinning Record=] は、[=Originator=] が自身の [=Identity=] の zone で公開する DNS record set であり、その [=Originator=] のために [=Core Profile=] を発行することを許された [=Core Profile Issuers=] を名指しするか、その [=Originator=] が [=Originator Profile=] を 持たないことを宣言する。レコードが issuer を名指している [=Originator=] は、それらの issuer に pin されている（pinned）。 このレコードを公開していない [=Originator=]、または zone が署名されて いない [=Originator=] は、[=Use Case Specification=] が unpinned の [=Originator=] を認める場合には unpinned である。[=Use Case Specification=] は、代わりにこのレコードを要求してもよく、その場合 にはレコードの不在は失敗である。
Key Identifier
[=Key Identifier=] は [=Originator Verification Keys=] のうちの 一つ、または issuer () の [=Verification Key=] のうち、その issuer が発行する文書の検証に用いる ものを識別する。これは鍵そのものから導かれ、本文書が定めるとおりに 計算した public key の digest である。したがって同じ鍵は、 [=Content Attestation=] の中、[=Core Profile=] の中、DNS の中の どこに現れても同じ [=Key Identifier=] を持つ。二つの鍵は、同じ digest アルゴリズムで計算した [=Key Identifiers=] が等しいとき同じ鍵である。
Originator
[=Originator=] は、なんらかの [=Content=] を [=Recipients=] へ送る entity である。Originator Profile Framework において [=Originator=] は、[=Content Attestation=] のようなさまざまな形の [=Signed Data from Originator=] を作る entity でもある。この枠組みでは すべての issuer も [=Originator=] である。issuer 自身の [=Core Profile=] はその issuer についてのものであり、issuer が発行する文書は [=Signed Data from Originator=] である ()。
Originator Key Record
[=Originator Key Record=] は、鍵そのものではなく [=Key Identifiers=] を列挙する DNS record set である。[=Core Profile Issuer=] は、自らが発行する [=Core Profile=] ごとに一つを自身の 名前の下で公開し、それはその [=Core Profile=] の [=Originator Verification Keys=] のうち取り下げられていないものの [=Key Identifiers=] を列挙する。それが存在することは、その [=Core Profile=] が revoke されていないことを意味する。
Originator Key Record Name
[=Originator Key Record Name=] は、[=Originator Key Record=] の 完全修飾 DNS 名である。[=Core Profile Issuer=] が割り当て、[=Core Profile=] が保持する。
Originator Profile
[=Originator Profile=] は、ある [=Originator=] に関する [=Validated Attributes=] のうち、枠組みが検証可能にするものの集合で ある。 [=Originator Profile=] は一つの [=Core Profile=] と一つ以上の [=Profile Annotations=] から成り、[=Use Case Specification=] は これにそのユースケースに固有の文書を加えることができる。[=Core Profile=] は [=Originator Verification Keys=] などの本質的な情報を含み、 [=Profile Annotations=] は [=Originator=] に関する追加の [=Validated Attributes=] を 与える。
Originator Profile Bundle
[=Originator Profile Bundle=] は、[=Originator Profile=] を運ぶ 文書の集合である。すなわち、[=Originator=] についての一つ以上の [=Core Profiles=]（[=Verifier=] は の手順 5 で、 の上限の範囲で、その中から 選ぶ）、それらとともに提示される [=Profile Annotations=]、各 [=Core Profile Issuer=] と各 [=Profile Annotation Issuer=] の [=Accreditation Chain=]（[=Root Core Profile=] で終わる）、および [=Use Case Specification=] が [=Originator Profile=] に加える文書である。 [=Originator Profile Bundle=] がどのように [=Verifier=] へ運ばれるかは [=Use Case Specification=] が定義する。
Originator Verification Key
[=Originator Verification Key=] は、[=Originator=] の [=Core Profile=] が載せる [=Verification Key=] であり、[=Signed Data from Originator=] はそれで検証される。
Permitted Host Record
[=Permitted Host Record=] は、[=Originator=] が自身の [=Identity=] の zone で公開する DNS record set であり、その [=Identity=] そのもの ではなく、その配下にもない host が当該 [=Originator=] の [=Originator Profile=] を提示することを許す。
Presented Identity
[=Presented Identity=] は、[=Content=] がその下で [=Recipient=] に 届く identity であり、[=Verifier=] が [=Use Case Specification=] の 定める方法で配信の経路から得る。たとえば web ページの origin や、 メッセージの author のドメインである。[=Verifier=] は、これを [=Core Profile=] にある [=Originator=] の [=Identity=] と照合する。
Profile Annotation
[=Profile Annotation=] は署名済みデータであり、[=Profile Annotation Issuer=] が [=Profile Annotation Policy=] の下で発行し、 [=Validated Attributes=] の集合を、両者が対象とする [=Identity=] を介して、 ある [=Originator=] の [=Core Profile=] へ結びつける ()。 [=Profile Annotation=] の種類はそれぞれ特定の目的に仕える。たとえば Organization Profile や、ある法域に固有の annotation である。
Profile Annotation Issuer
[=Profile Annotation Issuer=] は、一つ以上の種類の [=Profile Annotations=] を発行する entity である。それとしての立場と、発行して よい種類は、その [=Issuer Accreditation=] が述べる ()。
Profile Annotation Policy
[=Profile Annotation Policy=] は、[=Profile Annotations=] の発行と 管理を律するポリシーの集合である。
Recipient
[=Recipient=] は [=Content=] を受け取る entity である。
Revocation Record
[=Revocation Record=] は、[=Profile Annotation=] の issuer が自身の 名前の下で公開する DNS record set であり、それが存在することは、その annotation が revoke されたことを意味する。
Revocation Record Name
[=Revocation Record Name=] は、ある [=Profile Annotation=] が revoke された場合に、その [=Revocation Record=] が公開される完全修飾 DNS 名 である。annotation の issuer が割り当て、[=Profile Annotation=] が 保持する。
Root Core Profile

Identity とは何か。 [=Originator=] の [=Identity=] は完全修飾ドメイン名である。 [=Core Profile=] は、その subject の [=Identity=] を、当該の名前を値と する dns: URI [[RFC4501]] として保持しなければならない (MUST)。サブドメインはそれ自体で一つの identity である。組織が目的ごとに 別々の [=Originator Profiles=] を持つ場合は、そのそれぞれに別の [=Identity=] を用いることによってそうし、ある [=Identity=] に対して発行 された [=Profile Annotation=] は、別のものについて何も述べない。

canonical form。 ドメイン名が canonical form にあるとは、次のすべてを満たすことを いう。

  • すべての label が小文字であること。
  • すべての label が LDH label [[RFC5890]] であること（したがって国際化された label はその A-label として現れる）。ただし [=Originator Key Record Name=] または [=Revocation Record Name=] の中ではアンダースコアで始まる label [[RFC8552]] も許される。
  • 空の label が無いこと。
  • 末尾のドットが無いこと。

dns: URI が canonical form にあるとは、 そのような名前だけを保持し、他に何も持たないことをいう。すなわち [[RFC4501]] が本来は許す authority も query も持たない。

等しい、配下にある、同じかその配下にある。 二つの名前が 等しいとは、その canonical form が 1 オクテットに至るまで等しいことを いう。ある名前が別の名前の配下にあるとは、前者の canonical form が、 label の区切りを先頭に付けた後者の canonical form で終わることをいう。 こうして一致は label の境界で起きる。たとえば www.example.com は example.com の配下に あるが、badexample.com はそうではない。ある名前が別の 名前と同じかその配下にあるとは、両者が等しいか、前者が後者の配下に あることをいう。

署名者の義務。 本仕様の文書に署名する者はすべて、[=Content Attestation=] に署名する [=Originator=] を含め、自らが行う署名の対象に入るすべてのドメイン名を canonical form で書かなければならない (MUST)。それらの名前は、その文書が対象とする [=Identity=]、その文書が issuer として保持する [=Identity=] ()、およびその文書が保持する [=Originator Key Record Name=] または [=Revocation Record Name=] () である。

canonical form にない名前。 [=Verifier=] は、DNS が返した名前が canonical form にないとき、たとえば SVCB record の TargetName が大文字や末尾の 点を含むとき、まずそれを canonical form にした上で受け入れなければ ならない (MUST)。そうした名前における大文字小文字の違いや末尾の点は、 失敗ではない。[=Verifier=] は、文書の中の canonical form にない値も、 同じようにして受け入れてもよい (MAY)。いずれの場合も、canonical form が異なる二つの値を一致とみなしてはならない (MUST NOT)。

規則が当てはまる所。 本節の規則、すなわち canonical form にしてから比較することは、本文書が 求めるドメイン名のすべての比較に適用される。

[=Presented Identity=] が [=Identity=] と比較される場面では、 [=Presented Identity=] が何であるか、[=Verifier=] がそれをどう得る か、どう canonical form にするかを [=Use Case Specification=] が定義 する ()。比較そのものは本節の規則で ある。

Root Core Profile、Issuer Accreditation、Accreditation Chain

Issuer Accreditation とは何か。 issuer の立場は [=Issuer Accreditation=] が述べる。これは、issuer 自身の [=Core Profile=] に対する [=Profile Annotation=] であり、 その issuer を accredit した body が発行する。それは、その issuer が [=Core Profile Issuer=]、[=Profile Annotation Issuer=]、 [=Accreditation Body=] のいずれであるか、またはそのうちの複数であることを 述べる。[=Profile Annotation=] であるから、これは [=Revocation Record Name=] を保持し、他のものと同様に revoke され得る。 の定義のとおり、[=Accreditation Body=] とは、 [=Issuer Accreditations=] を発行することを許された者である。

Root Core Profile。 [=Root Core Profile=] は [=Originator Key Record Name=] を保持せず、それについて [=Originator Key Record=] が引かれることはない。それでも、その [=Root Issuer=] の [=Issuer Key Record=] は、他の issuer のものと同じく _issuer-key._op.<issuer> に公開され ()、すべての chain の最上段について 参照される。最上段は [=Root Core Profile=] が保持する鍵で署名されている からである ()。[=Verifier=] は、 [=Root Core Profile=] が述べる署名の有効期間を検証の条件として扱ってはならない (MUST NOT)。[=Root Core Profile=] は期限切れにならず、 の経路を通じて置き換えられ、 それが保持する日付はその置き換えの予定である。

Root Core Profile がどこから来るか。 [=Verifier=] は、自らが受け入れる [=Root Core Profiles=] を保持し、それ 以外を受け入れない ()。それら は検証ソフトウェアとともに届く。本文書は、プロトコル を通じて [=Root Core Profile=] を得る手段を定義しないし、ある issuer から その parent issuer を指す DNS のレコードも無い。したがって chain は、コンテンツに付随する文書から検証される。 が規定するとおりである。

[=Root Issuer=] がこれらのレコードを公開しないとすれば、[=Root Issuer=] が 発行する [=Core Profile=] の [=Originator Key Record=] を公開する者は無い。 [=Verifier=] はその不在を revoke と読み、そのような [=Core Profile=] は どれも使えない。代わりにそれらについて検査を免除すれば、revoke できなく なる。そのような [=Core Profiles=] は必ず存在する。chain の最上段の issuer の [=Core Profile=] は、[=Root Issuer=] からしか来ないからである。

誰が accredit するか、accredit が与えないもの。 [=Issuer Accreditation=] が [=Accreditation Chain=] の段となるのは、 その発行者が [=Root Issuer=] であるか、同じ chain の中で それより [=toward the root=]（root の側）で [=Accreditation Body=] として立てられた者である 場合に限られる。[=Accreditation Body=] は、[=Root Issuer=] と同じく、どの立場を 述べてもよい (MAY)。[=Accreditation Body=] の立場も含む。ある者が 与えてよいものと、自ら発行してよいものは別である。自ら文書を発行するには、 [=Accreditation Body=] はそのための立場を要する。

  • [=Core Profile=] を発行するには、[=Core Profile Issuer=] として 立てられている必要がある（ の段取り 5）。
  • [=Issuer Accreditation=] 以外の 種類の [=Profile Annotation=] を発行するには、その種類を含む種類の 集合を持つ [=Profile Annotation Issuer=] として立てられている必要が ある（ の段取り 8 の検査 (b)）。

chain のどの段でも、body が与えてよいものと自ら発行してよいものは別々に 決まる。立場だけでどの種類の annotation でも発行できる body は、 どの accreditation もその annotation を記述しない、ただ一つの issuer に なってしまう。そのとき [=Root Core Profile=] の鍵は、accreditation だけでなく コンテンツについての annotation にも署名することになる。その種類について accredit された別の [=Identity=] は、body がそれまで持っていたものを何も 失わせない。

ある者が Accreditation Body とみなされるとき。 ある者を [=Accreditation Body=] とみなすのは、 [=Verifier=] がその者を [=Accreditation Body=] として立てる [=Accreditation Chain=] を、その chain についての の DNS の確認まで含めて検証した 場合に限られる。そのような者は、[=Issuer Accreditations=] を発行する のに [=Profile Annotation Issuer=] の 立場を別に持つ必要はない。 の段取り 2 と 8 では、その者を [=Accreditation Body=] として立てる chain、またはその者の [=Root Core Profile=] が、その accreditation の発行者の chain の役を果たす。 それでも、自らが発行する [=Issuer Accreditations=] については、そのような者はその語 の意味での [=Profile Annotation Issuer=] であり、 の上限 2 に一つとして数える。

複数の accreditation、複数の chain。 ある issuer が複数の [=Issuer Accreditation=] を持つ場合、 [=Verifier=] が検証したそのうちのどれか一つがある種類を認めて いれば、その issuer はその種類を持つ。その accreditation に複数の chain で至れる場合、[=Verifier=] は、次に定める [=Originator Profile Bundle=] の順序で 最初に検証したものを用いる。この順序は、issuer に最も近い段から root の側へ向かって組み立てる。

Originator が署名する文書。 [=Originator=] は、特定のユースケースの目的のために、自らの [=Originator Verification Keys=] に対応する鍵で他の文書にも署名する。そのような 文書は [=Originator Profile=] の外にある。自らのレコードの名前を 持たず、それについて答える DNS のレコードも無く、DNS で revoke されない。

Originator が署名する文書の有効性。 その有効性は [=Originator Profile=] と、それに署名した鍵に従う。 すなわち、 のいう意味でその鍵が現行の ものである間、かつそれを保持する [=Core Profile=] が有効である間 にのみ、それらの 文書は役に立つ。そのような文書が何を含み、[=Verifier=] がそれを どう扱うかは [=Use Case Specification=] が定義する。

Core Profile Issuer が発行する文書。 [=Originator Profile=] の外にある文書のすべてが [=Originator=] に よって署名されるわけではない。[=Use Case Specification=] が、 [=Core Profile Issuer=] が [=Originator=] について発行するそのような 文書を定義し、それを [=Originator Profile=] に加えない場合、その文書は同じ意味で [=Originator Profile=] の 外にあり、その有効性は同様に [=Originator Profile=] と、それに署名 した鍵に従う。

Issuer Key Record

レコードを公開する場所。 [=issuer=]、すなわち [=Core Profile Issuer=]、[=Profile Annotation Issuer=]、[=Accreditation Body=]、[=Root Issuer=] () は、自らの [=Issuer Key Record=] を _issuer-key._op.<issuer> における OPKEY の record set として公開しなければならない (MUST)。ここで <issuer> は当該 issuer を識別する名前である ()。

存在が意味すること。 その record set は、当該 issuer の文書の上の署名を [=Verifier=] が受け入れる鍵の [=Key Identifiers=] を列挙する。すなわち、issuer が署名に用いている鍵と、本節の以下が それに並べて保たせる鍵である。その record set に [=Key Identifier=] が存在することは、その鍵による署名が受け入れられる ことを意味する。存在しないことは、受け入れられないことを意味する。 その鍵で署名された文書が何と述べていようと同じである。

レコードが運ぶもの。 [=Issuer Key Record=] は当該 issuer 自身の鍵の [=Key Identifiers=] だけを保持する。[=Originator=] の鍵は別の名前に列挙され ()、ある issuer からその parent issuer を指す DNS のレコードは存在しない。 [=Accreditation Chain=] は文書から検証される。 が規定するとおりである。

Verifier の検査。 [=Verifier=] は、issuer の鍵で署名を検証するすべての文書について、 その鍵の [=Key Identifier=] が当該 issuer の [=Issuer Key Record=] に 存在することを確かめなければならない (MUST)。[=Root Core Profile=] 自体は そのような文書ではない。[=Verifier=] はそれを DNS に照らして検証する のではなく、保持する ()。一方、 [=Root Issuer=] が署名する [=Issuer Accreditations=] と それ以外の [=Core Profiles=] は そのような文書である。chain の他の段のものと同じく、署名した 発行者の [=Issuer Key Record=] に照らして検査される ()。

署名の鍵を変えること。 issuer が署名に用いる鍵を変えるときは、新しい鍵の [=Key Identifier=] を、前の鍵のものと並べて公開する。 が求めるとおり、自らの [=Issuer Key Record=] の TTL が過ぎてから、新しい鍵で署名した文書を 発行する。新しい鍵で署名した文書が検証を通るより前に、新しい鍵は その issuer の新しい [=Core Profile=] にも載っていなければならない。 [=Verifier=] は issuer の鍵を issuer 自身の [=Core Profile=] から取る からである ()。その [=Core Profile=] は、issuer が自らの [=Core Profile=] を受ける issuer が発行する ()か、新しい [=Root Core Profile=] である。これらの段取りの順序は [[?OPF-OPS]] が示す。

Originator Key Record

レコードとは何か、何を運ばないか。 [=Core Profile Issuer=] は、自らが発行し、revoke していない [=Core Profile=] ごとに [=Originator Key Record=] を公開しなければ ならない (MUST)。これは、その [=Core Profile=] が保持する [=Originator Key Record Name=] における OPKEY の record set であり、その [=Core Profile=] にある各 [=Originator Verification Key=] の [=Key Identifier=] の形ごとに 1 レコードを含む ()。[=Verifier=] は、[=Core Profile=] そのものをどこで得られるかを [=Originator Key Record=] から知ることは ない。本文書はその目的のレコードをそこに置かない。

[=Core Profile=] をどこで得られるかをレコードが述べるとすれば、[=Verifier=] はそれを issuer から取得することになる。そのとき issuer には個々の [=Verifier=] が見える。DNS が issuer に見せるのは、resolver が転送するもの だけである ()。また issuer は、 自らのレコードには本来要らないサービスを運用しなければならなくなる。 代わりに、[=Originator Profile Bundle=] が、[=Use Case Specification=] の 定める道で [=Core Profile=] を運ぶ。

存在と不在。 存在と不在は次の意味を持ち、[=Verifier=] はそのとおりに読まなければ ならない (MUST)。

  • record set が存在することは、その名前を保持する [=Core Profile=] が revoke されていないことを意味する。
  • あるレコードが存在することは、それが識別する鍵が当該 [=Core Profile=] について current（現行）であることを 意味する。
  • 他のレコードが残っている中で、あるレコードだけが存在しないことは、 その鍵だけがもはや現行のものではないことを意味する。
  • record set 全体が存在しないことは、[=Core Profile=] が何と述べて いようと、その [=Core Profile=] が revoke されたことを意味する。

registration。 ある [=Originator=] の [=Core Profile Issuer=] への registration（登録）は、その [=Originator=] の [=Originator Key Record=] が少なくとも一つ公開されている間、有効で ある。[=Core Profile Issuer=] は、それらをすべて取り除くことで登録を 終える。

Verifier の規則。 [=Verifier=] は、[=Core Profile=] には現れるがその [=Originator Key Record=] には現れない鍵を受け入れてはならない (MUST NOT)。 [=Verifier=] は、[=Originator Key Record=] には現れるが [=Core Profile=] には現れない鍵も、受け入れてはならない (MUST NOT)。[=Verifier=] が 署名を検証するのは [=Core Profile=] が保持する鍵によるからである。

鍵が使われなくなる二つのあり方。 [=Originator Verification Key=] が使われなくなるあり方は、退役と 取り下げの二つである。鍵は、新しい署名にはもう使われないが、その レコードがそれを保持する各 [=Core Profile=] の [=Originator Key Record=] に残されているとき、retired （退役している）である。それで署名されたコンテンツは検証 可能なままであり、文書やレコードの中にそれが退役していることを示す ものは何も無い ()。鍵は、その レコードがそれを列挙するすべての [=Originator Key Record=] から 取り除かれたとき、withdrawn（取り下げられている）である。 それで署名されたコンテンツはもはや検証されない。

Core Profile Issuer への要件。 [=Core Profile Issuer=] は次の要件を満たす。これらは が述べる要件であり、[=Verifier=] の 正しさがこれに依存する。

  • [=Originator Key Record=] を公開し、zone の negative caching の期間を 過ぎるのを待ってから、その名前を保持する [=Core Profile=] を発行 すること。どの [=Core Profile=] も新しい名前を保持する ()。したがってこの待ちは、署名の有効期間を更新する だけの [=Core Profile=] や鍵を替える [=Core Profile=] を含め、 発行のたびに先立つ。

    [=Core Profile=] を先に発行すると、[=Verifier=] がその 名前が存在しないという証明をキャッシュしてしまうかもしれない。また レコードを先に公開しても、resolver が隣接する名前のレコードから そのような証明を既に合成してしまっているかもしれない [[?RFC8198]]。negative caching の期間を待たなければならないのは そのためである。

  • [=Originator=] の鍵が変わるときは、最初の要件が述べるとおり先に公開した 自らの [=Originator Key Record=] を持つ新しい [=Core Profile=] を発行すること。 先の [=Core Profile=] の [=Originator Key Record=] を、その中の 退役させた鍵のレコードとともに、その [=Core Profile=] が期限切れに なるか revoke されるまで残すこと。 が 求めるとおりである。

    本文書は、その後に続く短い 期間を retention margin と呼ぶ。これは、レコードの time to live と、関わる時計どうしの差を吸収する。ある [=Core Profile=] が期限切れになり、retention margin が過ぎたら、 その [=Originator Key Record=] を取り除いてよい (MAY)。

    退役させた鍵のレコードを残すことで、その鍵が現行であった間に それで署名されたコンテンツは検証可能なままとなる。 [=Core Profile=] が期限切れになり、margin が過ぎたら、その [=Core Profile=] はもはや の検査を通ら ないので、レコードをそれ以上残しても何も得られない。

  • [=Core Profile Issuer=] は、各 [=Originator Key Record=] を、その [=Core Profile=] が保持する名前に置いておかなければならない (MUST) ()。レコードを zone に分ける方法を変える issuer は、新しいレコードについてそうする のであって、既存の名前は、それらを保持する [=Core Profiles=] が 期限切れになるか revoke されるまでそのままにしておく。

Revocation Record

Revocation Record とは何か。 [=Profile Annotation Issuer=] は、[=Profile Annotation=] を期限切れ より前に revoke するために [=Revocation Record=] を公開する。これは、 当該 annotation が保持する [=Revocation Record Name=] における TXT の record set であり、その名前はその annotation の一回の発行を名指す ()。存在することは当該 annotation が revoke された ことを、存在しないことは revoke されていないことを意味する。レコードを 持つのは revoke された annotation だけである。[=Issuer Accreditations=] を発行する body も、自らが発行した [=Issuer Accreditation=] を同じ 方法で revoke し、本節の [=Profile Annotation Issuer=] への要件は その body にも適用される ()。

[=Profile Annotation=] は、有効な間、DNS に自らのレコードを持たない。この点で、 [=Originator Key Record=] が鍵も列挙する [=Core Profile=] とは異なる。 annotation は鍵を運ばないので、有効なすべての annotation についてレコードを 置いても、それが存在することしか述べず、しかも annotation の数は多い。 期限切れより前に revoke されたものについてだけレコードを置けば zone は小さく 保たれ、単に更新されない annotation にはレコードが要らない。

レコードの形。 この record set は、一つの character-string から成る TXT レコードを 一つ持つ。[=Profile Annotation Issuer=] はそれを v=op1; revoked=<time> の形にしなければならない (MUST)。ここで op1 はここで定義される内容の版であり、 <time> は当該 annotation が revoke された時刻で あって、Internet date and time [[RFC3339]] として書かれる。 本文書は署名時点での判定を定義せず ()、 のどこもこの値を読まない。他のフィールドは 定義されない。とくに、このレコードは revocation の理由を保持しない。

この時刻は、本文書の後の改訂が署名時点での有効性を判定できるように 記録される。理由を運ばないのは、理由を公開すれば、revocation という 事実が述べる以上のことを DNS で述べてしまうからである。

Verifier の規則。 [=Verifier=] は存在だけで判断しなければならない (MUST)。内容を 解釈できない record set、あるいはその版が op1 でない record set は、revocation として扱わなければならない (MUST)。こうして、 内容の誤りが revocation を沈黙に変えてしまうことがない。その名前にその ような record set が無いという Secure な証明の二つの形は、同等の ものとして扱う。 が求めるとおりで ある。 [=Revocation Record Name=] における Insecure な応答は、検査の 失敗であって、不在ではない。

この版の [=Verifier=] は、内容の後の版をすべて revocation として 読む。したがって内容を変える改訂は、op1 の形のレコードを 読めるまま保たなければならなくなる。そうしなければ、すでに配備された [=Verifiers=] に revocation として読まれることなくレコードを変える ことができないからである。

レコードを残す期間と、レコードが要らないとき。 [=Profile Annotation Issuer=] は、revoke した [=Profile Annotation=] の署名の有効期間が終わり、かつ が [=Verifier=] に その終点を越えて認める許容差 が過ぎるまで、[=Revocation Record=] を公開し続けなければならない (MUST)。その後は、当該 annotation はどの [=Verifier=] の時計の上でも 検証されなくなるので、レコードを取り除いてよい (MAY)。そのような 許容差のうち最も長いものは、 が定める 上限である。単に更新されなくなるだけの annotation にレコードは要らない。 それは期限切れになった時点で有効でなくなる。[=Revocation Record=] は、 その時点より前に annotation を終わらせるためのものである。

期間の終わった annotation。 [=Revocation Record=] が存在しないことに意味があるのは、署名の有効期間が 問い合わせの時点でまだ終わっていない annotation についてだけである。 期間が終わったかどうかは、 の 許容差を入れて判定する。同じように判定して期間が終われば、レコードを 残す期間の規則が許すとおりレコードは取り除くことができる。 したがって、その許容差を入れて判定して期間が検証の時点で終わっている annotation については、不在は何も意味しない。[=Verifier=] は、 [=Use Case Specification=] がどの判定時点を指定していようと、その ような annotation を有効なものとして扱ってはならない (MUST NOT) ()。

Originator が公開するレコード

Originator が公開してよい二つのレコード。 [=Originator=] は、自らの [=Identity=] の zone に 2 種類のレコードを 公開してよい (MAY)。本文書はそのどちらも必須としない。 [=Use Case Specification=] がそれらを必須とするかどうか、また [=Verifier=] がいつそれらを参照するかは、その仕様が定義する。 どちらも、zone が署名されている場合にのみ効力を持つ。[=Verifier=] が それらに基づいて動くのは、問い合わせた名前において応答が Secure で ある場合だけだからである ()。

これらのレコードの運用を他者に任せる [=Originator=] は、issuer が 自らの名前空間の一部を委任しうるのと同じく ()、_op.<originator> を NS レコードで委任できる。そのとき委任先の zone は署名され、その DS レコードが [=Originator=] の zone に公開されなければならない。DS レコードが無ければ、委任先からの応答はすべて Insecure であり、 レコードは効力を持たない。その名前における CNAME や DNAME は委任では なく、 がそれを禁じている。

Issuer Pinning Record。 一つめは [=Issuer Pinning Record=] であり、この [=Originator=] に対して発行することを許された [=Core Profile Issuers=] を名指す。これは _op.<originator> における SVCB の record set [[RFC9460]] である。[[RFC9460]] がそれに求める protocol mapping document は [[OPF-DNS]] であり、各レコードが検証にとって何を 意味するかはここで定義する。以下で「root」とは DNS のルート （.）である。

  • ServiceMode のレコードは、その TargetName において許された [=Core Profile Issuer=] を一つ名指す。
  • ServiceMode のレコードは、TargetName が root であれば、どの issuer も名指さない。
  • TargetName が root である AliasMode のレコードは、この [=Originator=] が [=Originator Profile=] を持たないことを宣言する （この record set の denying form）。

[=Originator=] は、同じ名前において ServiceMode のレコードと AliasMode のレコードを公開してはならない (MUST NOT)。

Verifier がレコードをどう読むか。 [=Verifier=] は AliasMode の TargetName を辿ってはならない (MUST NOT)。 TargetName が root でない AliasMode のレコードは、denying form の 宣言として読まれ、検証は失敗する。 mandatory parameter ([[RFC9460]] Section 8) を持つ レコードは使えない。本文書は、[=Verifier=] が認識しうる parameter を 一つも定義しないからである。その他の parameter は無視される。使える レコードを一つも持たない Secure な ServiceMode の record set は 失敗であり、それによって [=Originator=] が pin されていない状態に なることはない。

Verifier が TargetName をどう比較するか。 [=Verifier=] は各 TargetName を [=Core Profile=] の issuer と ドメイン名として比較しなければならず (MUST) ()、TargetName を名前解決しては ならない (MUST NOT)。ServiceMode のレコードは集合として読まれる。 レコードの SvcPriority ([[RFC9460]]) は、ServiceMode と AliasMode を見分けること以外に、ここでは何の意味も持たない。[=Verifier=] は、 SvcPriority を理由にある TargetName を他より優先したり、 そのうちのどれかを無視したりしてはならない (MUST NOT)。

問い合わせる名前。 [=Verifier=] は、問い合わせる名前を [=Originator=] の [=Identity=] の canonical form から組み立てなければならない (MUST) ()。 canonical form にできない [=Identity=] は検証の失敗であり、[=Verifier=] は [=Originator=] が pin されていないかのように進めてはならない (MUST NOT)。

[=Issuer Pinning Record=] への問い合わせは、Secure な不在が 検証の継続を許す唯一の問い合わせである。誤って組み立てられた名前はどこか別の zone の名前であり、 その答えはこの [=Originator=] について何も述べない ()。

結果。 この record set を参照する [=Verifier=] は、その結果を次のように 扱わなければならない (MUST)。

  • Secure な ServiceMode の応答: この [=Originator=] は pin されて いる。[=Core Profile=] の issuer が TargetName の中に無ければ、 検証は失敗する。使えるレコードを一つも持たない record set は どの issuer も名指さず、検証は失敗する。TargetName が root (.) だけの record set はその一つである。
  • TargetName が何であれ、Secure な AliasMode の応答: 検証は 失敗する。 record set が、二つのモードについての [=Originator=] への要求に反して ServiceMode のレコードも保持して いる場合も同じである。[=Verifier=] は、そのような record set を ServiceMode の応答として読んではならない (MUST NOT)。
  • Secure な不在の証明、または Insecure な応答: この [=Originator=] は pin されていない。検証は続き、その結果には pin されていなかったことが記録される ()。別名を経て到達した応答は、この場合 として読まれる ()。
  • 名前解決の失敗一般、および Indeterminate という結果: 検証は 失敗する。これを不在として扱っては ならない (MUST NOT)。そう扱えば、別の issuer が発行した [=Core Profile=] を握る攻撃者が、この一つの問い合わせを妨げるだけで pin を外せてしまうからである。

Permitted Host Record。 二つめは [=Permitted Host Record=] であり、 <host>._site._op.<originator> における TXT の record set である。それが Secure に存在することは、当該 host が この [=Originator=] の [=Originator Profile=] を提示することを許す。 この record set は、一つの character-string から成る TXT レコードを一つ持つ。許可は host ごとに与えられる。複数の host を許す [=Originator=] は、互いのサブドメインである host も含め、host ごとに レコードを公開する。そのレコードの名前が DNS の許す長さを超えることに なる host は、レコードによって許すことはできない。

許可が host ごとに与えられるのは、[=Verifier=] が、提示された host から 組み立てた一つの名前を問い合わせ、ほかを問い合わせないからである。host の 配下にまで及ぶ許可は、共有の host のように、その配下で提示するすべての当事者に 広がってしまう。レコードは host の zone ではなく [=Identity=] の zone に置かれる。 host の zone を持つのは host を運用する者であり、その者が [=Originator Profile=] を提示してよいかこそが、このレコードの決めることである。 その zone には、署名の有無を問わず、何も求めない。

Originator への要求。 host は名前の中に小文字で、A-label として、末尾のドットを付けずに 書かれなければならない (MUST)（ の canonical form）。[=Originator=] はレコードを v=op1 の形にしなければならない (MUST)。すなわち、ここで 定義される内容の版だけであって、それ以上は何も無い。このレコードが 述べることはすべて、それがそこに在ることによって述べられているからで ある。 が求めるとおり、[=Originator=] は _site._op の下に wildcard のレコードを公開しない。 wildcard はすべての host を一度に許してしまう。

Verifier の規則。 [=Verifier=] は、提示された host そのものから組み立てた名前を問い 合わせなければならず (MUST)、それ以外の名前は問い合わせない。 [=Verifier=] は、record set が v=op1 という 一つの character-string から成る TXT レコードを持つ場合に限り、 その host を許されたものとして扱わなければならない (MUST)。そのような レコードを持たない record set、たとえば zone の他の場所にある wildcard から合成されたものは、不在として読まれる。 [=Verifier=] は、[=Use Case Specification=] が検査せよと言う host についてのみ、このレコードを参照する（ の 段取り 3）。Secure な不在の証明、Insecure な応答、および 別名を経て到達した応答を、いずれも拒否として扱わなければならない (MUST)。このレコードが参照されるのは、何かがその host を名乗った 場合だけだからである。

レコードを変えるもの。 どちらのレコードも静的である。[=Originator=] の鍵が変わっても、それに 新しい [=Core Profile=] が発行されても、[=Profile Annotation=] が revoke されても変わらない。変わるのは、[=Originator=] が [=Core Profile Issuer=] を変えるとき、issuer を持たないと宣言する とき、host を許すか、その許可をやめるときである。

DNSSEC の要求と名前解決の結果

四つの validation state。 Secure、Insecure、Bogus、Indeterminate と名付けた結果は、 [[RFC4035]] Section 4.3 の security state である。 レコードの存在や不在について本文書が述べることはすべて、DNSSEC の validation state についての言明である。

Verifier が state を確立する手段。 [=Verifier=] はその state を、次の二つの手段のいずれかによって、 自ら決定しなければならない (MUST)。

  • root ゾーンについての自らの DNSSEC の trust anchor で validate する。
  • 認証された経路で到達し、その結果を信頼できる validating resolver に依拠する。

[=Verifier=] は、応答が validate されたという認証 されていない指示に依拠してはならない (MUST NOT)。二つの手段の どちらも持たない [=Verifier=] は、本文書の手続きを実行できない。 [=Verifier=] が応答の validation state をどう確立するかは、 [=Use Case Specification=] が問い合わせさせる名前においても同じである。 そのような名前でその state が何を意味するかは、その仕様が定める。

依拠できる validating resolver を持たない [=Verifier=] も、自らの DNSSEC の trust anchor で validate することはできる。本節はそれを認めている。 そのような [=Verifiers=] がそれを実際に行えるようにする方法を、 validate に要る DNSSEC のデータをどう得るかを含めて検討しており、 後の版でその 1 つを記述するかもしれない。本節の要件は変わらない。

resolver に依拠する Verifier。 resolver から state を得る [=Verifier=] は、その resolver が validate していることの 保証を、設定または試験によって持たなければならない (MUST)。validate しない resolver からの応答は validation state を持たず、Insecure と して読んではならない (MUST NOT)。

別名。 本文書が定義する名前 () において、 [=Verifier=] はレコードを、問い合わせた名前においてのみ用いなければ ならず (MUST)、別名を辿ってはならない (MUST NOT)。この規則は、 [=Use Case Specification=] が [=Verifier=] に問い合わせさせる名前には 適用しない。

別名を経て到達した応答。 CNAME または DNAME の レコードが問い合わせを転送した ために record set が別の owner 名に属している応答は、そのレコードが 公開されたものか wildcard から合成されたものかを問わず、issuer が 公開するすべてのレコードについて、その validation state が何であれ 失敗である。[=Originator=] のレコード () については、そのような応答は Insecure な応答と同じように読まれる。ただし、その validation state が Bogus または Indeterminate である場合は、結果の表の最後の行が当てはまる。別名の先で見つかった レコードが用いられることは決してない。問い合わせた名前について wildcard から合成された応答は、他の応答と区別されない。

ローカルな段取りと DNS の段取りの順序

段取りの三つの群。 の段取りには、何が何に依存するかによって 番号が付いているのであって、実行の順序によってではない。段取りは 3 つの群に分かれる。[=Verifier=] がローカルに行うこと、DNS に問う こと、そして最後に導く判断である。

問い合わせの前のローカルな検証。 [=Verifier=] は、[=Originator Profile Bundle=] の文書から取った名前について、その文書の 署名を、自らが受け入れる [=Root Core Profile=] で終わる [=Accreditation Chain=] を通じて検証し終えるまでは、DNS の問い合わせを 発してはならない (MUST NOT)。[=Verifier=] は、さらに、DNS の 問い合わせを発する前に、[=Core Profile=] から選んだ鍵で [=Content Attestation=] の署名を検証すべきである (SHOULD) （ の段取り 7）。

[=Originator Profile Bundle=] の中のどの署名も、 [=Content Attestation=] の署名も、検証のために DNS を必要と しない。各 issuer の鍵はその issuer の [=Core Profile=] で届く。 DNS に問うのは、既に署名を検証した鍵が今なお現行のものかどうか、 および [=Core Profile=] や annotation が今なお有効かどうかだけである。

[=Content Attestation=] の検査はローカルで済む。それは、本物でない [=Content Attestation=] が、その横の [=Core Profile=] と [=Accreditation Chains=] が本物である場合でも、たとえばそれらが別の [=Originator Profile Bundle=] から写されたものである場合でも、 問い合わせを一つも引き起こさないようにする。

並行する問い合わせ。 [=Verifier=] は、検証し終えた文書から導かれる問い合わせを並行して 発してよい (MAY)。それらは互いに依存しない。 [=Presented Identity=] そのものは [=Originator Profile Bundle=] からではなく配送チャネルから来るが、 の名前は、[=Core Profile=] が運ぶ [=Identity=] から組み立てられる。したがってそれらへの問い合わせは、他のすべての問い合わせと 同じく、[=Core Profile Issuer=] の chain と、[=Core Profile=] の 署名の検証を待つ。段取り 3 の比較は問い合わせを要しないので、すぐに 行ってよい。

  • 存在と不在の検査がどれだけ新しいか。

Verifier が報告すること。 [=Verifier=] は、結論を渡すどの場面においても、次のとおりにする。

名前解決の失敗と pinning の downgrade

は、Bogus な応答、 Indeterminate の結果、 SERVFAIL、タイムアウト、その他の使える応答が得られないことを、 どの名前においても検証の失敗として読み、決して不在としては読まない。 その理由は [=Issuer Pinning Record=] にある。

[=Verifier=] が _op.<originator> への問い合わせの失敗を、 レコードが不在であるかのように扱ったとする。すると、pin された issuer 以外の [=Core Profile Issuer=] からその [=Originator=] の [=Core Profile=] を得ている攻撃者は、その一つの問い合わせの名前解決 を妨げるだけで、pin された [=Originator=] を pin されていないように 見せられてしまう。pinning は何も守らないことになる。 不在が何も revoke されていないことを意味する [=Revocation Record=] においては、同じ規則が、攻撃者が問い合わせを 塞ぐことで revocation を隠すことを防ぐ。他の名前では不在が既に失敗を 意味するので、失敗を同じに扱っても失うものは無い。

pin されていない道へ進む結果は二つだけである。当該レコードが存在 しないことの Secure な証明、すなわちそこには何も無いという DNSSEC に 裏づけられた言明と、Insecure な応答、すなわち署名されていない zone の 状態である。別名を経て到達した応答は後者として読まれる。どちらも、 SERVFAIL のような、名前解決を妨げることで 生じる種類の失敗ではない。とはいえ Insecure な応答が Secure なものと 同じ重みを与えられることは決してない。だからこそ [=Originator=] の レコードは、その zone が署名されている場合にのみ効力を持つ ()。

issuer が公開するレコードは、より厳しく読まれる。そのどれにおいても Insecure な応答は失敗である ()。不在が普通の応答で ある [=Revocation Record Name=] においても同じである。経路上の攻撃者 は、署名された zone に Insecure と答えさせることはできない。そうした 名前で Insecure な応答を生むのは issuer の側の誤りであり、たとえば 自らのレコードを収める zone () を、署名 せずに委譲することである。

そこで Insecure を不在として読むなら、その 誤りはその下のすべての revocation を黙って無かったことにしてしまう。 失敗として読めば、誤りは見える。これは、内容を解析できない [=Revocation Record=] を revocation として数えるのと同じ原則である ()。代償として、issuer は自らの レコードを、[=Revocation Record=] も含めて、自らが署名しない zone に 公開できない。したがって事実上、issuer が公開するすべての zone が 署名されていなければならない。

とはいえ Secure な不在の証明は、何も偽造しない攻撃者によっても 差し出されうる。[=Issuer Pinning Record=] が存在しないことの証明で、 [=Originator=] がそれを公開する前に作られたものは、その中の署名が 失効するまで有効であり、[=Verifier=] と権威サーバの間の経路上に いる攻撃者は、その期間内にそれを replay できる。すると [=Verifier=] は pin されていない [=Originator=] の場合と同じく進み、 [=Issuer Pinning Record=] が名指さない issuer からの [=Core Profile=] が受け入れられる。

Revocation の遅れと replay の窓

この枠組みにおける revocation は即座ではなく、その遅れは、revoke する 当事者がしばしば設定できないパラメータによって抑えられる ()。そこから 3 つの窓が生じる。

  • 検知の遅れ。鍵の取り下げ、[=Core Profile=] の revoke、登録の終わりが 見えるのは、 [=Originator Key Record=] や [=Issuer Key Record=] についてキャッシュされた 肯定応答が期限切れになるときであり、すなわちその time to live の 内側である。[=Profile Annotation=] の revocation が見えるのは、 [=Revocation Record=] が存在しなかったというキャッシュされた証明が 期限切れになるときであり、すなわち [=Profile Annotation Issuer=] の zone の negative caching の期間の 内側である。

    この期間は、issuer ではなく zone の DNS プロバイダが 設定するのが普通であり、1 日の単位になることもある。これまでに 定義されたユースケースが必要とする revocation は、分の単位ではなく 日の単位であるため、本仕様はこれを受け入れている。自らの zone の negative caching のパラメータを設定できる issuer、あるいは自らの Revocation Record node をそれができる zone に委譲する issuer は、この 遅れを短くできる。それ以上を必要とするユースケースは、本仕様のこの 部分をやり直さなければならない。

  • Replay。[=Verifier=] と権威サーバの間の経路上に いる攻撃者は、署名された時点では真であった応答を replay できる。 その後に取り除かれた record set や、[=Revocation Record=] が公開 される前に作られた不在の証明である。その窓は当該 zone の RRSIG の有効期間であり、プロバイダはこれを日や週の単位に設定するのが普通 である。その内側では、攻撃者が到達できる [=Verifier=] から revocation を隠せる。この攻撃には経路上の位置が要り、その効果は 署名とともに終わる。
  • 古い応答。権威サーバに到達できない間、古いデータ を提供する resolver [[?RFC8767]] は、取り除かれた record set を その time to live を超えて生かし続けうる。これを突くには issuer の サーバを到達不能にする必要があるので、それらのサーバの可用性は、 issuer が与える revocation の保証の一部である。

上の 3 つの窓の前に、当事者が動くまでの時間もかかる。compromise を 知った issuer は、いずれの窓が動き出すよりも前に、その変更を公開 しなければならず、本文書はその時間を何も抑えていない。[=Verifier=] に対する キャッシュの上限 () は、これらの窓を zone の パラメータが許すかぎり短く保つためのものである。文書や応答をそれ より長く保持する [=Verifier=] は、自らの遅れをそこに加えることに なる。

鍵の compromise

[=Originator=] の鍵。[=Originator Verification Key=] に対応する [=Signing Key=] を握る攻撃者は、その鍵が現行のものでなくなるまで、 [=Originator=] の名前で [=Content Attestations=] に署名できる。 [=Core Profile Issuer=] は、その鍵を列挙するすべての [=Originator Key Record=] からその鍵のレコードを取り除くことでそれを 終わらせる。ただし上記の検知の遅れを伴う。 が本来求める保持は、compromise された 鍵には適用されず、issuer は、その鍵で署名されたコンテンツが検証され なくなることを受け入れる。

[=Originator=] 自身にも、[=Core Profile Issuer=] を通さない 手段が一つある。自らの zone で [=Originator Profile=] を持たないと 宣言することである ()。これは粗い 手段である。すべてを止めてしまうからであり、また、zone が署名されて いる [=Originator=] にしか使えず、[=Verifier=] がそのレコードを参照 するユースケースでしか使えない。それを持たない [=Originator=] は、 自らの [=Core Profile Issuer=] がどれだけ速く動くかに依存する。それは 本文書が定めないサービス水準である。この非対称性は本質的である。 issuer は署名の有効期間の終わりを自らの署名の内側に書き込むので、 [=Originator=] はそれを延ばすことができず、短く切り上げること しかできない。

置き換えた鍵を残すこと。鍵を入れ替える [=Originator=] は、置き換えた鍵を [=retired=]（退役した）鍵として保つか、 その [=Core Profile Issuer=] に取り下げてもらうかを選ばなければならない。保つ場合、その鍵のレコードは、その鍵を保持 する各 [=Core Profile=] の [=Originator Key Record=] に、その [=Core Profile=] が期限切れになるか revoke されるまで残る ()。取り下げる場合、そのレコードを すべての [=Originator Key Record=] からただちに取り除く。この選択は、ある性質を別の性質と 引き換えにするものである。保てば、その [=Core Profile=] が続く間、 その鍵で既に署名された [=Content Attestation=] がすべて検証可能な ままになる。取り下げれば、その鍵の compromise が使われうる窓が 閉じる。

この窓は時とともに狭まらない。[=Content Attestation=] がいつ署名されたかについて、[=Verifier=] は信頼できる説明を持たない からである。attestation が保持する唯一の時刻は、その署名者が書いた ものであり、 はまさにその理由でそれを判断から 除いている。したがって、なお現行である鍵の [=Signing Key=] を握る 攻撃者は、古く見える attestation を作れる。そして枠組みの中に、それを、 その鍵が残された目的である本物の古いコンテンツと区別するものは無い。 よって、compromise されたと考えられる鍵は、どのコンテンツが検証され なくなろうと、ただちに [=withdrawn=]（取り下げられる）となる。

置き換えた鍵の二つの扱い方、 すなわち退役させるか、新しい鍵でコンテンツに署名し直して置き換えた鍵を 取り下げるかのどちらがユースケースに合うかは、配送された後にコンテンツ に署名し直せるかどうかによる。どちらを推奨するかは [=Use Case Specification=] が述べる事柄である。

issuer の鍵。issuer の [=Issuer Key Record=] にある鍵の compromise は、その鍵が署名したすべての文書に及ぶ。 [=Core Profile Issuer=] であればそのすべての [=Core Profile=] （[=Root Issuer=] が発行したものを含む）に、 [=Profile Annotation Issuer=] であればそのすべての [=Profile Annotation=] に及ぶ。[=Root Issuer=] または [=Accreditation Body=] であれば、その鍵で署名したすべての [=Issuer Accreditation=]、したがってそれらを通るすべての [=Accreditation Chain=] にも及ぶ。これを封じ込める手段は、 X.509 における中間認証局の compromise に対するものと同じ形をしており、 3 つある。

  1. 当該 issuer が、自らの [=Issuer Key Record=] からその鍵を取り除く。 それで署名されたすべての署名は、その record set の time to live の 内側で の検査を通らなくなる。
  2. 侵害された issuer の [=Issuer Accreditation=] を発行した issuer、 すなわちその [=parent issuer=] が、その accreditation の [=Revocation Record=] を公開する。 その issuer を通るすべての [=Accreditation Chain=] が通らなくなる。 が chain の最後の段だけでなく 各段の revocation を検査するのはこのためである。その検査が無ければ、 この手段は効力を持たない。
  3. 当該 issuer が、影響を受けるすべての文書を新しい鍵で発行し直し、 新しい文書が、[=Use Case Specification=] の定めるところにより [=Verifiers=] に届く。

初めの二つは DNS のキャッシュの時間の内側で効力を持つ。三つめは 再配布にかかる時間だけかかり、それが完了するまで、影響を受けた [=Originators=] は検証され得ない。issuer がどの期限までに動くか、 何を報告しなければならないかは、この枠組みのガバナンスの事柄であり、 ここには述べない。

[=Root Core Profile=]。[=Root Issuer=] には [=parent issuer=] が無く、したがってその [=Root Core Profile=] には revoke されうる accreditation も無い。その compromise は、[=Verifiers=] が 受け入れる集合からそれを取り除くことで扱われる。取り除きは、検証 ソフトウェアが配布され更新される経路を通じて行われ、それは [=Root Core Profile=] が届いた経路でもある ()。これは、DNSSEC が自らの root trust anchor に与える扱いであり、X.509 の root store が compromise された root に与える扱いでもある。

[=Issuer Key Record=] からの鍵の除去は [=Root Core Profile=] にも当てはまる。その [=Root Issuer=] も、他の issuer と 同じく [=Issuer Key Record=] を公開するからである。compromise された鍵を そのレコードから取り除けば、その鍵で署名されたすべての文書が DNS のキャッシュの時間の内側で通らなくなる。 その間に、[=Root Core Profile=] の置き換えが、検証ソフトウェアが配布される 経路を通じて進む。

Pinning が何を守るか、そしてなぜ任意なのか

発行すべきでない [=Identity=] に対して [=Core Profile=] を発行した [=Core Profile Issuer=] は、誤りによるのであれ、欺かれたのであれ、 compromise されたのであれ、その保持者に検証される profile を与えて しまう。[=Issuer Pinning Record=] は、[=Originator=] が、自分に対して発行して よい issuer はどれかを述べることを可能にする。これにより、他の issuer からの profile は で 通らなくなる。またこれは、[=Originator=] が自らの条件で issuer を 変えることを可能にし、否定の形では、[=Core Profile Issuer=] の助けなしに自らの profile を止めることを可能にする。本文書は、これらのいずれも [=Originator=] に求めていない。レコードが不在であれば、 [=Verifier=] は pin されていない道を進む。

それが任意でありうる理由は、これまでに定義されたユースケースでは、 コンテンツが、[=Core Profile Issuer=] の制御しない要素によって その [=Originator=] に結びつけられているからである。 [=Presented Identity=] は配送チャネルから来るのであり、 [=Use Case Specification=] の結びつけの規則は、 [=Core Profile=] が何かの役に立つより前に、それを [=Core Profile=] の保持する [=Identity=] と照合する。誤って発行された [=Core Profile=] は、そのとき、被害者の identity の下でコンテンツを 提示することもできる攻撃者にしか役立たない。それは二つめの、独立した 破綻である。その要素が各ユースケースにおいて何であるか、それを issuer から独立に保つものが何かは、当該 [=Use Case Specification=] が述べる。

この論理は、照合すべき [=Presented Identity=] が無い場面では成り立た ない。archive から、オフラインで、あるいは添付から読まれるコンテンツ や、manifest のようにコンテンツとともに運ばれる容れ物に入って、 その [=Originator=] 以外の場所から提示されるコンテンツである。 [=Originator Profile Bundle=] と attest されたコンテンツをそのように 運ぶこと自体は問題ではない。署名も DNS の検査 も、他のどこででもそうであるように働く。欠けているのは独立した identity である。そのため、誤って発行された [=Core Profile=] に対する 唯一の守りは issuer の正しさになり、二つめの要素を取り戻すものが pinning である。

したがって、そのような場面についての [=Use Case Specification=] は、[=Issuer Pinning Record=] を求めて二つめの 要素を戻すか、一つだけで済ませるかのいずれかである。後者の場合、 は [=Verifier=] に、結びつけを検査しなかった と報告させる。こうして、欠けているものが結論の中に埋もれるのではなく、 結論とともに運ばれる。pinning の他に、誤った発行に対する手立ては issuer に課される手立てであり、この枠組みのガバナンスに属する。

Originator の zone

この [=Originator=] は、自分に対して発行してよい [=Core Profile Issuers=] を名指す のレコードを公開している。この zone は署名されている。署名されていなければ、このレコードは効力を 持たない。 

; optional: this Originator names one permitted Core Profile Issuer
_op.news-publisher.example.   3600  IN  SVCB  1 cp-issuer.example.

この例に [=Permitted Host Record=] は現れない。コンテンツは [=Identity=] そのものの配下の host の下で提示されているからである。別のドメインの host の下でコンテンツが提示される [=Originator=] であれば、その host について <host>._site._op.news-publisher.example に v=op1 を保持する TXT の record set を公開することに なる ()。

Core Profile Issuer の zone

この zone は、当該 issuer の [=Issuer Key Record=] と、それとは別の 名前でこの [=Originator=] の [=Core Profile=] の [=Originator Key Record=] を保持する。OPKEY レコードのフィールド、およびその中で [=Key Identifier=] が保持される 形式は [[OPF-DNS]] が定義する。TLSA の record set は の移行期の形式であり、 type value が割り当てられるまでの間だけ公開される。 

; the Issuer Key Record: the key with which this issuer signs
_issuer-key._op.cp-issuer.example.   3600  IN  OPKEY  3 1 1 ( c9d1...cip-key-spki-sha256...02 )
_issuer-key._op.cp-issuer.example.   3600  IN  TLSA   3 1 1 ( c9d1...cip-key-spki-sha256...02 )   ; transitional

; the Originator Key Record of the Core Profile of news-publisher.example, one record per current key
; (the leftmost label, a UUID, is the record label)
7f3e1c2a-9b4d-4e8f-a1c5-2d6b8e0f4a91._originator-key._op.cp-issuer.example.   3600  IN  OPKEY  3 1 1 ( 1f3a...key1-spki-sha256...9c )
7f3e1c2a-9b4d-4e8f-a1c5-2d6b8e0f4a91._originator-key._op.cp-issuer.example.   3600  IN  TLSA   3 1 1 ( 1f3a...key1-spki-sha256...9c )   ; transitional

[=record label=] 7f3e1c2a-9b4d-4e8f-a1c5-2d6b8e0f4a91 は 不透明であり、issuer が選んだものである。 [=Verifier=] は名前の全体を [=Core Profile=] から取り、それが _originator-key._op.cp-issuer.example の配下にあることだけを 検査する ()。レコードを複数の zone に 分ける issuer は両者の間に label を挟むので、同じレコードが代わりに 7f3e1c2a-9b4d-4e8f-a1c5-2d6b8e0f4a91.7f._originator-key._op.cp-issuer.example に置かれることもありうる。[=Verifier=] はどちらの場合も同じことを する。

Profile Annotation Issuer の zone

各 [=Profile Annotation Issuer=] は、[=Core Profile Issuer=] と同じ 種類の名前で自らの [=Issuer Key Record=] を公開する。 _revocation の下にレコードを持つのは revoke された annotation だけなので、何も revoke していない issuer の zone には そのレコードが無い。 

; press-assoc.example: nothing revoked, so no record below _revocation
_issuer-key._op.press-assoc.example.   3600  IN  OPKEY  3 1 1 ( 55ae...pa1-key-spki-sha256...71 )

; factcheck.example: one annotation revoked before its expiry (record label 3a9f6d1e-...-e6d7)
_issuer-key._op.factcheck.example.     3600  IN  OPKEY  3 1 1 ( 8c40...pa2-key-spki-sha256...d3 )
3a9f6d1e-5c2b-4a7e-9e0d-b4f1c8a2e6d7._revocation._op.factcheck.example.   600  IN  TXT  "v=op1; revoked=2026-11-15T09:30:00Z"

このレコードの内容は が定義する 形式である。すなわち版と revocation の時刻である。[=Verifier=] は record set の存在だけで判断するので、上の値は手続きの何も変えない。 それがそこにあるのは、zone を読む運用者のためであり、その時刻を 必要としうる後の用途のためである。

段取り問い合わせここでの結果
1 入力を取る 無し [=Originator Profile Bundle=] と [=Content Attestation=] は手元にあり、[=Presented Identity=] は、 コンテンツが提示された host、すなわち www.news-publisher.example である
2 chain をローカルに検証する 無し 三つの chain はいずれも、[=Verifier=] が受け入れる [=Root Core Profile=] まで検証される。これが成功するまで、文書が 保持するどの名前についても問い合わせは発しない
3 identity を結びつける この例では問い合わせ無し host が [=Core Profile=] の保持する [=Identity=] の配下に あるので、[=Use Case Specification=] の規則は問い合わせなしに 満たされる。別のドメインの host であれば <host>._site._op.news-publisher.example で検査 される
4 [=Issuer Pinning Record=] を参照する _op.news-publisher.example SVCB ServiceMode の Secure な応答であり、その TargetName cp-issuer.example は [=Core Profile=] の issuer である。この [=Originator=] は pin されている。 Secure な不在の証明、または Insecure な応答であれば pin されて いないことになり、検証は続く。名前解決の失敗であれば検証は 終わる
5 [=Core Profile=] を検査する _issuer-key._op.cp-issuer.example OPKEY 署名は、当該 issuer 自身の [=Core Profile=] が保持する鍵で 検証され、[=Core Profile=] は署名の有効期間の内側にあり、その鍵の [=Key Identifier=] c9d1…02 は [=Issuer Key Record=] にある
6 [=Originator Key Record=] を検査する 7f3e1c2a-…-4a91._originator-key._op.cp-issuer.example OPKEY この名前は当該 issuer の Originator Key Record node の配下にあり、 record set は存在して 1f3a…9c を保持している。その [=Core Profile=] は revoke されておらず、その鍵は現行のもので ある
7 [=Content Attestation=] を検証する 無し attestation が名指す [=Key Identifier=] 1f3a…9c の [=Core Profile=] の鍵で署名が 検証され、その [=Key Identifier=] は [=Originator Key Record=] に ある
8 各 [=Profile Annotation=] を検査する _issuer-key._op.press-assoc.example OPKEY と b2c4e8a0-…-0a94._revocation._op.press-assoc.example TXT。_issuer-key._op.factcheck.example OPKEY と 3a9f6d1e-…-e6d7._revocation._op.factcheck.example TXT どちらの annotation も [=Core Profile=] の保持する [=Identity=] を名指し、どちらの署名も検証され、それらに署名した鍵はそれぞれの issuer の [=Issuer Key Records=] にあり、どちらも署名の有効期間の内側に ある。_revocation の下の一つめの名前は Secure な 不在の証明を返すので、その annotation は有効である。二つめは record set を返すので、その annotation は有効でない。どちらも 検証を失敗させない
9 結論を導く 無し [=Content Attestation=] は検証された。対象は [=Originator=] news-publisher.example であり、それは pin されていた。press-assoc.example の annotation は有効であり、factcheck.example のそれは有効で ない。検査の新しさは上記の応答のそれである

三つの [=Accreditation Chains=] のための問い合わせを別にすると、この 検証が発する問い合わせは、 の note のとおりに数えて 7 つである。[=Issuer Pinning Record=] に 1 つ、[=Core Profile Issuer=] に 2 つ、各 [=Profile Annotation Issuer=] に 1 つずつ、各 [=Profile Annotation=] に 1 つずつである。[=Permitted Host Record=] を参照する場合は、さらに 1 つ加わる。段取り 5 の問い合わせは [=Core Profile Issuer=] についての段取り 2 の後に続く。段取り 4 と 6 の問い合わせは、それに加えて [=Core Profile=] の署名の検証の後に、 段取り 8 の問い合わせは各 annotation の署名の検証の後に続く。それらの 署名を検証し終えたら、問い合わせは互いを待たず、まとめて発してよい。 段取り 7 は問い合わせを発さず、この例では段取り 3 も発しない ()。
