はじめに

Originator Profile Framework は、コンテンツの [=Recipient=] が、 [=Originator=] 自身が提示するデータから、そのコンテンツの [=Originator=] が誰であるか、およびその [=Originator=] について第三者が 何を validate したかを知ることを可能にする。Architectural Overview [[OPF-AOV]] は、一般のモデルを 述べている。Core Specification [[OPF-CORE]] はすべての use case が 共有するフレームワークの部分を定め、コンテンツをどう届けるかに依る部分は、 届け方ごとの [=Use Case Specification=] に委ねている。本文書は、 電子メールについての [=Use Case Specification=] である。

このユースケースの設計は、概略としては次の四つからなる。

  • メッセージは S/MIME で署名され、[=Originator Profile Bundle=] （プロファイルを運ぶ単一の MIME パート）が、その署名が覆う内容の 一部として運ばれる。この枠組みは署名そのものには関与しない。 メッセージの署名に用いられた鍵の上に、その鍵を [=Originator=] の [=Identity=] に結びつける [=Core Profile=] を置き、そのプロファイルの 上に、第三者が [=Originator=] について確かめた [=Validated Attributes=] を運ぶ [=Profile Annotations=] を置く。
  • DNS は Core Specification [[OPF-CORE]] が与える役割、すなわち 現行性と失効の役割を果たす。このユースケースでは [=Sending Domain=] の zone が DNSSEC で署名されていることを要求するので、[=Originator=] が 自身の zone に公開するレコードは [=Verifier=]（Recipient に代わって Originator Profile を検証するソフトウェアの構成要素）に常に authenticated data として届く。Core Specification はこれを求めていない。
  • 検証は [=Mail Client=]（メールクライアント）が行う。Mail Client はメッセージの DKIM 署名から DMARC [[RFC9989]] を自身で評価し、 [=Originator Profile=] を検証する。[=Receiving Mail Server=]（受信側 メールサーバ）が DMARC を評価することは前提にできない。評価して 失敗を記録している場合、[=Mail Client=] はそれを尊重する。
  • 有効性を判断する時点は、表示の時点か、Mail Client 自身が記録した受信の 時点である。メッセージの S/MIME の検証は、signer の certificate path の validation を含め、S/MIME 実装のものであってこの枠組みの外にある。 この枠組みが加えるのは、signer の鍵が [=Originator=] の鍵の一つで あることの検査と、その鍵を通じた [=Originator Profile=]、すなわち [=Recipient=] に示される [=Identity=] と [=Validated Attributes=] で ある。

メッセージの構造

署名

Originator が何に、どの鍵で署名するか。本仕様の下でメッセージの中に [=Originator Profile=] を提示する [=Originator=] は、そのメッセージを S/MIME [[RFC8551]] で署名し なければならない（MUST）。また [=Originator Profile Bundle=] を、メッセージが 添付を運ぶ形で、すなわち multipart のエンティティの body part として、 署名が覆う内容の中に置かなければならない（MUST）。[=Originator=] は、 そのメッセージが運ぶ [=Core Profile=] の [=Originator Verification Keys=] の一つでメッセージに署名しなければならない（MUST）。

メッセージの構造。[=Originator=] は、メッセージに次の構造を与えなければならない （MUST）。この構造を満たす形は、後に挙げるものがすべてである。

  • メッセージの最上位の body は S/MIME の署名であるか、メッセージが 暗号化されている場合は、復号した内容がその署名である暗号化の層で ある。
  • 署名は S/MIME の署名データの二つの形のいずれかをとる。一つは smime-type が signed-data の application/pkcs7-mime の body で、CMS SignedData [[RFC5652]] が署名された内容を内包する。もう一つは multipart/signed の body [[RFC1847]] で、最初の body part が署名された内容、2 番目がそれに対する分離された CMS SignedData を運ぶ。
  • 署名された内容は、メッセージの body も収める multipart/mixed のエンティティであり、[=Originator Profile Bundle=] はその multipart/mixed のエンティティの 直下の body part である。

署名が application/pkcs7-mime の body である場合、 [=Originator=] はその body に、[[RFC8551]] では任意とされる smime-type parameter を値 signed-data で付けなければ ならない（MUST）。

構造を満たす形。これらの要件を満たすメッセージの形は次のとおりであり、これに限る。

  • multipart/signed の body で、その最初の body part、 すなわち署名された内容が、メッセージの body と [=Originator Profile Bundle=] を収める multipart/mixed のエンティティである もの。
  • smime-type が signed-data の application/pkcs7-mime の body で、その SignedData が、 メッセージの body と [=Originator Profile Bundle=] を収める multipart/mixed のエンティティを内包するもの。
  • 最初の二つの形のいずれかを、暗号化の層、すなわち smime-type が enveloped-data または authEnveloped-data の application/pkcs7-mime の body [[RFC8551]] が包む もの。メッセージは署名されてから暗号化される。このようなメッセージ は、それを復号する [=Mail Client=] だけが検証できる。
  • 三つの形のいずれかで、メッセージの body 自体が multipart/alternative や multipart/related のような multipart のエンティティであるもの。そのときそのエンティティと [=Originator Profile Bundle=] はどちらも、署名された multipart/mixed のエンティティの直下の body part であり、bundle は body のエンティティ の中には無い。
メッセージの body を保護し、それとともに bundle が存在することと その内容とを保護する S/MIME の署名は、この bundle がこの署名者によって このメッセージに添えられたことを主張する。bundle の中の文書に対する 各 issuer の署名は、その文書が名指す当事者または鍵を、その issuer が endorse したことを主張する。後者は前者から独立しているので、署名鍵を 運ぶ [=Core Profile=] がその鍵で作られた署名に覆われているという 事実は、循環を生まない。bundle を署名の外に置けば、差し替えに対して 無防備になり、endorsement の integrity が壊れる。

Verifier が用いる署名と bundle

Verifier がどの bundle を用いるか。[=Verifier=] は、署名が覆う内容の中に が要求するとおりに置かれた [=Originator Profile Bundle=] と、それを覆う署名を用いる。 [=Originator Profile Bundle=] のメディアタイプ（）の part がそれ以外の場所（署名された内容の外を 含む）にあれば、それは本仕様にいう [=Originator Profile Bundle=] では なく、検証に用いられない。そのメディアタイプの part をそのような場所に しか持たないメッセージは、署名された内容が [=Originator Profile Bundle=] を運ばないメッセージである （ の手順 1）。

smime-type parameter。[=Verifier=] は、 application/pkcs7-mime の body の形をその smime-type parameter だけから判断し、body が運ぶ CMS の内容からは判断しない。 smime-type parameter が無いか、signed-data 以外の値で ある body は、本仕様が受け入れる形の署名ではない。

どの署名か、その SignerInfo。本仕様がいう署名とは、 が要求するとおりに置かれた [=Originator Profile Bundle=] を、署名された内容の直下に収める SignedData である。その SignerInfo のうち、bundle の中の [=Core Profile=] の [=Originator Verification Key=] を鍵とする certificate を指すものは、アルゴリズムが何であれ、同じ署名者、 すなわち [=Originator=] の署名である。アルゴリズムの移行期のように、 一つの [=Core Profile=] は複数のアルゴリズムの鍵を持つことができ、 それらの鍵はどれも同じ [=Originator=] として署名する。 の鍵の照合は、 それが少なくとも一つあれば満たされる。

その SignedData が複数の SignerInfo を持つ場合、[=Verifier=] はそれらを 次のように扱う。

  • [[RFC5652]] が一つの署名者の署名を扱うのと同じく、[=Originator=] の 署名は、[=Originator=] の SignerInfo のうち一つが [=Verifier=] の 対応するアルゴリズムで通れば通る（手順 1）。[=Verifier=] が対応 しないアルゴリズムのものは、それだけでは失敗にならない。
  • どの [=Core Profile=] にも鍵が無い SignerInfo は、その署名が通らない 場合を含め、それだけでは失敗にならない。
  • [=Verifier=] は、ほかの SignerInfo が [=Originator=] とは別の [=Identity=] の [=Core Profile=] の [=Originator Verification Key=] を 鍵とする certificate を指していれば、検証を失敗させなければならない （MUST）。複数の [=Identity=] の [=Core Profiles=] が、[=Originator=] を決める条件（）を満たす場合と ちょうど同じく失敗する。
中継するものに署名する gateway のように、経路上の当事者は自身の鍵で SignerInfo を足すことができる。その鍵はどの [=Core Profile=] にも無く、 そのような SignerInfo が失敗の原因になるなら、そうした当事者の誰もが メッセージを失敗させられることになる。これに対し、別の [=Identity=] の [=Core Profile=] に鍵がある SignerInfo は、メッセージに第二の [=Identity=] の署名を置くものであり、手順は、複数の [=Identity=] の [=Core Profiles=] が運ぶ鍵を失敗させるのと同じように、選ばずにそれを 失敗させる。

Originator Profile Bundle

bundle が運ぶもの。[=Originator=] は、自身の [=Originator Profile Bundle=] に、Core Specification が [=Originator Profile Bundle=] の運ぶものとして定める 文書を含めなければならない（MUST）（[[OPF-CORE]], Originator Profile Bundle）。これらの文書の それぞれの形式は Core Specification [[OPF-CORE]] が定める。

chain の全体がメッセージとともに運ばれる。[=Originator=] は、各 [=Accreditation Chain=] の全体を [=Originator Profile Bundle=] で運ばなければならない（MUST）。[=Verifier=] は [=Originator Profile=] の いかなる部分もネットワークから取得することを要求されず、 [=Core Profile Issuer=] とすべての [=Profile Annotation Issuer=] は bundle から見つける。これによって [=Verifier=] は、Core Specification が求めるとおり、DNS の問い合わせを 発する前に各 chain を手元に持つ（[[OPF-CORE]], Originator Profile Bundle）。

media type を付けた一つの part。[=Originator=] は、[=Originator Profile Bundle=] に、そのために登録 された media type を付けなければならない（MUST）。 を参照。[=Originator=] は、署名された内容にその media type の part を 二つ以上置いてはならない（MUST NOT）。囲まれた message/rfc822 の body の中の part は、囲まれた メッセージに属し、数えない。複数を見つけた [=Verifier=] は、その中から 選ばず、検証を失敗させなければならない（MUST）。署名された内容が一つも 運ばないメッセージは評価しない （ の手順 1）。

[=Originator Profile Bundle=] の media type はまだ登録されておらず、 その登録は Originator Profile Blueprints [[?Originator Profile Blueprints]] における対応する作業と揃える こととしている。登録されるまで、本仕様は相互運用可能な形では実装 できない。

署名者の certificate

Verifier が照合する鍵。[=Verifier=] は、S/MIME 実装が署名の検証に用いた certificate の SubjectPublicKeyInfo [[RFC5280]] を、[=Key Identifier=] の導出元の鍵に ついて Core Specification [[OPF-CORE]] が要求するとおりに正規化した うえで、そこから [=Key Identifier=] を導出しなければならない（MUST）。 [=Verifier=] は、その [=Key Identifier=] を [=Core Profile=] の [=Originator Verification Keys=] の [=Key Identifiers=] と照合しなければ ならない（MUST）。S/MIME 実装が署名を受け入れないメッセージは、検証に 失敗する（ の手順 1）。

S/MIME は署名者の公開鍵を X.509 certificate で運ぶ。S/MIME 実装は、 [[RFC8551]] と [[RFC5280]] が要求するとおりに、署名を検証し certificate path を validate する。本仕様はそれらの規則を述べ直すことも 緩めることもしない。certificate とその path の certificate を SignedData の中に入れて運ぶか、他の方法で得るかは、S/MIME の署名者の事柄であって、 本仕様の事柄ではない。本仕様が加えるのは、この節の鍵の検査である。 それはメッセージを、certificate だけにではなく、その [=Profile Annotations=] の運ぶ [=Validated Attributes=] とともに [=Originator Profile=] に結びつける。鍵を 正規化するのは、同じ鍵がここでも [=Core Profile=] におけるのと同じ 識別子を与えるようにするためである。

certificate は Originator Profile の外にある。certificate を [=Core Profile=] に入れてはならない（MUST NOT）。 [=Core Profile=] が運ぶのは鍵であって certificate ではなく、署名者の certificate は [=Originator Profile=] の一部ではない。[=Verifier=] は、 署名者の certificate の certificate path を、[=Originator Profile=] の 一部として扱ってはならない（MUST NOT）。

certificate の有効期間と、CRL または OCSP によるその失効は、S/MIME の 層に属し、この枠組みの外にある。2 つの層を結ぶ唯一のものは鍵の同一性で ある。 を参照。

ヘッダフィールド

DKIM の h= タグの外のヘッダフィールドはここでは保護されない。本仕様は、S/MIME が与える以上のヘッダフィールドの保護を要求しない。 ただし、 が DKIM 署名の h= タグに求める範囲は除く。本仕様が照合する identity は [=Sending Domain=] であり、メッセージをそのドメインに結びつけるのは DMARC [[RFC9989]] の仕事であって、S/MIME の署名の仕事ではない。S/MIME の実務は S/MIME の署名の中でヘッダフィールドを保護することを勧めるが、 本仕様はそれを求めない。

後方互換性

本仕様を実装していないメールクライアント（したがって本文書の意味での [=Mail Client=] ではないもの）は、 [=Originator Profile Bundle=] を未知の型の添付として扱い、無視する。 bundle は署名された内容の通常の一部であるから、S/MIME の署名は それでも検証される。したがって、配備はクライアントごとに一つずつ 進められる。

したがって [=Originator=] は、受信者が検証できるようになる前から 本仕様の下でメッセージを送ることができる。メッセージは、受信側が検証 できるところでは検証される。受信側では、検証は当初、既存のメールクライアントへの プラグインとして、あるいは検証を組み込んで配布されるメールクライアント として届くと見込まれる。

送信ドメインと DNS に対する要求

本仕様は、この枠組みの DNS 設計にリソースレコードも名前も加えない。 名前、レコード型および形式は Core Specification [[OPF-CORE]] と [[?OPF-DNS]] が定める。本仕様が定めるのは、それらのレコードのうち どれを [=Originator=] が公開することを要求されるか、および それらが無いことが何を意味するかである。

関わる zone は二つあり、以下では 区別する。署名されていることを要求される [=Sending Domain=] の zone と、 [=Issuer Pinning Record=] を持つ [=Originator=] の [=Identity=] の zone で ある（）。[=Sending Domain=] はその [=Identity=] であるかその下にある（）ので、 二つは同じ zone であるか、前者が後者の下にある。DKIM の鍵と DMARC policy record がどこに公開されるかは別の事柄で、 が定める。[=Verifier=] がメッセージの 整合をどう確かめ、したがってどの [=Sending Domain=] を取るかは、 にある。

本仕様において、DNSSEC の状態は、DNSSEC 自身が検証を行う resolver に ついて定める四つ [[RFC4033]] [[RFC4035]] であり、Core Specification [[OPF-CORE]] が与えるとおりである。

  • Secure: resolver が trust anchor と 応答までの chain of trust を持ち、応答の中のすべての署名を検証できる。
  • Insecure: resolver が trust anchor と chain of trust を持ち、途中のある委任点で DS レコードが無いことの署名 された証明を持つ。そのため、応答の zone は署名されていないことが示される。
  • Bogus: resolver が trust anchor と、 応答が署名されていることを示す安全な委任を持つが、応答が検証に失敗する。
  • Indeterminate: その部分の木が 署名されているかどうかを示す trust anchor が無い。

データが認証されている（authenticated）のは、応答が Secure である場合に 限る。認証された否定（authenticated denial）とは、Secure である存在の 否定であり、Core Specification が Secure proof of absence と呼ぶもので ある。それが証明する不在が、認証された不在（authenticated absence）で ある。

Presented Identity

Presented Identity とは何か。メッセージの内容がその下で提示される identity は [=Sending Domain=]、 すなわち DKIM [[RFC6376]] による DMARC [[RFC9989]] の下での整合が 確立された From ヘッダフィールド [[RFC5322]] のドメインである。これは このユースケースの [=Presented Identity=] であり、[=Originator=] を決めるために、[=Core Profile=] の運ぶ [=Identity=] と比べられる値 である。本節は、メッセージが整合し結び つけられるために [=Originator=] が行うことと、[=Verifier=] が [=Sending Domain=] をどう取るかを定める。

どの Core Profile が Originator のものか。署名は [=Originator=] を名指ししない。[=Originator=] とは、 [=Originator Profile Bundle=] の中の [=Core Profile=] （[=Root Core Profile=] 以外）が二つの条件を満たす当事者である。 すなわち、その [=Core Profile=] が署名者の certificate の鍵を が求めるとおりに照合して運び、 かつその [=Identity=] が、Core Specification [[OPF-CORE]] の規則で 比較して、[=Sending Domain=] そのものであるか [=Sending Domain=] を その配下に持つ。

DKIM による整合。メッセージの中で [=Originator Profile=] を提示する [=Originator=] は、メッセージが DKIM によって DMARC の下で、strict な整合で整合するように、From ヘッダフィールドのドメインと同一の d= のドメインで、 メッセージに DKIM の署名をしなければならない（MUST）。

DNS の名前。[=Originator=] は、次の 2 つの名前が、途中で経由 する CNAME や委任を通じて、レコードがあればレコードとして、無ければ認証された 否定として、authenticated data として解決されるようにしなければならない （MUST）。

  • その署名の DKIM 鍵が公開されている名前
  • From ヘッダフィールドのドメインの DMARC ポリシーレコードの名前

鍵の公開を他者に任せる [=Originator=] は、その他者のゾーンを署名させ なければならない（MUST）。

[=Sending Domain=] のゾーンが署名されていることという の要求は、メールサービスの事業者が 鍵を持つ場合のように、selector やポリシーレコードが他者のゾーンへ alias または委任されている場合には、それだけではこれらの名前を守らない。 strict な整合の下では d= ドメインは From ヘッダフィールドの ドメインなので、別のゾーンの鍵やポリシーレコードは、そのような alias か、その名前の委任によってだけ生じる。

DKIM の署名。[=Originator=] は、DKIM の署名に l= タグ [[RFC6376]] を使ってはならない（MUST NOT）。 [=Originator=] は、DKIM の署名の h= タグに From、To、Cc、 Subject、Date、Reply-To および Message-ID のヘッダフィールドを 挙げなければならない（MUST）。それぞれの名前は、そのフィールドが メッセージにある数より 1 回多く挙げ、存在しないフィールドの名前は 1 回挙げる。 [=Originator=] は、DKIM の selector を受信者ごと、またはメッセージごとに 変えてはならない（MUST NOT）。

l= タグを持つ DKIM の署名は、署名が覆う長さの後ろに 付け足された内容があっても検証に通り、その内容は S/MIME の署名が 保護しない。

h= にヘッダフィールドをこのように挙げるのは oversigning と呼ばれるやり方である。DKIM は、h= に複数回挙げられた ヘッダフィールドの実体を最後のものから上へ順に署名し、存在する実体の 数を超えて挙げた名前は、さらにもう一つの実体が無いことを署名する。 そのため、後からその名前のフィールドが付け加えられると署名が壊れる （[[RFC6376]], Signatures Involving Multiple Instances of a Field; Attacks Involving Extra Header Fields）。変更されずに別の受信者へ replay されたメッセージ（）が変わって いないのは署名が覆う範囲だけである。h= の外のヘッダ フィールドは途中で置き換えられうる。そのように置き換えられた Reply-To は、本仕様の検査がすべて通るまま、受信者の返信を別の宛先へ 向けてしまう。

[=Mail Client=] はその selector の下に公開された鍵を問い合わせる ので、受信者ごと・メッセージごとに違う selector は、その問い合わせに よって、どのメッセージが開かれたかを [=Originator=] に知らせてしまう （）。[=Verifier=] は そのような selector の使い方を検出できない。これは [=Originator=] に 対する要件である。

DMARC のポリシーレコード。[=Originator=] は、From ヘッダフィールドのドメインに、DKIM について strict な整合を求める adkim タグ（adkim=s）を持つ DMARC ポリシー レコード [[RFC9989]] を公開しなければならない（MUST）。そのドメインに レコードがあり整合が strict であれば、[[RFC9989]] の評価は DNS Tree Walk を行わず、[=Verifier=] が DMARC のために問い合わせる名前はすべて From ヘッダフィールドのドメインの下にある。

relaxed な整合は組織ドメインに拠る。組織ドメインを [[RFC9989]] は DNS Tree Walk で決め、[[?RFC7489]] は公開接尾辞の一覧で決めていた。一方に 従う verifier は、他方に従う verifier と異なる結果に至りうる （[[RFC9989]], Changes from RFC 7489）。strict な整合は 2 つのドメインを そのまま比べ、どちらにも依存しない。また、評価が問い合わせる名前を すべて From ヘッダフィールドのドメインの下に留める。これが、本仕様が strict な整合を求める理由である。

メッセージを検証できるまま保つ。[=Originator=] は、 署名に使うのをやめた DKIM の selector の鍵を、その selector で署名した メッセージがまだ検証されうる間、公開し続けるべきである（SHOULD）。 [[RFC6376]] が失効と読む空の p= タグでレコードを公開する ことは、レコードを削除するのと同じく、その公開を終える。 [=Originator=] は、DKIM 署名から [[RFC6376]] の x= タグを 省くか、メッセージがまだ検証されうる期間より先に設定するべきである （SHOULD）。これらの期間の長さはここでは定めない。この枠組みの Operations document の事項であり、推奨値はまだ設定されていない （）。

メッセージを表示するときに DMARC を評価する [=Mail Client=] は、その鍵が 公開されなくなるとその評価に失敗し、x= を過ぎた署名を、 [[RFC6376]] が認めるとおり期限切れとして扱うことができる（Validate the Signature Header Field）。どちらの場合も、メッセージはもはや整合していない （ の手順 3）。

Sending Domain。[=Originator=] は、本仕様の下の メッセージを、自身の [=Identity=] であるかその配下にある [=Sending Domain=] からだけ送らなければならない（MUST）。 [=Originator=] は、From ヘッダフィールドが複数のアドレスを運ぶ メッセージ、または複数の From ヘッダフィールドを運ぶメッセージを、 本仕様の下で送ってはならない（MUST NOT）。[=Originator=] は、署名者の certificate の鍵を運び、かつ [=Sending Domain=] がその [=Identity=] で あるかその配下にある [=Core Profile=] を、複数の [=Identity=] について 含む [=Originator Profile Bundle=] を持つメッセージを送ってはならない （MUST NOT）（ の手順 3）。本仕様は [=Permitted Host Record=] を用いない。

複数の [=Identity=] の [=Core Profiles=] が署名者の鍵を運び、 [=Sending Domain=] がそれらの [=Identity=] のそれぞれであるかその 配下にある場合、どの [=Originator=] が 署名したかはメッセージのどこにも書かれておらず、手順は選ばずに失敗 する。そのため、example.jp と mail.example.jp のように入れ子の [=Identity=] を持つ組織は、 両方の [=Core Profile=] が運ぶ鍵でメールに署名しない。[=Identity=] ごとに 別の鍵を使うか、bundle に [=Core Profile=] の一方だけを入れる。
代理送信に [=Permitted Host Record=] は要らない。strict な整合の下では d= のドメインは From ヘッダフィールドのドメインなので、 メールサービス事業者は [=Originator=] 自身のドメインの下で署名し、鍵は そこに公開されるか、そこから別名または委任で辿られる。自身の [=Identity=] の外にある登録ドメインから送る [=Originator=] は、その ドメインについて、そのドメインを [=Identity=] とする [=Core Profile=] を 示す。
後の改訂で、[=Originator=] の [=Identity=] の外にある [=Sending Domain=] を [=Permitted Host Record=] によって認めることがありうる。その場合、 そのレコードは の手順 3 の 問い合わせより前に問い合わせる。[=Sending Domain=] が結び付けられて いないメッセージについて、DKIM の鍵や DMARC のポリシーレコードを 問い合わせないためである。

Verifier が Sending Domain をどう取るか。[=Verifier=] は、Core Specification [[OPF-CORE]] がドメイン名を比較する 際の正準形に [=Sending Domain=] を変換しなければならない（MUST）。 その形にできない [=Sending Domain=] は、正準形にできない値すべてに ついて Core Specification が求めるとおり、検証の失敗となる（手順 1）。From ヘッダフィールドのドメインが国際化ドメイン名で ある場合（[[RFC6531]] の下で送られたメッセージではありうる）、 [=Verifier=] は、[[RFC8616]] がメール認証のために定めるとおりにそれを A-label に変換しなければならない（MUST）。これは DMARC の下で整合が 確立される際の形でもある。本仕様は他の変換を定めない。比較そのものは、 ある名前が別の名前の配下にあるとはどういうことかを含めて、Core Specification の規則である。

範囲外のメッセージ。経路の途中で DKIM の署名が壊れる メッセージは本仕様の範囲外である。メーリングリストがメッセージを 書き換える場合や、受信側のゲートウェイが件名に印を付け、本文に注意書きを 加え、またはリンクを書き換える場合がそれに当たる。本仕様は、そのような 中継者を越えて認証結果を運ぶために ARC [[?RFC8617]] に依拠しない。

受信者自身のメールシステムの中で書き換えられたメッセージは、DMARC を 自ら評価するその [=Mail Client=] にとって整合していない （）。本仕様が想定する配備は、銀行が 顧客に送るメールのようにフィッシング対策を主目的とするものであり、 メーリングリストを含まない。

整合の確立

Mail Client は DMARC を自身で評価する。本節は、[=Verifier=] がメッセージの整合をどう確立するか（[=Sending Domain=] はそこから取られる。）と、 どのメッセージが整合せず、したがって評価されないかを定める。 [=Mail Client=] は、メッセージの DKIM [[RFC6376]] の署名だけから、 DMARC のポリシーレコードの adkim タグが何を求めていても strict な整合の下で、自身で DMARC [[RFC9989]] を評価しなければならない （MUST）。

途中で記録された DMARC の結果。[=Mail Client=] は、 [[RFC8601]] の authserv-id が定める信頼境界の外から来た Authentication-Results ヘッダフィールドを無視しなければならない （MUST）。その境界の内側で、自身の [=Receiving Mail Server=] が付けた Authentication-Results ヘッダフィールドが記録する DMARC の結果は、 次のように扱う。

  • fail：[=Mail Client=] は、自身の評価が pass であっても、 そのメッセージを整合していないものとして扱わなければならない （MUST）（ の手順 3）。
  • pass：それは [=Mail Client=] 自身の評価の代わりには ならない。
  • それ以外の値（たとえば none や temperror）： その評価に影響しない。

自身の [=Receiving Mail Server=] が付けたヘッダフィールドを見分けられない [=Mail Client=] には尊重すべき記録された結果が無く、自身の評価に基づいて 進む。

DNSSEC と Issuer Pinning Record

Sending Domain の zone。[=Originator=] は [=Sending Domain=] の zone を、[=Verifier=] がその zone のレコードを 認証されたデータとして得られるように（）、 DNSSEC で署名させなければならない（MUST）。[=Originator=] は、その zone を、そこにある名前の不在が 認証された否定で示されるように署名させなければならない（MUST）。 NSEC レコードで、または Opt-Out フラグを持たない NSEC3 レコード [[?RFC5155]] で署名させる。

存在は Secure な応答からだけ、不在は認証された否定からだけ。[=Verifier=] が、本仕様が問い合わせさせる、その zone の中の名前を 問い合わせるとき、その名前が存在することを示すのは Secure な応答だけであり、不在であることを 示すのは認証された否定だけである（）。 Core Specification が定める名前についても、Core Specification が同じ ことを述べている（[[OPF-CORE]], DNSSEC Requirements and Resolution Outcomes）。

署名されていない、または認証できない zone は検証に失敗する。[=Sending Domain=] の zone が署名されていない場合、または [=Verifier=] がそのレコードを認証できない（応答が Insecure、Bogus または Indeterminate である）場合、 の手順 3 の表の 1 行目が述べる とおり、本仕様の下での検証は失敗する。[=Verifier=] は、 そのようなメッセージを、Core Specification [[OPF-CORE]] の意味で pin されていない [=Originator=] を提示しているものとして扱ってはならない （MUST NOT）。

Opt-Out の下では、名前の否定、たとえばもう公開されていない DKIM の selector の鍵の否定は Insecure となり、 検証を失敗させる（ の手順 3）。 認証された否定であれば、メッセージは整合していないままになるところで ある。

Issuer Pinning Record。[=Originator=] は、自身の [=Identity=] の zone において、自身に対して [=Core Profile=] を発行する ことを許された [=Core Profile Issuers=] を、その [=Identity=] の [=Issuer Pinning Record=]、すなわち Core Specification [[OPF-CORE]] が その目的のために定めるレコードにおいて名指ししなければならない （MUST）。Core Specification は [=Originator=] にこのレコードを要求 しない。このユースケースでは要求される。

[=Verifier=] は、受け取った [=Core Profile=] をそのレコードに照らして 検査しなければならない（MUST）。[=Verifier=] は、次のいずれの場合も 検証を失敗させなければならない（MUST）（ の手順 4）。

  • そのレコードが認証されたデータとして不在である。
  • 応答が Insecure である。
  • 応答が別名を経て到達したものである（Core Specification はこの レコードについてそれを Insecure な応答 として読む）。
  • そのレコードがその [=Core Profile=] の issuer を名指ししていない。

これらのいずれも、Core Specification が認証された不在と Insecure な応答に与える読みのように [=Originator=] を pin されていない状態のままとはしない。

[=Identity=] の zone はいずれにせよ署名されている。[=Sending Domain=] は その [=Identity=] そのものであるかその配下にあり （）、そのレコードが認証された データとして [=Verifier=] に届くのは、その [=Identity=] の zone を通る 署名された経路に沿ってだけだからである。ただしこのことは、Core Specification が認めるとおりこのレコードの名前が委任された先の zone には及ばない（[[OPF-CORE]], Records Published by the Originator）。[=Identity=] の zone にその DS レコードが無ければ、その zone からの応答はすべて Insecure である。
この要求の費用は、いずれにせよ署名される zone における 静的なレコード一つ分である。それによって得られるのは、[=Core Profile Issuer=] から独立した 手段、すなわち [=Originator=] が電子メールでの自身の [=Originator Profile=] の利用を止める手段であり、また誤って発行された [=Core Profile=] に対する第二の要素である。電子メールに対する主たる 脅威であるフィッシングに対して、その独立した手段は費用に見合う。

issuer のレコードは Core Specification のものである。issuer が公開する レコード、すなわち各 issuer の [=Issuer Key Record=]、[=Core Profile Issuer=] の [=Originator Key Records=]、および [=Profile Annotation Issuer=] の [=Revocation Records=] は、 Core Specification [[OPF-CORE]] が定める。本仕様はそれらに対して Core Specification の要求以上のものを置かない。

  5. Core Profile を検査する（DNS）。一般の手順 （[[OPF-CORE]], Procedure の手順 5）と同じである。ただし [=Time of Judgement=] は のものとする。issuer の鍵は、 メッセージが運ぶ [=Accreditation Chain=] の中の issuer の [=Core Profile=]、または [=Verifier=] が受け入れる [=Root Core Profile=] から取る。 署名の検証はこの手順のローカルな部分で あり、手順 4 と手順 6 の問い合わせより前に行う。
  6. Originator Key Record を検査する（DNS）。一般の手順と 同様。この問い合わせは、[=Core Profile=] の署名の検証（手順 5）の 後に行う。その名前は [=Core Profile=] から取るからである。

  7. Content Attestation を検証する。 S/MIME の署名が [=Content Attestation=] に当たる。それは手順 1 で検証し、その鍵は 手順 3 で照合した。一般の手順と同じく、その鍵が [=Core Profile=] について現に有効であること、すなわち手順 6 で取得した [=Originator Key Record=] がその [=Key Identifier=] を列挙している ことを確かめる。本仕様において [=Key Identifier=] は、 [=Content Attestation=] が名指すのではなく、[=Verifier=] が署名者の certificate から導出する（）。 それ以外の点では、この手順は一般の手順と同じである。

  8. 各 Profile Annotation を検査する（DNS）。一般の 手順と同じである。ただし [=Time of Judgement=] は のものとする。検証の時点で 署名の有効期間が終わった annotation は、その手順が述べるとおり、 [=Time of Judgement=] がいつであっても効力を持たない。その期間が 終わったことは検証の失敗ではない。[=Time of Judgement=] が受信の 時点である場合、受信の時点で何が効力を持っていたかは、その時点で 作られた記録からしか立証されない（）。

  9. 結果を導き、報告する。 一般の手順と同様。 none の結果は、失敗とは区別して、そのまま提示する （）。[=Verifier=] は、この枠組みの検査の 結果を S/MIME 署名の検証の結果とは分けて報告しなければならない （MUST）。

この手順が加える問い合わせ。この手順が行う DNS 問い合わせの数は一般の手順のそれに、次のものが 加わる。手順 3 における、評価する署名の DKIM の鍵と、From ヘッダ フィールドのドメインの DMARC のポリシーレコードである。 の下の評価は DNS Tree Walk を行わないので、 DMARC のためにほかの名前は問い合わせない。手順 3 の問い合わせは、[=Mail Client=] が評価するすべての メッセージについて行われる。[=Permitted Host Record=] は問い合わせない （）。

提示

Mail Client が提示するもの。[=Mail Client=] は、自身の検証の結果を、[=Originator Profile=] が [=Originator=] について述べることとともに、[=Recipient=] に提示する。 結果が pass である場合、一般の手順の出力（[[OPF-CORE]], Outcome and Time of Judgement）は、[=Originator=] の [=Identity=] と、効力を持つ [=Profile Annotations=] をそれぞれの issuer とともに与える。

どの属性をどう見せるか。[=Mail Client=] が提示する のは、[=Core Profile=] と効力を持つ [=Profile Annotations=] が [=Originator=] について運ぶ [=Validated Attributes=]、またはその うちこのユースケースが求める部分である。値だけでは、[=Verifier=] が 受け入れる [=Root Core Profile=] の下で立つ issuer が [=Originator=] を検証した、ということしか言わない。 どの属性をどのように見せるか（たとえば段階的に見せる）は、 [=Mail Client=] の UX の設計の事柄である。

三つの結果。本仕様の下の検証の結果は、次の三つの値のいずれかである。

  • pass: の検査が すべて通った。
  • fail: 署名された内容が [=Originator Profile Bundle=] を 運び、 の検査（手順 1 の S/MIME 署名の検証を含む）のいずれかに落ちた。
  • none: S/MIME で署名されていないか、署名された内容が [=Originator Profile Bundle=] を運ばないため（手順 1）、または 整合していないため（手順 3）、メッセージが本仕様の下で評価されな かった。それは失敗ではない。

決める最初の手順と、none の提示。手順は順に進む。メッセージが落ちた手順、または評価されないとわかった 手順のうち最初のものが、その結果を決める。[=Mail Client=] は、結果が none のメッセージを、本仕様が評価しなかったものとして、 失敗としてではなく提示しなければならない（MUST）。この区別は、提示が 運ばなければならないものの一部である。

どの DMARC の結果を提示するか。[=Mail Client=] が依拠する DMARC の結果は、自身の評価によるものである （）。提示でそれを [=Receiving Mail Server=] が記録していることもある結果と区別するかは ユーザインタフェースの設計による。本仕様はその区別を要求しない。

Core Specification が提示に既に求めること。annotation が有効であるかのように [=Verifier=] が提示してはならない ものは Core Specification [[OPF-CORE]] が述べる。結果が渡される あらゆる場面で pin された [=Originator=]、pin されていないもの、 および [=Issuer Pinning Record=] が参照されなかったものを区別する ことも同文書が要求する。どちらもここでは述べ直さない。このユース ケースでは最後のものは生じない。

受信の時点の結果を保つ。自身の結果に ついて seal した記録、または cache を保つ [=Mail Client=] は、受信の 時点の結果を保つために、 が認める とおりそれを用いることができる。

有効性、失効、そして時点

有効性の層

四つの層は Core Specification のものであり、Issuer Pinning Record もその一つを終わらせる。この枠組みの内側にある有効性の四つの層、すなわち鍵、[=Core Profile=]、 [=Originator=] の登録、各 [=Profile Annotation=] と、それぞれを 終わらせるものは、Core Specification のもの（[[OPF-CORE]], Revocation Model and Time Constraints）であり、ここでは繰り返さない。このユース ケースに固有のことの一つは登録の層にある。[=Issuer Pinning Record=] を取り除くことも有効性を終わらせる。その認証された不在は検証を失敗 させるからである（）。

枠組みの外の層。このユースケースに固有のもう一つの ことは、この枠組みの外側にある層である。署名者の X.509 certificate で あり、その有効性は S/MIME 実装が判断する。それは CRL または OCSP、 あるいは信頼しないという決定で終わり、certification authority と 受信側の当事者のポリシーがその手段を持つ。

層は互いに独立している。この枠組みの内側の四つの層と外側の一つの層は、それぞれ単独で判断され、この枠組みの 検査と S/MIME の検証のどちらが失敗しても検証は失敗する。両者を結ぶ唯一のものは鍵の同一性であるから、 両者の間に時間にわたる不変条件は要らない。certificate が失効しても [=Originator Profile=] は有効なままでありうるし、その逆も同様に 成り立ちうる。

発行に対する不変条件

Core Specification の不変条件がそのまま適用される。本仕様は、Core Specification が発行に対して置く不変条件（[[OPF-CORE]], Revocation Model and Time Constraints）に何も加えず、それらはこのユースケースでも そのまま適用される。第一に、[=Profile Annotation=] の有効性は、 それが annotate する [=Core Profile=] の有効性の内にある。第二に、退役した鍵の レコードは、それを運ぶ [=Core Profile=] が期限切れになるまで、同文書が 定める保持の余裕と例外のもとで保持される。第三に、issuer の鍵は、同文書が 求める期間だけ重なる。このうち 2 つ目は、事後に何を検証できるかを 左右する（）。退役した鍵は撤回されて いないので、それで署名されたメッセージは の手順 7 を引き続き通る。

置き換えられた鍵を retired として残すか withdraw するか

電子メールは置き換えた鍵を退役した鍵として残す。このユースケースにおいて、[=Originator=] は、置き換えた鍵を撤回せず、 退役した鍵として残すことが望ましい（SHOULD）。既に配送されたメッセージに 署名し直すことはできないからである。そのとき、置き換えた鍵で 署名されたメッセージは、その鍵を運ぶ前の [=Core Profile=] が期限切れに なるか失効するまで検証可能なままである。

Core Specification がユースケースに委ねること。Core Specification は、この選択を各 [=Use Case Specification=] に 委ね、2 つの道、すなわち鍵を退役した鍵として残す道と、コンテンツを 新しい鍵で署名し直して置き換えた鍵を撤回する道、およびその選択が何と 何を引き換えるかを述べている（[[OPF-CORE]], Key Compromise）。その引き換えには鍵を残すことの費用も含まれる。

退役した鍵が役に立つのは、その Core Profile が現行である間だけである。退役した鍵を運ぶ [=Core Profile=] はそれ自身が [=Time of Judgement=] において有効である必要があるので、その鍵が役に立つのはその profile が 現行である間だけである。その先の検証は の 第二と第三の段階に当たる。

判断時点

表示の時点か、記録した受信の時点。[=Mail Client=] にとって、[=Time of Judgement=] は表示の時点か自身が 記録した受信の時点のいずれかであり、以下のとおりである。これは、検証の 時点に代えて [=Use Case Specification=] が指定することを Core Specification [[OPF-CORE]] が認める別の時点であり、配送経路が [=Verifier=] に与える時点である。[=Verifier=] が時計のずれに対して 認める許容は、Core Specification の一般の手順のものである。

どちらの時点でもよく、Mail Client はどちらかを報告する。[=Mail Client=] は、メッセージ を表示する時点を基準とするか、またはメッセージを取り込んだときに自身が 記録した受信時点を基準として、受信時に下されたであろう判断を再現 するかのいずれかで、有効性を判断しなければならない（MUST）。どちらも 認められ、[=Mail Client=] はどちらを用いたかを報告しなければならない （MUST）。

受信の時点は評価の記録があるときだけ。[=Mail Client=] が受信の時点を基準に判断してよい（MAY）のは、 メッセージを取り込むときに DMARC を評価し、その評価の記録を保って いる場合に限る（）。したがって、 メッセージを表示するときにだけ DMARC を評価する [=Mail Client=] は、 表示の時点を基準に判断する。

受信の時点をどこから取るか。受信の時点を基準に判断する [=Mail Client=] は、その時点を 二つの出所のいずれかから取らなければならない（MUST）。一つは、 メッセージを取り込んだ時点についての自身の記録であり、 が求める DMARC の評価とともに作る。もう 一つは、[[RFC8601]] の authserv-id が定める信頼境界の内側で自身の [=Receiving Mail Server=] が付けたことを確かめられるヘッダフィールド である。その境界の外で記録された時点は、メッセージの送り手が選べた 時点だからである。本仕様はそのようなフィールドを名指ししない。 Received ヘッダフィールド [[RFC5322]] は、それを確かめるための authserv-id を持たないからである。

受信の時点は、メッセージがその受信者を欺きえた時点であり、受信時を 基準に判断する [=Mail Client=] にとっては、メッセージを取り込むときに その client が DMARC を評価した時点でもある。したがって、受信を基準に判断することは、 フィッシングに対して問題となる問いに答えている。記録された受信時点に 依拠できるかどうかは、記録された結果に依拠できるかどうかと同じ問いで ある。 を参照。

signingTime 属性は Time of Judgement ではない。CMS [[RFC5652]] の signingTime 属性は、[=Verifier=] の判断に 何の役も持たない。Core Specification [[OPF-CORE]] は、署名の属性として運ばれる時刻を含め、署名者が書いた時刻の値を すべて判断から除いており、signingTime はそのような属性である。

signingTime 属性と受信の時点との間に大きな食い違いがある場合に、 [=Verifier=] がそれを結果に記すべきかどうか、およびどれだけの食い違いを 大きいと数えるべきかは、決まっていない。ここでは規定しない。

事後の検証

三つの段階。[=Mail Client=] はメッセージを表示するたびにそれを検証するので、 事後の検証とは、その検証を後の時点で繰り返すことにほかならない。 それは best-effort で成功し、三つの段階を追って劣化する。

  1. [=Core Profile=] と [=Profile Annotations=] が期限切れになって いない間は、メッセージは受信時と同じ手順で検証できる。撤回と失効の 状態は現時点の状態であるから、メッセージの受信後に撤回された鍵は 検証を失敗させる。これは意図された振る舞いである。
  2. [=Core Profile=] が期限切れになった後でも、署名鍵のレコードが の規則の下でなお その [=Core Profile=] の [=Originator Key Record=] に保持されている 間は、鍵をその [=Originator Key Record=] と照合することはできる。 ただし [=Core Profile=] 自体は期限切れになっている。受信の時点で [=Core Profile=] が有効であったことは、そのとき、 その時点で作られた記録、すなわち [=Mail Client=] 自身が seal した記録 または cache によってのみ立証できる。
  3. その後は、DNS の中に過去の状態に答えるものは何もなく、受信時に何が 真であったかを立証するのは、その時点で作られた記録、すなわち [=Mail Client=] 自身が seal した記録または cache だけである。

最初の段階は Core Profile と同じだけ続き、何もそれを延ばさない。メッセージがこれらのうち最初の段階にとどまる期間は、そのメッセージが 署名された鍵を運ぶ [=Core Profile=] で決まる。すなわち、その [=Core Profile=] が期限切れになるか失効するまで続く （）。この枠組みも本仕様も、他の手段で それを延ばさない。DNS が答えるのは問い合わせの瞬間についてだけだから である。[=Revocation Record=] の不在は時点を運ばず、record はそれが失効 させる対象が期限切れになると取り除かれ、単に失効した登録はそこに あったという痕跡を残さない。段階の果てが更なる問い合わせではなく そのような記録であるのは、このためである。

添付として転送されたもの。message/rfc822 のパートに囲まれたメッセージは、それ自体で一通の メッセージとして検証できる。その bundle は囲まれた body の中にあり、 外側のメッセージの part としては数えない（）。 [=Mail Client=] は、内側のメッセージを表示の時点を基準に判断しなければ ならず（MUST）（）、内側のメッセージが 運ぶ Authentication-Results ヘッダフィールドを無視する。

内側のメッセージは変更されていないので、検証できる。[=Mail Client=] は 内側のメッセージがいつ受信されたかについて自身の記録を持たず、内側の メッセージが運ぶ Authentication-Results ヘッダフィールドは元の受信者の ために書かれたものである。

インラインで転送されたもの。インラインで転送された メッセージは、署名も bundle も残らないので検証できない。

replay されたもの。変更されずに別の受信者へ replay されたメッセージは、DKIM 署名が変わらない ので DMARC の下で整合したままであり、その受信者についても最初の 受信者のときと同じく検証に通る。それが変わっていないのは DKIM 署名が覆う範囲だけである。その h= タグの外の ヘッダフィールドは途中で置き換えられうるが、 が求める oversigning はそれを防ぐ。 replay が達成するのは、 [=Originator=] の本物のメッセージが、送られた先ではない [=Recipient=] について検証に通ることである。それを送っていない identity の下で コンテンツを提示させることはできない。

Security Considerations

[=Originator Profile Bundle=] はメッセージの内側を、S/MIME の署名が 覆う内容の一部として運ばれ（）、 [=Originator Profile=] のいかなる部分もネットワークから取得されない （）。したがって、経路上の攻撃者や、メッセージが 通過する保管場所にいる攻撃者は、bundle を差し替えることも付け加える こともできない。いずれも署名された内容への変更だからである。また、 そのような攻撃者が妨げたり覗いたりする取得も存在しない。同じ理由で、 Core Specification [[OPF-CORE]] が述べる上限を越えて本物の文書を 押し出すこと（displacement、他の文書で本物を締め出すこと）は、 送信者にしかできない。

その攻撃者にできるのは、署名と bundle をまとめて取り去り、通常の 署名されていないメッセージを残すことである。これは偽の結果を生まない。 [=Originator Profile=] を提示しないメッセージは、単に本仕様の下で 評価されない。本仕様を実装していないクライアントも同じように振る舞う （）。こうして、この枠組みの endorsement は転送中のメッセージから奪いうるが、メッセージに対して 偽造することはできない。

プロファイルを提示しないメッセージについて、本仕様は結果 none のほかには何も述べない。それはメッセージが評価 されなかったことだけを記録する（）。 その結果はメッセージに対する判断ではない。あるドメインが自身のメールすべてに署名していることを 知る必要のある [=Recipient=] は、ここからそれを知ることはできない。

Presented Identity をどう得て、どう結びつけるか

このユースケースにおいてコンテンツがその下で提示される identity は [=Sending Domain=] であり、それは DMARC [[RFC9989]] によってメッセージ から得られる（）。したがって、 コンテンツがそのドメインの下で届いたという保証は DMARC が与える保証で あり、本節はそれを所与とする。本仕様が加えるのは 2 つの規則である。 [=Mail Client=] は DKIM [[RFC6376]] だけから、strict な整合だけで DMARC を評価する（）。そして、あるドメインについて DKIM を通せる者、したがってその下でコンテンツを提示できる者が、 そのコンテンツを本仕様の下で検証させるには、それに加えて署名に用いる [=Core Profile=] の鍵が要る（）。

これこそが、その結びつけを [=Core Profile Issuer=] から独立したものに している。この独立性は、Core Specification [[OPF-CORE]] が各 [=Use Case Specification=] に述べることを要求しているものである。 発行されるべきでなかった [=Identity=] に対して発行された [=Core Profile=] が役に立つのは、その [=Identity=] から整合したメールも 送れる攻撃者に対してだけである。それは第二の、別の当事者の手にある、 別の失敗である。

このユースケースはその要素だけに拠ってはいない。[=Issuer Pinning Record=] がここでは要求され、その認証された不在は失敗である （）。したがって [=Originator=] は、 自身が求めていないプロファイルに対して自前の手段を持ち、 [=Core Profile Issuer=] がそれを revoke することに依存しない。 [=Originator=] の [=Identity=] でも その配下でもない [=Sending Domain=] は認められない。本仕様は [=Permitted Host Record=] を用いないからである （）。

この手段が及ぶのは [=Identity=] そのものまでである。Core Specification [[OPF-CORE]] が述べるとおり、サブドメインはそれ自体が一つの identity であるから、[=Originator=] の [=Identity=] の配下の名前は、自身の [=Issuer Pinning Record=] を伴う自身の [=Originator Profile=] を 持ちうる。親の [=Identity=] の zone にある [=Issuer Pinning Record=] はそれについて何も語らない。[=Originator=] が 自身の [=Identity=] の配下に委任するものは、この帰結を伴って委任される。

[=Sending Domain=] と [=Core Profile=] が運ぶ [=Identity=] との比較は 正準形の上で行われ、厳密である（）。 Core Specification [[OPF-CORE]] が述べるとおり、正準形が異なる 2 つの ドメインは、どれほど似て見えようとも別のドメインである。したがって、 他のドメインに似ているという理由で登録されたドメインは、それ自身に 結びつけられ、他の何にも結びつけられない。自分の知っている名前に似た 名前を [=Recipient=] がどう受け取るかは、この枠組みが答える問いでは ない。

このことが変換に置く重みは、ここでは一つの段に落ちる。 [=Sending Domain=] は、整合が確立されたのと同じ形にしなければならず、 国際化された名前についてそれは [[RFC8616]] の変換である （）。他の変換で作られた名前は 比較に失敗するので、そのような誤りは、通ってしまう検証ではなく、 失敗した検証に終わる。

認証された不在を失敗とせよという本仕様の要求（）は 別の事柄である。そこで問題になるレコードは、[=Sending Domain=] からでは なく [=Originator=] の [=Identity=] から作られる名前のところで問い合わせ られるので、[=Sending Domain=] のいかなる変換もそこには届かない。

From ヘッダフィールドから単一のドメインが定まらないメッセージは、 [=Sending Domain=] を持たない。[=Originator=] はそのようなメッセージを 送らず（）、[=Verifier=] はそれを 整合していないものとし、その結果は none である （）。

層は独立に失敗する

本仕様の下のメッセージは、独立に下される 2 つの判断に覆われている。 S/MIME の判断と、この枠組みの判断である （）。両者を結ぶ唯一のものは署名鍵の 同一性である。S/MIME 実装が署名を受け入れることは、この枠組みの検査と 並んで下される判断ではなく、その前提条件であり、署名が受け入れられない 場合、この枠組みの結果は の fail である。 は、 2 つの結果を分けて報告することを要求している。

bundle を運ぶメッセージの S/MIME の署名が失敗した場合、この枠組みの 結果は fail であり、そのメッセージについてこの枠組みが 述べることはほかに何も残らない。[=Originator Profile Bundle=] をこのメッセージに 結びつけるのはその署名だけであるから （）、検証できない署名が残すのは、同じ [=Originator=] の別のメッセージから持ち出されたかもしれない bundle、 あるいは [=Originator=] が何にも添えたことのない bundle である。 そのようなメッセージについて通った結果を報告する [=Verifier=] は、 endorse された当事者が署名していない内容に対する endorsement を報告 していることになる。

S/MIME の署名が検証でき、この枠組みの検査が失敗した場合に残るのは、 そのメッセージが certificate の運ぶ鍵で署名されたという事実である。 その鍵が [=Core Profile=] の名指しする [=Originator=] のものである ことは確立されていない。まさにそれが失敗したのだからである。

また、この枠組みの失敗は、 本文書が定めるままでは、それがどの失敗であったかを述べない。失効、 期限切れ、到達できない zone、そしてそれがカバーしないドメインから 提示されたプロファイルは、いずれも同じ結果に終わる。Core Specification [[OPF-CORE]] がそのいずれにおいても fail closed である ためである。攻撃と運用上の障害は結果によって区別されない。

この独立性は時間にわたっても及ぶ。この枠組みによる鍵の endorsement を 終わらせるのは、そのレコードを、それを列挙するすべての [=Originator Key Record=] から取り除くこと、またはその鍵を運ぶすべての [=Core Profile=] が期限切れになることである （、）。 どちらも S/MIME が署名を受け入れることを止めはしない。したがって、 あるメッセージの検証を完全に止めたい当事者は、両方の側でそれが撤回 されるように図らなければならない。

は、この枠組みの検査の結果を S/MIME 署名の検証の結果とは分けて報告することを要求しており、 はそのどちらをどう表示するかを定めて いない。したがって、S/MIME が署名を受け入れ、この枠組みの検査が 失敗したときに [=Recipient=] が何を示されるかは決まっていない。また、 表示の時点で両者が単一の表示にまとめられてしまえば、分けて報告する ことは何ももたらさない。本仕様がそれについて何かを述べるべきかどうかは、 本版では決まっていない。

Verifier がどこに置かれ、そこで DNSSEC の validation をどう得るか

[=Mail Client=] は、依拠できる DNSSEC の validation 状態を必要とする。 その状態は Core Specification [[OPF-CORE]] が認める 2 つの手段の いずれかで得られる。すなわち、自身の trust anchor で validate するか、resolver を認証し応答を保護する経路で validating resolver の言うことを受け取るかである。[=Mail Client=] は利用者のいる ところで動き、それは自身の制御下にないネットワークであり、その端末に 与えられた resolver が何であれそれを使う。 がこの要求を明示的に述べているのは、 この当事者のためである。

[=Mail Client=] とその resolver との間の経路を押さえた攻撃者を考える。 クライアントがその要求を満たしている場合、攻撃者は応答が届くのを 妨げられるが、応答を選ぶことはできない。攻撃者が得るものは、 このユースケースが失敗を不在と読むことが決して無いことによって 抑えられている。手順が参照するすべての名前は fail closed であり、 [=Verifier=] が認証できないレコードは失敗であって、pin されていないという 結果には決してならない（）。

Core Specification [[OPF-CORE]] が最も注意して防いでいる格下げ、すなわち pin された [=Originator=] を pin されていないものに変えることは、 ここでは対応物を持たない。[=Issuer Pinning Record=] は このユースケースでは要求され、その認証された不在は失敗である。 Core Specification はこのレコードを要求せず、その不在を [=Originator=] が pin されていない状態のままとして読む。Core Specification だけに従う [=Verifier=] はレコードが不在でも先へ進む。 このユースケースがしないのはそれである （）。

したがってそのような攻撃者は、経路を押さえている間は検証を抑え込む ことができる。クライアントが自身で validate する場合にありうるように 問い合わせが平文で resolver に届く場合には、狙った [=Originator=] に ついてそうすることができる。問い合わせの名前が、どれが検証されて いるかを語るからである。

攻撃者にできないのは応答の偽造である。攻撃者が仕立てた レコードは認証されておらず、要求を満たすクライアントは認証されていない ものに基づいて動かない。ただし攻撃者は、署名された時点では認証されて いた応答を replay できる場合がある。これは別の限界を持つ別の攻撃で ある（）。

その要求を満たしていないクライアントには、そのような限界が無い。 平文の応答における AD ビットのような、認証されていない validation の しるしを受け取ることは、すべての DNS 応答を攻撃者の選択に委ねることで ある。そのときこの枠組みは、[=Originator Profile Bundle=] の中の文書が 既に主張していること以上には何も加えない。Core Specification [[OPF-CORE]] は、これをその要求の理由として述べている。

抑え込みは小さなことではない。失敗を示された [=Recipient=] は、経路上の 攻撃者と一時的に到達できない zone とを区別できず、どちらの場合も同じ 結果が報告される。また、代わりに使える弱い検査も無い。どちらの手段も 持たない [=Mail Client=] はそもそも検証できず、本仕様の下で評価される べきメッセージはすべて失敗する。プロファイルを提示しないメッセージは、 そもそも評価されない（）。

認証された不在の replay

この攻撃の一般の形は Core Specification [[OPF-CORE]] にある。[=Verifier=] と権威サーバとの間の経路上の攻撃者は、署名された時点では真であった 応答を、その応答に対する署名が有効である限り replay できる。これには [=Revocation Record=] が存在しなかったことの証明も含まれる。 この手順が不在を確かめる名前は、この攻撃から一様に影響を受ける わけではない。

[=Profile Annotation=] の [=Revocation Record=] においては、不在こそが その annotation を有効なままにするものであり （ の手順 2 と手順 8）、この手順の中で そうなる唯一の名前である。そこで不在を replay すれば失効は隠され、 annotation は検証され続ける。この手順が参照する枠組みの他のすべての名前、 すなわち各 issuer の [=Issuer Key Record=]、[=Issuer Pinning Record=] と [=Originator Key Record=] においては、 要求されるのは存在であって、不在は失敗である （、 ）。そこで不在を replay しても、 検証が失敗するだけであり、問い合わせを妨げた場合に 得られるもの以上のものは攻撃者に何ももたらさない。

メールに固有なのは、同じメッセージが何度も繰り返し検証されることで ある。[=Mail Client=] はメッセージを表示するたびに検証する （）。したがって経路を押さえた攻撃者は、 配送の 1 回だけではなく、読まれるたびに機会を得る。そして保存された メッセージは、届いてから長く経った後に読まれる。

攻撃者が去れば、同じ事実は受信者 に有利に働く。replay された不在の下で受け入れられたメッセージは、次の表示の ときに改めて検証され、そのとき失効が現れる。この窓は、Core Specification [[OPF-CORE]] が述べるとおり、その不在を返したゾーンの RRSIG の有効期間のままであり、 メッセージが古いからといって延びることはない。

転送

インラインで転送されたメッセージ、すなわち本文が別のメッセージの body に引用されたものは、[=Originator Profile Bundle=] を運ばないので、 元のメッセージについて何も検査できない （）。そのような body の中にある、 元のメッセージが検証されたという主張は、引用された本文の一部であり、 転送した者の値打ちとちょうど同じだけの値打ちしかない。

転送するメッセージ自体が本仕様の下で署名されている場合、検証される のは転送者である。[=Sending Domain=] は評価されるメッセージのそれで あるから（）、別のメッセージを引用 するメッセージについて有効な結果を示された [=Recipient=] は、引用した 当事者についての有効な結果を持つのであって、引用された当事者について は何も持たない。インラインの転送が最も読み違えられやすいのはこの場合 である。表示すべき結果が存在し、しかもそれが、読み手が目にしている 内容についての結果ではないからである。

Privacy Considerations

本節は何も要求しない。 の 問い合わせが何を、誰に対して明かすか、およびそれを限るために設計が何を しているかは、Core Specification [[OPF-CORE]] の privacy considerations に あり、ここでは繰り返さない。このユースケースが加えるのは、当該仕様が [=Use Case Specification=] に委ねているもの、すなわち問い合わせがいつ、 どの当事者によって行われるか、および [=Originator=] 自身の zone に対して 行われる問い合わせが何を名指しするか、である。

問い合わせがいつ行われるか

[=Mail Client=] はメッセージを表示するたびにそれを検証する （）。したがって、その cache が答えない 問い合わせはメッセージが開かれたときに行われ、問い合わせの時刻は メッセージが読まれた時刻である。

メッセージが取得されるのを見ている受信者自身のプロバイダを除けば、 メールの中の何も、メッセージがいつ読まれたかを明かさない。メッセージは 読まれる前に配送され、読む行為は受信者自身のシステムの上で起こり、 そのとき [=Originator Profile=] を構成する文書がどこかから取得される こともない（）。残るのは DNS の問い合わせで ある。表示の時点で検証することは、それに読む行為の時刻を与える。こうして、受信者自身のシステムの外のどこからも見えな かった出来事が、それらの問い合わせを見る当事者に見えるようになる。

それらの問い合わせの中には、[=Mail Client=] が DMARC を評価するために 行うもの、すなわち署名の DKIM の鍵と、そのドメインの DMARC のポリシー レコードの問い合わせがある。Mail Client は検証するすべての メッセージについてこれを行う（）。 メッセージを表示するときに DMARC を評価する [=Mail Client=] は、他の 問い合わせと同様、読む時刻にそれらを行う。背景で同期するクライアントの ように、メッセージを取り込むときに DMARC を評価するものは、メッセージが 届いたときにそれらを行い、読まれる時刻からは切り離される。

問い合わせが何を名指しするか

issuer が公開する [=Originator Key Records=] と [=Revocation Records=] は不透明なラベルで名づけられており、そのため resolver と権威サーバとの間の観測者は、issuer の record のどれかが 検査されていることは知るが、それが誰のものかは知らない。これは Core Specification [[OPF-CORE]] が述べる性質であり、ここでも変わらずに成り立つ。 しかしそれは [=Originator=] 自身の zone にあるレコードには及ばない。

[=Issuer Pinning Record=] は [=Originator=] の [=Identity=] から 作られる名前の下に公開され、その名前はドメインそのものを運ぶ。 このユースケースはそのレコードを要求するが、Core Specification は 要求しない （）。したがって、その問い合わせは本仕様の 下で評価されるすべてのメッセージについて行われる。これに対して一般の 手順において [=Verifier=] がそのレコードを参照するのは、その [=Use Case Specification=] が要求する場合か、[=Verifier=] が自ら そうすることを選ぶ場合だけである。このユースケースでは [=Permitted Host Record=] を問い合わせない （）。

前節と合わせると、これは、[=Mail Client=] が用いる resolver が、その 利用者がどのドメインからのメールをいつ読むかを見る、ということを意味 する。その resolver は利用者の端末に与えられたものであり、同時に クライアントが認証された経路で到達することを求められる resolver でも ある（）。この露出は、利用者または ネットワークが選んだ resolver に向かうものであり、それに対する手立ては Core Specification [[OPF-CORE]] があらゆる問い合わせについて挙げる ものである。

[=Originator=] 自身の zone は、それらの問い合わせを、 自身の resolver が生む集約の形で、cache によって減じられた上で見る。 一つのレコードがその [=Originator=] からのすべてのメッセージに用いら れるからである。そして、問い合わせは resolver から届くので、どの [=Recipient=] が尋ねたかは知らない。

DMARC の評価のための問い合わせは、From ヘッダフィールドのドメインを 名指しし、DKIM の鍵は署名の selector と d= のドメイン から作られる名前の下で問い合わされる。そのドメインは、 strict な整合の下では同じそのドメインである。 selector は送信者が各メッセージに書き込む値である。

もし selector が受信者ごと、あるいはメッセージごとに異なれば、 問い合わされる名前がそのメッセージを特定する。そのとき、送信者の zone に 届いたその問い合わせは、そのメッセージが開かれたこと、そのおおよその 時刻、どの resolver を通してかを送信者に知らせる。その名前を共有する 他のメッセージは無いので、cache によって集約されて消えることもない。

は、[=Originator=] に対して、 そのような selector の使い方を禁じている。[=Mail Client=] はそのような使い方を 検出できないので、この保護はクライアントが行う何かではなく、送信側に 対する要件に拠っている。

[=Mail Client=] がメッセージを表示するときに検証し、それによって自身の resolver に対して、また集約の形で [=Originator=] の zone に対して、 その [=Originator=] からのメッセージがおよそその時刻に読まれたことを 明かすことは、 と が要求するレコードとから導かれる。 受信の時点を基準に判断してもそれは無くならない。DNS における存在または 不在の検査は、有効性をどの時点を基準に判断するかにかかわらず、 問い合わせの瞬間の状態の検査だからである。したがって、受信を基準に 判断する [=Mail Client=]（）も、 表示するときにやはり問い合わせる。 本仕様がこの露出について何かを述べるべきかどうかは、本版では決まって いない。

Web Media Use Case Specification との違い

本付録は、本仕様が Web Media Use Case Specification [[OPF-WEB-MEDIA]] とどのように異なるかを述べる。構造上の結論は、Email のユースケースがこの枠組みの DNS 設計に一行も加えないということである。 違いは次の五つの項目に分かれる。(1) [=Originator=] 自身のレコードに 何が要求されるか。(2) [=Presented Identity=] をどう取り、どの文書が結びつけを宣言 するか。(3) 外側の certificate の層があるかどうか。(4) 検証がどこで 行われ、どの時点を基準に判断し、その結果が保たれるかどうか。(5) [=Originator Profile=] が何からなるか。

この表と、Web Media [=Use Case Specification=] の付録「Differences from the Email Use Case Specification」にある表とは、一つの表を両側から書いた ものである。両者は整合させておくものとし、一方に行を加えたら他方にも 加える。
